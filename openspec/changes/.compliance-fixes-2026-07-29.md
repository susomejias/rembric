Plain working note, **not** an OpenSpec artifact. Three defects bringing shipped
code into line with already-published specs, plus one test hardening. No change
folder: nothing here adds API surface, and `openspec/specs/` was not edited —
the specs were already correct.

Tree note: a concurrent agent held `apps/server/src/dashboard/**` (graph view)

## Defect 1 — the entity channel admitted `superseded` rows

`openspec/specs/memory-entities/spec.md:348` requires "an existing **active**
memory"; `findOtherMemoriesForEntity`'s own doc comment says "Other **active**
memories". The predicate was `status != 'archived'`, which admits `superseded`.

**Fix** — `apps/server/src/db/repositories/entities-repository.ts:298`:
`sql\`${memory.status} != 'archived'\``→`eq(memory.status, 'active')`.
Sole production caller is `services/save-time-candidates.ts:183`.

### Impact measured, with denominators

**On the retrieval eval corpus as shipped** (`test/retrieval/corpus.ts`, 40
items, ingested by `ingestCorpus` through the real save path with the real
`loadEmbedder()`): the entity channel contributed **0 candidates of any
status**, so the superseded subset was **0 of 0**.

That 0 is vacuous, and the denominators say why — nothing could have made it
non-zero:

| quantity on the eval corpus                      | value |
| ------------------------------------------------ | ----- |
| memory rows (38 active / 2 superseded)           | 40    |
| entity links in total                            | **2** |
| distinct entities                                | 2     |
| rarity-gate evaluations across all 40 saves      | 2     |
| `findOtherMemoriesForEntity` calls (gate passed) | 2     |
| rows it returned (any status)                    | **0** |
| **superseded rows carrying ≥1 entity link**      | **0** |

The corpus prose carries almost no extractable addresses, so each of its 2
entities is linked to exactly 1 memory — the just-saved row, which is excluded.
The corpus is not an instrument for this quantity.

**On an instrument that can detect it** — the same real corpus plus 6
entity-bearing items forming two `topic_key` chains (real file paths, real
`ETIMEDOUT`/path entities), 46 items, same real embedder and save path:

| entity-channel rows returned during ingest | before fix | after fix |
| ------------------------------------------ | ---------- | --------- |
| total                                      | 5          | 3         |
| `active` targets                           | 3          | 3         |
| **`superseded` targets**                   | **2**      | **0**     |

So **2 of 5 (40%)** entity-channel candidates were non-compliant. Denominator
for the superseded side: 2 superseded rows carried entity links, out of 4
superseded rows.

### Neighbouring predicates checked, deliberately NOT changed

- **`:164` `findMemoriesByEntity`** — correct as-is. Documented: an omitted
  `status` means "any but archived" because the entity retrieval path is
  specified as complete within scope. Different contract, different requirement.
- **`:242` `scopeActiveMemoryCount`** and **`:266` `entityLinkCount`** — the
  rarity gate's denominator and numerator. Both use `!= 'archived'` and both
  disagree with their own names/doc comments ("active"). **Not changed**, because
  they are not _provably_ spec-violating: the only governing scenario
  (`memory-entities/spec.md:363`) is one-directional — "an entity linked to a
  large share of the scope's **active** memories → SHALL NOT generate
  candidates" — and `!= 'archived'` still satisfies it, since active rows are
  counted on both sides of the ratio. No published requirement constrains the
  converse.

  There is a real latent degradation worth its own OpenSpec change, recorded
  here rather than fixed silently: because a long `topic_key` chain concentrates
  many superseded links on one entity, the gate can block the channel for that
  entity. E.g. 100 active + 52 superseded chain rows all naming `foo.ts` gives
  53/152 = 0.35 > 0.15 → blocked; on active-only counts it is 1/100 = 0.01 →
  admitted. That silently disables the entity channel for exactly the evolving
  topic it is most useful on. Note `tune-hot-query-paths` task 4.5 already plans
  to rework `scopeActiveMemoryCount`, so that is the natural place to fix it.

### Regression test

`db/repositories/entities-repository.test.ts` — "returns only active rows".
Fixture places the superseded and archived rows at **newer** `created_at` than
the active one, so under `ORDER BY created_at DESC` a wrong predicate surfaces
them at index 0 rather than being hidden by scan order.

**Mutation check** (match count asserted as 1 before mutating): predicate
reverted to `!= 'archived'` → **1 failed | 22 passed (23)**, failing with
`expected [ 'm_superseded', 'm_active' ] to deeply equal [ 'm_active' ]` —
i.e. the superseded row appeared first, opposite to the assertion. Restored →
**23 passed**.

## Defect 2 — `not_conflict` dismissal walked one predecessor, not the chain

`openspec/specs/memory/spec.md:509`: the dismissal "SHALL be carried forward by
**walking the `replaces` chain**". `saveWithTopicKey` sets
`replaces = [prior.id]` — a single element — so a pair dismissed two saves ago
re-surfaced.

**Fix** — `services/save-time-candidates.ts`: the not_conflict lookup's source
set is now a bounded breadth-first `replaces` ancestry (`collectAncestorIds`)
instead of `saved.replaces`.

Reuse, per the brief: each hop is the **existing** content-free ancestry read
`MemoryRepository.findReplaces` (selects only the `replaces` column, PK probe),
and the depth bound is the **existing** `PREDECESSOR_CAP = 10` that
`memory.get`'s `collectPredecessors` uses (exported from `services/memory.ts`).

A walk over `memory_replaces` was rejected: its PK is
`(predecessor_id, successor_id)`, so the ancestry direction (by `successor_id`)
has no index and would be a table scan, or need a new index + migration.

`excludeIds` was deliberately left on the direct `saved.replaces`, matching the
spec's separate clause ("rows already linked to it via `replaces`"); only the
dismissal source set widened.

### Hot-path cost measured — 1k / 20k / 50k rows

Corpus of realistic ~1.3KB bodies plus a 14-deep `topic_key` chain (deeper than
the cap, so the walk is measured at its bound), `ANALYZE` run, 2000 iterations.

| measurement                            | 1k        | 20k       | 50k       |
| -------------------------------------- | --------- | --------- | --------- |
| BEFORE `listNotConflict(1 source id)`  | 0.0275    | 0.0223    | 0.0218    |
| ADDED walk (10 PK probes)              | 0.1200    | 0.1283    | 0.1342    |
| AFTER walk + `listNotConflict(10 ids)` | 0.1536    | 0.1579    | 0.1570    |
| **delta added**                        | **0.126** | **0.136** | **0.135** |

All ms. The delta is **flat in corpus size** — it is 10 primary-key probes, not
a scan. The widened `IN` list costs 0.007–0.010 ms of it.

Against the save path it sits in:

| denominator (ms)                                  | 1k        | 50k       |
| ------------------------------------------------- | --------- | --------- |
| FTS candidate pass alone                          | 0.71      | 33.2      |
| `scopeActiveMemoryCount` (already per-save)       | 0.047     | 1.41      |
| **end-to-end `saveWithTopicKey` + full detector** | **5.64**  | **188.1** |
| delta as share of that end-to-end path            | **2.39%** | **0.07%** |

The end-to-end figure excludes the embedder, so it is the _smallest_ honest
denominator; a real save additionally runs an ONNX forward pass.

Two further facts that settle it:

- **A save without a `topic_key` pays nothing.** `replaces` is empty → the walk
  returns `[]` having issued **zero** queries, and the relations lookup is
  skipped exactly as before. Only `topic_key` re-saves walk at all.
- The measured spread between two structurally identical save paths
  (topic re-save 5.64 ms vs plain save 6.45 ms at 1k) is ~0.8 ms — roughly **6×
  larger than the 0.135 ms added**. The delta is inside the noise band.

**Decision: landed.**

Residual, stated plainly: the cap is 10, so a dismissal more than 10 supersedes
back still re-surfaces. That is the deliberate price of the bound the brief
required; an unbounded walk was not acceptable.

## Defect 3 — `EXPECTED_TABLES` tolerated unclassified tables

`test/schema-drift.test.ts` asserted only "every expected table is present" and
tolerated extras. It was missing **five** owned tables, not the two reported:

- `memory_replaces` (already listed in this same file's
  `EXPECTED_WITHOUT_ROWID_TABLES`, which proves the omission was an oversight)
- `prompts_fts`
- `oauth_authorization_codes`, `oauth_clients`, `oauth_tokens` — all three are
  Drizzle-declared in `db/schema/oauth.ts`

Also added the four `prompts_fts_*` shadows, for symmetry with the `memory_fts_*`
shadows that were already enumerated. `EXPECTED_TABLES` now enumerates all 28
non-vec0 tables (actual DB total: 37).

**Tolerance tightened rather than kept.** Exact-set equality is now asserted for
every table not matching a new `VERSIONED_SHADOW_TABLE = /^memory_vec_/`. Only
the sqlite-vec shadow layout genuinely varies by extension version (the
`metadatachunks*` / `metadatatext*` tables appear only once metadata columns
exist). FTS5's shadow set is fixed by the table's own options, so it is
enumerated — `_content` appearing would mean a migration silently stopped using
external content, which is drift worth failing on.

The pre-existing `SHADOW_TABLE` regex was **not** narrowed: three other
assertions (index snapshot, PK drift, WITHOUT ROWID) rely on it, and the index
set genuinely does vary where the table set does not. Its comment was corrected
to say so. No assertion in `test/invariants.test.ts` was touched.

**Mutation checks** (each match count asserted before mutating):

| mutation                                                    | result                                                      |
| ----------------------------------------------------------- | ----------------------------------------------------------- |
| A: drop `memory_replaces` from `EXPECTED_TABLES`            | **1 failed / 8 passed**                                     |
| B: inject a stray `CREATE TABLE stray_drift_table(x)`       | **1 failed / 8 passed**, diff shows `+ "stray_drift_table"` |
| C: stray table present **but** new exact-set assert removed | **9 passed** — the old tolerant form lets it through        |

C is the point: it demonstrates the tolerance itself was the hole, not just the
five missing names. Restored → **9 passed**.
