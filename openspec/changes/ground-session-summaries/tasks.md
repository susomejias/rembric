## 1. Truncation: one direction, one constant

- [x] 1.1 Make `truncateSummary` tail-keeping with a leading marker: `marker + s.slice(-(SUMMARY_MAX_CHARS - marker.length))`, still surrogate-pair safe, still never exceeding `SUMMARY_MAX_CHARS`.
  - Needed a new helper: `sliceWithoutSplittingSurrogatePair` guards the END of a head-slice, and the tail-slice's orphan risk is the mirror image — a LOW surrogate first, not a high one last. Added `sliceTailWithoutSplittingSurrogatePair` beside it. `SUMMARY_TRUNCATE_SUFFIX` renamed to `SUMMARY_TRUNCATE_MARKER`, since it no longer suffixes anything.
  - **`truncateTitle` deliberately still head-keeps.** A label's meaning is at its start; flipping both for symmetry would have been wrong. The two directions now differ on purpose and the docstrings say why.
- [x] 1.2 Test the boundary arithmetic directly: exactly `SUMMARY_MAX_CHARS` is unchanged; `+1` yields a marked result of exactly `SUMMARY_MAX_CHARS`; the result's tail equals the input's tail; a surrogate pair at the cut point is not split. **Mutate each assertion** — restore head-keeping and confirm the tail assertion fails, because an assertion on length alone passes under both directions.
  - **Done, and the mutation confirmed it.** Added "keeps the END of the text and discards the beginning" (a `HEAD-MARKER … TAIL-MARKER` fixture) and flipped the emoji test to the low-surrogate direction. Restoring head-keeping fails **exactly** that one new assertion out of 82 — the pre-existing length and marker-presence assertions passed under both directions, which is why they were not sufficient. Six call sites that asserted `endsWith('…[truncated]')` updated to `startsWith`.
- [x] 1.3 ~~Derive the plugin's wire bound from the server constant. It SHALL NOT exceed the server cap.~~ **Task text corrected — this was the wrong call and the delta spec was amended with it.** `_transcript.sh:33-40` states its own rationale for exceeding the cap and the rationale is sound: a client cannot know a given server's cap at runtime, so a plugin hard-bounded to one version's value would silently under-deliver against a server whose cap is higher, and the server is meant to be the only authoritative trimmer. Forcing the plugin to cut exactly at the cap would also require duplicating the truncation marker into bash, Python and TS — four copies of one string, which is the duplication pattern this repo keeps getting burned by.
  - **The defect was the DIRECTION, not the size.** Two successive tail-cuts are idempotent (the result is the last `min(bounds)` chars of the original); a tail-cut followed by a head-cut is what produced the middle window. So `RBR_TRANSCRIPT_MAX_CHARS` stays above the cap, its misleading comment is corrected, and the missing guard — that every client trims the SAME SIDE the server does — becomes 1.4.
- [x] 1.4 Add an invariant test asserting every client-side trim keeps the same SIDE as the server's. Asserting the two _numbers_ agree would have been the wrong guard — it would have failed on a correct tree and passed on the broken one, since the numbers disagreed harmlessly while the sides disagreed fatally.
  - Added `invariants.test.ts::"summary truncation keeps the same side in every layer"`. One entry per language pinned to that language's real tail idiom, each asserting the tail form is present AND the head form is absent: bash `${out: -$RBR_TRANSCRIPT_MAX_CHARS}`, opencode `body.slice(body.length - MAX_TRANSCRIPT_CHARS)`, Hermes `transcript[-_SUMMARY_MAX_CHARS:]`. Plus one asserting `truncateTitle` still keeps the HEAD, so the deliberate asymmetry is pinned rather than looking like an oversight.
  - **Mutation-checked in both directions**: flipping the server to head-keep fails the server assertion; flipping Hermes to `transcript[:_SUMMARY_MAX_CHARS]` fails its own. My first version of the guard used one regex narrow enough to miss opencode's `slice(body.length - N)` form — it failed on a correct tree, which is the other way a guard can be wrong.
- [x] 1.5 Confirm no migration is needed and say why in the task: truncation is a write-time transform and stored rows are never rewritten. Rows written before this change keep their head-slice — which is the reason the marker's position must distinguish the two.
  - Confirmed: `truncateSummary` is called by the HTTP layer on the way in, and no code path rewrites a stored `summary`. A pre-existing head-truncated row keeps its trailing marker; a row written from now on carries a leading one, so the two are distinguishable on inspection without a migration.
