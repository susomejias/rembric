## Why

**Pi loses memory→session attribution silently, today, every time a user types `/new`.** The Pi extension never marks its Rembric session ended: `apps/plugin/.pi-plugin/index.ts:328` handles `session_shutdown` by awaiting `core.flushSessionSummary()` and `mcp.close()`, then `core.forgetSession()`, and ignores the event payload entirely (the parameter is named `_event`). The shared core it flushes through knows exactly two session paths — `POST /api/<slug>/sessions` (`apps/plugin/bin/rembric-plugin-core.mjs:130`) and `POST /api/<slug>/sessions/<id>/summary` (`:222`, `:249`) — and no `/end` path at all.

The cost is not the dashboard row. After `/new`, `/resume` or `/fork`, the old row is still `active` and a second `active` row exists for the same `(token, project)`. `findActiveForTransport` is deliberately "sole match or nothing" — `apps/server/src/db/repositories/agent-sessions-repository.ts:168`, `return rows.length === 1 ? rows[0] : undefined;`, commented "No ORDER BY: 'sole match or nothing' makes it unobservable." So for the whole `TRANSPORT_STALENESS_MS` window (30 min, `apps/server/src/services/agent-sessions.ts:27`) the new Pi session resolves to **nothing**: every `memory.save` lands with `session_id = NULL`, and an agent that omits `sessionId` gets `session_not_found` back from `memory.session_summary`. The ambiguity is by design and correct — the server refuses to guess — but only a client that closes the old session can remove it. Three of the five clients do (Claude Code via `SessionEnd`, Hermes via `on_session_end`); Codex cannot (its harness has no such event) and opencode deliberately does not. **Pi's omission is the only one with no reason recorded anywhere.**

Now it can be closed correctly, which was not obvious. `session_shutdown` is not a process-death signal: `SessionShutdownEvent { type: "session_shutdown"; reason: "quit" | "reload" | "new" | "resume" | "fork"; targetSessionFile?: string }` (`dist/core/extensions/types.d.ts:462-468`, `@earendil-works/pi-coding-agent@0.84.1`, doc comment "Fired before an extension runtime is torn down due to quit, reload, or session replacement"). Four of the five reasons are session replacement inside a surviving process, and **`reload` is the same session continuing**. Ending it would be unrecoverable: `openspec/specs/sessions/spec.md:66` — "No path SHALL transition a session back to `active`" — bounded by two CI invariant tests, and `AgentSessionsService.ensure` only touches `last_activity_at`. A session ended on `reload` yields `session_id = NULL` on every later save and `session_not_found` from `memory.session_summary` for the remaining life of the process. Self-resume is the same hazard by a different door: resuming the session already open emits `reason: "resume"` and returns the **same** id (`dist/core/session-manager.js:632`, `this.sessionId = header?.id ?? createSessionId()` reads the id out of the resumed file's header), so the reason alone is not a sufficient gate.

## What Changes

- **The shared core gains one session-end verb; only Pi calls it.** `plugin-session-protocol`'s single-implementation requirement puts the session HTTP client in exactly one JS/TS module, so a `/end` POST written in a client file would be a second copy of the session client by construction. **Rejected: putting it in `.pi-plugin/index.ts`** for the reason above. **Rejected: also calling it from opencode** — see below.
- **Pi ends its session on `quit`, `new`, `resume` and `fork`, and never on `reload`.** The gate is membership in an explicit reason set, not an exclusion of `reload`: a harness that adds a sixth reason must fail toward _not_ ending, because not-ending is recoverable by `abandonStale` and ending wrongly is not recoverable at all. **Rejected: ending unconditionally** (the pre-verification reading of the event name) — it ends a live session on every `/reload`.
- **A self-resume guard suppresses the end when the shutdown is a replacement by the same session file.** `event.targetSessionFile` is "Destination session file when shutting down due to session replacement"; when it names the file the session manager currently holds (`ReadonlySessionManager` is a `Pick<SessionManager, … | "getSessionFile" | …>`, `dist/core/session-manager.d.ts:140`), the session survives with its id intact and ending it is the `reload` failure again. The guard compares only when `targetSessionFile` is a non-empty string, so a `quit` whose `getSessionFile()` returns `undefined` still ends — a bare `!==` comparison would silently suppress the end whenever both sides are `undefined`.
- **One atomic `POST /end {summary, title, final:false}` replaces the shutdown `/summary` POST on the ending reasons.** Body comes from the same summary-body builder the per-turn flush uses (`rembric-plugin-core.mjs:208`), falling back to `{}` when the builder returns `null` on an empty transcript. **Rejected: `/summary` then `/end`.** Each core POST is bounded by `AbortSignal.timeout(POST_TIMEOUT_MS)` with `POST_TIMEOUT_MS = 3000` (`:8`), so two sequential POSTs put ~6 s of exit latency in front of a quitting user and break the existing teardown-budget assertion at `apps/plugin/.pi-plugin/plugin.test.ts:719-723` (`elapsed < POST_TIMEOUT_MS * 2`). One POST also removes the ordering question entirely and matches `apps/plugin/scripts/session-end.sh:52-64`, the only shutdown path in this repo with production mileage — it exercises three body shapes of this one endpoint.
- **On `reload` and self-resume the handler keeps today's behaviour exactly**: the awaited `/summary` flush, no `/end`. The summary must still be flushed there, because the extension runtime is torn down and the in-memory transcript accumulator does not survive it.
- **opencode keeps today's behaviour, and this change says so in the lifecycle matrix rather than leaving it a gap.** Its `server.instance.disposed` flush is fire-and-forget by measurement — the host kills the subprocess before async handlers settle (`rembric-plugin-core.mjs:237` records exactly this) — so an `/end` issued there often would not land and no requirement could promise `ended`. The no-end decision was taken twice, and the durable reason is resumability (`openspec/changes/archive/2026-05-19-add-opencode-session-summary-on-dispose/design.md:92`).
- **The client-side rule "never end a session you may write to again" becomes spec text**, because the server's precedence is asymmetric and one shape is lossy: active rows are last-final-wins, terminal rows are **first**-final-wins (`apps/server/src/services/agent-sessions.ts:274-280`, comment "Deviation from the active path's last-final-wins … First curated value stands"). So `/end` followed later by a curated `memory.session_summary` silently drops the curated text. Pi's `/end` fires from the teardown handler, after which nothing writes.
- **Two dead/absent pieces of spec text are repaired while in the area.** `openspec/specs/plugin-session-protocol/spec.md:77` conditions opencode's `ended` transition on "the MCP server's terminating path", a mechanism that no longer exists — `openspec/specs/sessions/spec.md:247` makes `memory.session_end` / `POST /end` the sole transition. And the authoritative per-client lifecycle matrix (`:255-274`) has **no row for Pi and no row for opencode** while its own preamble states that divergence from the mapping is a specification violation.
- **BREAKING**: none at any wire, schema or on-disk surface. No server change, no new MCP tool, no migration.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `pi-plugin` — the requirement titled "Session close is awaited, with the interrupt exception recorded" (`:215-241`) closes nothing today; it becomes the contract for the atomic `/end`, its body source and the `{}` fallback, plus the write-after-end prohibition. Its enumeration of what the extension imports from the core gains the session-end call. Two requirements are **added**: the reason gate plus self-resume guard (with `reload` as the discriminating control), and Pi's terminal-status behaviour — asserted nowhere today — including an explicit statement of what `abandonStale` still has to cover.
- `plugin-session-protocol` — the per-client lifecycle matrix gains Pi's rows and opencode's rows (the latter describing today's behaviour; the gap is pre-existing and this is the natural moment). "Sessions under the Pi client MUST converge on a non-null summary" changes mechanism: the awaited shutdown POST is `/end` on a real close and `/summary` on a reload or self-resume, and convergence must hold across both. The general convergence requirement's stale reference to "the MCP server's terminating path" is corrected to the mechanism that exists. The single-implementation requirement's enumeration gains the session-end call, so a second copy reds the invariant test.

## Impact

**Plugin code** — `apps/plugin/bin/rembric-plugin-core.mjs` gains one awaited `endSession(sessionId)` (build body via the existing `buildSummaryBody`, fall back to `{}`, POST `/api/<slug>/sessions/<id>/end` through the existing `rembricPost`, so it inherits the `POST_TIMEOUT_MS` bound and the single stderr diagnostic) and adds it to the returned object at `:271-289`. `apps/plugin/bin/rembric-plugin-core.d.mts` declares it on `SessionProtocol` (`:33-51`). `apps/plugin/.pi-plugin/index.ts:328-335` reads the payload: the locally-declared `ExtensionContext.sessionManager` (`:36`, currently `{ getSessionId: () => string }`) widens with `getSessionFile?: () => string | undefined`, and a local `SessionShutdownEvent` type joins the other locally-declared event types (`:42`, `:49`) — typed with `reason?: string` rather than the harness's five-member union, so the unknown-reason branch stays reachable instead of being typed out of existence.

**Tests** — `apps/plugin/.pi-plugin/plugin.test.ts`: the harness fires `session_shutdown` with `{}` today, so it must accept a payload and stub `getSessionFile`; new per-reason arms against the real server and DB the suite already stands up; the ambiguity arm with its must-fail control; the teardown-budget measurement re-run with `reason: 'quit'` (`:719-723`).

**Docs** — `apps/plugin/.pi-plugin/README.md` (the "Session close" section, `:87-95`) and `docs/agents.md:409-413` both describe the shutdown handler as writing the final summary and say nothing about ending; both gain the reason table. Neither's Ctrl-C text is touched here (see below).

**Empty-session purge exposure narrows for Pi, and only for genuinely empty rows.** `purgeEmpty` runs inside the consolidation sweep, and its predicate is `status ∈ {ended, abandoned}` ∧ no summary ∧ no `title_final` ∧ no referencing memory/prompt/confirmation ∧ `ended_at < now − SESSION_PURGE_GRACE_MS` (1 h, `apps/server/src/services/agent-sessions.ts:15`). Today a content-free Pi row waits for `abandonStale` (`SESSION_ABANDON_AFTER_MS`, default 24 h, `apps/server/src/config.ts:126`) before its `ended_at` exists, so purge eligibility arrives at ~25 h; ending at quit moves it to ~1 h. A row with any content is unaffected.

**Accepted behaviour regression, stated rather than buried.** Ending at `quit` means a later resume of that session id lands on a terminal row: auto-attach is off, and a `memory.save` without an explicit `sessionId` gets `session_id = NULL`. Today, resuming within 24 h works because the row is still `active`. This is not a new class of problem — Claude Code already ends on `SessionEnd` and already lives with exactly this, through the same server code path — but for Pi it is a regression inside that window, and it is accepted because the two failures are not comparable: attribution loss after `/new` is silent, immediate and unfixable by the user, whereas the resume case is visible in the dashboard and recoverable by passing the id explicitly, which terminal rows accept (`openspec/specs/sessions/spec.md`, "Terminal session rows MUST accept late summary and title writes"). **Rejected: letting `ensure` reactivate an ended row** — it crosses the documented terminal FSM contract that two invariant tests bound, and would need its own change.

**`abandonStale` remains the safety net and its coverage is not overclaimed.** SIGKILL runs no handler. A single-press Ctrl-C reaches none either (as the shipped spec records). Print mode registers only `SIGTERM` plus `SIGHUP`. Any of those leaves the row `active` until the sweep flips it to `abandoned`, exactly as today.

**Load-bearing invariants** — none violated. Append-only memory, `topic_key` convergence, fresh-context judgment and derived-never-stored review state are untouched; the change adds no MCP tool and no SQL; the extension keeps speaking `/mcp/<slug>`, so `resolveEffectiveScope` fixes its project as before. `sessions.status` moves only along the existing `active → ended` edge through the existing `POST /end`.

**Existing installations** — nothing to migrate. No schema change, no migration file, no first-boot work, no derived-data invalidation (`memory_fts`, `memory_vec` and the three entity tables are untouched). Rollback is symmetric: reverting to the previous `@rembric/pi` restores today's behaviour, and rows already `ended` stay `ended` — which is the FSM working as specified, not damage. The server image is unaffected in both directions.

**Deliberately out of scope, recorded so they are not lost:**

- **The Ctrl-C claim in the shipped specs is false and needs its own change.** `openspec/specs/pi-plugin/spec.md:221-223` and `apps/plugin/.pi-plugin/README.md:89-95` state Ctrl-C is not a session-close path. `dist/modes/interactive/interactive-mode.js:3046-3056` shows `handleCtrlC()` calling `void this.shutdown()` on a second press within 500 ms, and `shutdown()` awaits `runtimeHost.dispose()` before `process.exit(0)`; Pi's own comment at `:3089` reads "Interactive quit (Ctrl+D, Ctrl+C, /quit, extension shutdown())". The original pty probe most likely sent one press, or two spaced beyond 500 ms. The evidence to settle it is **one pty run away** with the `pi` CLI already installed in this environment — not an open question, just a change this one must not absorb, because it rewrites a published measurement and its scenarios.
- **Two latent server defects around `/end`.** `session_deleted` is absent from `statusForCode` (`apps/server/src/server/api-router.ts:335-364`), so it would surface as 500 through the TOCTOU window between `rejectIfDeleted` and the service call; and the soft-delete guard for `/end` exists only in the HTTP handler, so `svc.end()` on an active soft-deleted row succeeds. Neither is reachable from this change's path, and both are server-side.
