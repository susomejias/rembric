## Why

**Every Rembric tool call in Pi prints its whole JSON payload into the transcript, and a failed one prints it wearing the success colour.**

The Pi adapter registers each discovered MCP tool with an `execute` and nothing else (`apps/plugin/.pi-plugin/index.ts:284-301`). Pi's `ToolExecutionComponent` takes the renderer path whenever a tool definition exists — `hasRendererDefinition()` returns `this.builtInToolDefinition !== undefined || this.toolDefinition !== undefined` (`dist/modes/interactive/components/tool-execution.js:75-77`, `@earendil-works/pi-coding-agent@0.84.1`) — so with no `renderCall` and no `renderResult` the operator gets `createCallFallback()` (`:106-108`, the **registered** name, i.e. the underscored `memory_context`) followed by `createResultFallback()` (`:109-115`), which is `new Text(theme.fg("toolOutput", output), 0, 0)` over the entire text. The server pretty-prints: `apps/server/src/mcp/result.ts:7` is `const text = JSON.stringify(payload, null, 2);` and `apps/server/src/mcp/errors.ts:15` the same. So a `memory.context` result is not a long line, it is hundreds of lines, and Pi's global `app.tools.expand` toggle (default `ctrl+o`, description "Toggle tool output" — `dist/core/keybindings.js:27`) has nothing to collapse because the extension never opted into the collapsed half of that contract.

**The error half is worse, and it is a defect this change discovered rather than a presentation preference.** `apps/plugin/.pi-plugin/index.ts:298` returns `...(isError ? { isError: true as const } : {})` — that property is dead. Three measurements against 0.84.1:

- `AgentToolResult` (`@earendil-works/pi-agent-core/dist/types.d.ts:316-330`) declares `content`, `details`, `usage?`, `addedToolNames?`, `terminate?` — **no `isError` member**.
- `executePreparedToolCall` returns `{ result, isError: false }` **hardcoded** on the success path (`pi-agent-core/dist/agent-loop.js:470`); the only `isError: true` in that function is its `catch` (`:477`).
- The TUI spreads the host's flag last: `component.updateResult({ ...event.result, isError: event.isError })` (`dist/modes/interactive/interactive-mode.js:2641`), so a flag carried inside the returned object is overwritten even if it survived that far.

Consequently an MCP application error — the `mcpError()` shape at `apps/server/src/mcp/errors.ts:9-19`, `{ isError: true, content: [{ type: 'text', text: JSON.stringify({ ok: false, code, message }, null, 2) }] }` — renders on the **success** background, and the `toolResult` message handed to the model carries `isError: false` (`agent-loop.js:534-547`, `isError: finalized.isError`). The discriminating control that this is specifically the application-error path: a transport or JSON-RPC failure already throws out of `send()` (`index.ts:126-128`, `:132-135`), reaches Pi's `catch`, and **is** flagged correctly today. So issue #333's acceptance criterion "Errors show a compact failure state and can reveal the original diagnostic text" is not merely unimplemented — it is unsatisfiable without touching `execute`, and the issue's own "plugin-only presentation change" scope statement is superseded here with the user's explicit agreement.

## What Changes

- **`execute` throws instead of returning a flag Pi ignores.** When the MCP result carries `isError: true`, the adapter throws `new Error(text)`. Pi's `catch` calls `createErrorToolResult(message)` (`agent-loop.js:519-524`), which returns `{ content: [{ type: "text", text: message }], details: {} }` — the same single text block the adapter returns today (`index.ts:295-299`), so the model's **text** is unchanged and is now correctly flagged. This is the harness's documented rule, verbatim at `docs/extensions.md:1984`: "**Signaling errors:** To mark a tool execution as failed (sets `isError: true` on the result and reports it to the LLM), throw an error from `execute`. Returning a value never sets the error flag regardless of what properties you include in the return object." **Rejected: stay presentational** by smuggling the flag through `details` — it leaves both the wrong background and the wrong model-facing flag, i.e. it satisfies the issue's error criterion in appearance only. **Rejected: a `tool_result` extension handler** returning `{ isError: true }`, which does reach the flag (`agent-session.js:244-270` → `agent-loop.js:505`, `isError = afterResult.isError ?? isError`) — real, but two moving parts (a marker in `details` plus a global handler filtering by tool name) for the outcome one `throw` gives, and it writes an extension-owned marker into session history.
- **A generic `renderResult` collapses every discovered tool to one line and expands to the complete original text.** No response schema is read and no tool name is branched on: the renderer joins `result.content`'s text blocks, which is the same string the fallback renders.
- **Collapsing applies to every tool, always — no size threshold.** A one-line result gains nothing from being collapsed, and because `app.tools.expand` is a **global** toggle (`interactive-mode.js:262` holds one `toolOutputExpanded` flag; `setToolsExpanded` at `:3308-3324` pushes it to every child of the chat container) recovering that one line expands the whole transcript. Accepted for predictability: a threshold makes the operator's mental model "sometimes collapsed, depending on a number they cannot see". The collapsed line still carries a line **count** — that is a signal, not a gate, and it is what tells the operator whether pressing the key is worth it.
- **The error branch reads `context.isError`, never `result.isError`.** Pi narrows the first renderer argument to `{ content: this.result.content, details: this.result.details }` (`tool-execution.js:248`); the flag arrives only on the fourth argument, built at `:103` as `this.result?.isError ?? false`. A renderer reading `result.isError` would be permanently false — the same bug as the dead property above, repeated one layer up.
- **A minimal `renderCall` renders the canonical dotted name.** Without it the call line is `createCallFallback()`'s `theme.fg("toolTitle", theme.bold(this.toolName))` = the underscored registration spelling `memory_context`, a name that exists only to satisfy a provider's `^[a-zA-Z0-9_-]+$` pattern (`pi-plugin` spec, "Tools are registered under provider-safe names"). With it the operator reads `memory.context` on the call line. The call renderer shows the name and nothing else: rendering arguments would require knowing which argument matters per tool, which is the schema coupling the issue forbids.
- **The host packages are imported statically, as `peerDependencies` with range `"*"`.** `keyHint` from `@earendil-works/pi-coding-agent` and `Text` from `@earendil-works/pi-tui`. This is the shape the shipped spec already mandates (`openspec/specs/pi-plugin/spec.md:121`: "The harness's own packages SHALL be declared as `peerDependencies` with the range `"*"` and SHALL NOT be bundled") and that Pi prescribes (`docs/packages.md:171`: "If you import any of these, list them in `peerDependencies` with a `"*"` range and do not bundle them: `@earendil-works/pi-ai`, `@earendil-works/pi-agent-core`, `@earendil-works/pi-coding-agent`, `@earendil-works/pi-tui`, `typebox`"). Reusing `Text` — the same component the current fallback uses — makes the expanded view identical to today's by construction, word wrap included, rather than merely similar. `keyHint` gives the operator's real binding, which the issue explicitly asks for over a hard-coded `Ctrl+O`. **Rejected: a lazily-resolved dynamic import with a local `ctrl+o` fallback** — it dodges a convention the spec already sets, adds machinery, and paints a generic hint that later mutates into the real one; a hint that changes under the operator is worse than a stable correct one.
- **The rendering logic is a pure named export, so the tests do not depend on the stub.** A static host import is measurably unresolvable from this repo, so `apps/server/vitest.config.ts` gains a `resolve.alias` stub for both specifiers — and a stub can hollow out coverage. The shape that prevents it: a named export from `index.ts` taking `(text, expanded, isError, canonicalName, keyHintText)` and returning `string[]`, with no host import on its path, plus a thin `renderResult` wrapper that calls `keyHint(...)` and wraps the lines in `Text`. Collapsed, expanded and error rendering are then driven directly against a fake theme with nothing stubbed.
- **BREAKING**: none at any wire, schema or on-disk surface. No server change, no MCP protocol change, no new tool, no migration, no SQL. The one model-visible movement is stated rather than buried: for an MCP application error the `toolResult` message's `isError` goes `false` → `true` with unchanged text, which for at least one provider becomes a wire-level field (`@earendil-works/pi-ai/dist/api/anthropic-messages.js:829`, `is_error: msg.isError`). That is the point of the fix, not a side effect.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `pi-plugin` — two requirements are **added**: the compact-render contract (collapsed by default for every discovered tool, the global expand toggle, expansion byte-identical to today's text, schema-blind and tool-name-free, degradation when a renderer throws) and the error-signalling contract (`throw` from `execute`, `context.isError` as the only readable flag, what the model receives and what changes). One is **modified**: "MCP transport is Streamable HTTP with a Bearer token and no runtime dependency" (`:117`), which gains the permission and the measured conditions for importing host packages statically, plus the consequence that the repo's own test config must alias them and must not thereby become the only thing the tests exercise.

## Impact

**Plugin code, all inside the one file the spec permits.** `openspec/specs/pi-plugin/spec.md:15` — the directory "SHALL contain exactly four files at the top level: `package.json`, `index.ts`, `README.md`, and `plugin.test.ts`. There SHALL be no nested directories." — so the renderers and the pure helper live in `index.ts` next to the existing local type declarations, not in a new module. The local `ToolDefinition` type gains `renderCall?` and `renderResult?`; new local declarations mirror `ToolRenderResultOptions` (`dist/core/extensions/types.d.ts:307-312`) and the members of `ToolRenderContext` the renderer reads (`:314-339`, `isError` among them). `Component` is structural — `render(width: number): string[]` plus `invalidate(): void` (`@earendil-works/pi-tui/dist/components/../tui.d.ts:10-30`) — and `Text` implements it (`pi-tui/dist/components/text.d.ts`, constructor `(text?, paddingX?, paddingY?, customBgFn?)`), so returning `new Text(lines.join('\n'), 0, 0)` is exactly what the current fallback returns.

**`package.json`** gains `@earendil-works/pi-tui` under `peerDependencies` with range `"*"`, alongside the existing `@earendil-works/pi-coding-agent` entry. No `dependencies` key, no bundling — the prohibition at `spec.md:121` is honoured, not relaxed.

**Build guard is unaffected.** `scripts/pi-package.mjs::sharedModules()` scans `index.ts` with `/from\s+'(\.[^']*)'/g` and fails on any **relative** specifier not matching `^\.{1,2}\/bin\/([\w.-]+\.mjs)$` (`:23-48`). Bare `@earendil-works/*` specifiers do not match the scan regex at all, so they pass through untouched and nothing new is materialised into the tarball.

**Tests** — `apps/plugin/.pi-plugin/plugin.test.ts` (already collected: `apps/server/vitest.config.ts:14` includes `'../plugin/.*-plugin/*.test.ts'`). It imports `rembric from './index.js'` at module level (`plugin.test.ts:28`), so an unresolvable bare import fails the whole file at load, not one arm.

**`apps/server/vitest.config.ts`** gains its first `resolve.alias` block, stubbing the two host specifiers. Editing the server's shared test config for a Pi-client concern is a real smell and is accepted deliberately: the alternative is the dynamic-import machinery rejected above, and the pure-function split means the stub is never what the render assertions run against.

**Docs** — `apps/plugin/.pi-plugin/README.md` gains a short "Tool output" note (collapsed by default, `app.tools.expand` toggles, the toggle is global). `docs/agents.md`'s Pi section likewise.

**Load-bearing invariants** — none violated. Append-only memory, service-layer scope enforcement, `topic_key` convergence, fresh-context judgment, derived-never-stored review state and the SQL-confined-to-`db/` rule are untouched; no MCP tool is added and no tool's input schema, description or result payload changes. The extension keeps speaking `/mcp/<slug>`, so `resolveEffectiveScope` fixes its project exactly as before.

**Existing installations** — nothing to migrate. No schema change, no migration file, no first-boot work, no derived-data invalidation (`memory_fts`, `memory_vec` and the three entity tables are untouched; this change never reaches the database). The server image is unaffected in both directions, and a plugin release never rebuilds it (`publish-docker` gates on `server_release_created`). First run after upgrade: the next Pi session renders compactly; the extension runtime is created per session, so nothing has to be reloaded. Rollback is symmetric — reverting `@rembric/pi` restores today's rendering immediately and nothing persisted differs. The only asymmetry worth naming is the model-facing error flag: transcripts written under the new version record `isError: true` on MCP application errors, and a rollback simply stops writing it; no stored transcript becomes unreadable.

**Release track** — plugin tree, so this rides the unified `plugin` component. One shared version across all five clients, bumped by release-please through `extra-files`; no version carrier is edited by hand.

**Deliberately out of scope, recorded so it is not lost:**

- **Per-tool semantic summaries** (`memory.search · 7 results`, `memory.save · saved <title>`). The issue names this as a separate follow-up and it is: every such summary reads a response DTO, which is the coupling the discovery-based design exists to avoid.
- **A typecheck gate over `apps/plugin/.pi-plugin/index.ts`.** Nothing typechecks it today — `apps/server/tsconfig.json:26` is `"include": ["src/**/*"]`, root `typecheck` is `pnpm -r run typecheck`, and ESLint lints the file with `parserOptions: { projectService: false }` (`eslint.config.js:88-93`). Adding one is now _harder_, not easier, because the static host imports would need `@earendil-works/*` type declarations present in CI, i.e. either a devDependency on a package carrying five provider SDKs (a cost this client's spec already refuses) or a `paths` map onto a global install CI does not have. So issue #333's criterion "local type definitions cover the renderer API without weakening type safety" is answered by review plus the pure-function behavioural tests, and the absence of a compiler gate is stated rather than implied covered.
- **Print mode.** `renderResult` is an interactive-TUI concern; print mode builds no `ToolExecutionComponent`.
