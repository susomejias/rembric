# Compliance note — 2026-08-04

Plain working note, **not** an OpenSpec artifact, and not a defect fix: the fix
landed in `4f58bce`. This records a window in which a verification step that 16
archived change folders tick did not verify anything, so a future reader does not
read those ticks as stronger evidence than they are.

Nothing here retracts a change. No published spec was wrong, no shipped
behaviour was wrong, and CI was never affected.

---

## What was vacuous

`package.json` defined the local pre-flight as:

```
"check:spec-provenance": "node scripts/check-spec-provenance.mjs --base main --head HEAD"
```

Run from the `main` branch — this repo's normal state, it lands directly on
`main` — `main...HEAD` is empty **by construction**, because `main` and `HEAD`
resolve to the same commit. The script printed `spec-provenance: ok
(main...HEAD)` and exited 0 having examined no diff at all.

Measured on `main`:

```
git rev-list main...HEAD    -> 0
git rev-list HEAD~1...HEAD  -> 1
```

An empty range cannot distinguish "nothing violated the gate" from "nothing was
examined", and the script reported the first while doing the second.

## What was never affected

The CI job derives the range from the event payload
(`.github/workflows/ci.yml`: `github.event.pull_request.base.sha` /
`github.event.before` → `github.sha`), so on a push to `main` it examined the
real pushed range throughout. The gate protected the repository for the whole
window. What was empty was the local run a contributor makes _before_ pushing —
the step whose purpose is catching the problem earlier than CI.

## Where it came from

`openspec/changes/archive/2026-07-28-enforce-spec-archive-provenance/tasks.md:9`
is the task that chose the default, per that change's D6:

> Add a root `check:spec-provenance` script to `package.json` defaulting to
> `main...HEAD` so a contributor can run the gate locally before pushing (D6)

D6 analysed the contributor-on-a-branch case, where `main...HEAD` is exactly
right, and did not consider the on-`main` case. The same change's `design.md:39`
had already rejected a `pre-push` hook partly because "computing the pushed range
locally is fiddly" — the difficulty this defect is an instance of.

Worth recording for its own sake: that change's task 1.5 note documents catching
a **different** never-gates defect during implementation — an
`--is-ancestor` check that would have skipped on essentially every real PR, "a
gate that never gates". One instance of the class was caught before shipping and
another shipped in the same commit. The lesson is the one `CLAUDE.md` states
under _Claims need evidence_: a gate reporting success is evidence only once you
have shown it can report failure.

## Residual, not closed by `4f58bce`

- The new default depends on `origin/main` resolving. Where it does not (a remote
  under another name, a `.git`-less copy), the script warns and exits **0** —
  the same vacuous-pass class, relocated. That exit-0 policy is correct for CI
  (`development-environment/spec.md:449` mandates it for unresolvable ranges) and
  wrong for a human at a terminal.
- `git diff A...B` never sees the working tree, so uncommitted spec edits remain
  invisible at any range. Several of the 16 ticks were pre-archive runs, i.e.
  before committing.
- `check:delta-freshness` has the same shape (`ok (0 active change(s))` is a pass
  over zero inputs) and **no** published spec coverage at all.

These three are why a follow-up change is worth opening rather than treating
`4f58bce` as the end of it.
