## Why

The summary reminder fires on a **turn counter**, and a turn counter correlates with nothing. Turn 20 does not say whether anything happened.

Measured on this tree, driving the real hook scripts through real per-session counter files:

- **A 20-turn conversation in which the model used no tool at all still receives five reminders, 1880 bytes.** `prompt-nudge.sh` never opens the transcript — it reads `rembric_turn_count` and emits on turns 1, 5, 10, 15, 20 regardless of what the session did.
- **The one work-aware surface reaches one client of five.** `stop-nudge.sh` does consult the transcript, and at turn 10 on Claude Code it emits 1044 bytes of rubric plus extracted facts. Given a Codex transcript carrying a `function_call`, at the same turn 10, it emits `{}` — because `_rembric_facts_raw_codex_cli` **does not exist** (`apps/plugin/scripts/_transcript.sh` defines `_rembric_facts_raw_claude_code` and no Codex counterpart), so `rembric_session_facts_raw` returns empty and the script takes its `_emit_nothing` branch. Codex CLI has never received the end-of-turn reminder.
- **Three clients receive the opposite voice.** The periodic firing on opencode, Pi and Hermes comes from the shared core's `SUMMARY_NUDGE` (`apps/plugin/bin/rembric-plugin-core.mjs:25`), which asks _"did real work happen **this turn**?"_ — a delta question — while Claude Code's every-10 firing asks for the session's CURRENT COMPLETE state (`stop-nudge.sh:75`). `prompt-nudge.sh:46-48` records the split verbatim: _"Turn 1 only: that firing is protocol … `stop-nudge.sh` owns the every-N firing."_ The core has no counterpart to `stop-nudge.sh`, so the three in-process clients only ever get the delta voice.

The cadence constant is duplicated across **five** sites — `rembric-plugin-core.mjs:20,23`, `prompt-nudge.sh:10`, `stop-nudge.sh:10`, `.hermes-plugin/__init__.py:110-111` — over three independent counter mechanisms: an in-process `Map` (`rembric-plugin-core.mjs:101`, cleared at `:336`), TMPDIR marker directories (`_api.sh:148`), and Hermes's host-supplied `turn_number`. The in-process one is the loudest failure: a `pi -r` starts a fresh process, `userTurnCounts` is empty, turn 1 fires again, and the model is told to open a session it has been working in for an hour.

Nothing in that machinery can answer the only question that matters — _has anything happened since the stored summary was last written?_ — because no client knows when it was written, and no row records it.

## What Changes

- **The gate moves to the server, and that is the only way five clients can behave identically.** Three per-session timestamps decide: `last_work_at`, `last_summary_at` (a NEW column — nothing today records when a summary was written) and `last_nudge_at`. The notice fires when `last_work_at` is set AND (`last_summary_at` is null OR `last_work_at > last_summary_at`) AND `now - COALESCE(last_nudge_at, started_at) >= NUDGE_FLOOR_MS`. No counters, no flags to reset, and a hard ceiling of one notice per floor: if the notice was emitted and the model did not write, it does not repeat until the next floor. Chosen over per-client cadence tuning, which is what produced five constants and three counters, and over a server-side heuristic on Rembric's own MCP traffic, which counts calls to Rembric's own tools and therefore goes quiet exactly when a session has stopped using them — the case the notice exists for.
- **The client reports the turn that just ended; the server decides.** `POST /api/<slug>/sessions/:id/turn` with `{usedTools: boolean, title?: string}`, at the END of the turn, so no latency lands on the path where the user is typing. The response carries the notice's lines; the client CACHES them and prints them at the start of the next turn. The client keeps no counter and no cadence — it observes one turn, reports it, and forgets it.
- **The boolean is required because the server is blind to work.** The server sees pings and Rembric's own traffic. A turn that edited eight files without calling a Rembric tool is indistinguishable, from the server, from a turn of conversation. Only the client sits where the host's tool events are.
- **Five-client symmetry is a requirement of this change, not an aspiration, and all five are covered.** Every client reports, and every client prints. Four tool-observation sources are verified: Claude Code (`"type":"tool_use"`, the marker `_rembric_facts_raw_claude_code` already selects on) and Codex CLI (`"function_call"` / `mcp_tool_call`, one more `select` over a transcript the script already opens) via a byte-offset delta scan; opencode via non-`text` message parts, which the installed SDK enumerates and `plugin.ts:207` currently discards; and **Pi via a real run** against pi-coding-agent 0.84.1. The fifth, Hermes, uses the `messages` kwarg of `sync_turn`, whose whole chain is traced in the upstream tree at commit `7095e23`: the tool executor appends results into the agent loop's own working list at seven sites, `make_tool_result_message` sets `"role": "tool"` literally, the turn finaliser carries that list as a first-class parameter, and the dispatcher's signature inspection admits our `**kwargs`. `messages` is not assembled for memory's benefit — it is the list the loop already uses — so a tool-using turn putting a `role: "tool"` message in it is a consequence of the path rather than a claim in a docstring. What is left is corroboration in execution, which gates closing the change rather than starting it, and one clause (the assistant `tool_calls` field) that has no trace behind it and is defensive rather than load-bearing. Hermes also carries the one published deviation from reporting every turn: its host skips the memory fan-out on an interrupted turn, so those turns produce no report and no `last_activity_at` stamp.
- **Pi's source carries a trap that is contract text, not an implementation note.** The LAST `message_end` of a turn — the one this extension already handles — is the assistant message with `stopReason: "stop"` and text-only content; the `toolCall` parts were in an earlier `message_end` with `stopReason: "toolUse"`, and `turn_end.toolResults` is empty on that final turn. Reading any single event returns `false` for every turn that used tools, so the observation is a flag ACCUMULATED across the turn — reset in `before_agent_start`, set in `message_end`, read in `agent_settled` — and the scenario that pins it carries the control asserting the single-event reading fails. Hermes carries its own correction: a tool CALL lives in an `assistant` message's `tool_calls` field while the RESULT is a separate `role: "tool"` message, so testing roles alone misses a call that produced no result.
- **A client that cannot observe tool invocation SHALL send `usedTools: true` and its inability SHALL be named in the spec** — fail-open costs at most one notice per floor, fail-closed silently disables the feature on that client, and a silently disabled client is exactly what the symmetry rule exists to prevent. On Hermes below 2026.5.29 that branch is not caution but arithmetic: the provider synthesises `messages` from two strings, so neither condition can ever be satisfied and a `false` would assert "no tool ran" from evidence that could never have shown one.
- **One stretch-close notice, not a save nudge and a summary nudge.** A separate `save` floor would buy frequency at the same imprecision — nobody, server or client, can say what is "memorable" — and prompt saving does not depend on the nudge, because `initialize.instructions` already obliges the model to save as soon as there is a fix, decision or discovery. Where the model has gone a long stretch without saving anything, the notice degrades to naming the elapsed time rather than pretending to know what was worth keeping.
- **The notice carries an INVENTORY of what is stored: current per-section sizes and the live title.** The wording is contractual, not stylistic: a human reader of a draft read "Summary for this session (2 412 ch)" as a LIMIT, and a model would do the same and trim to fit. The notice therefore says "current sizes, not targets" and closes with "2 412 used of 10 000 available". It also gives explicit permission not to call when there is nothing to add.
- **A server-composed model-facing string cannot drift across clients, and that retires a test.** Byte-identity of the reminder across five clients stops being a cross-language fixture assertion (`apps/plugin/test/nudge-fixtures.json`'s `save`/`saveCore`/`summary`/`summaryCore`) and becomes a property: there is one implementation, in TypeScript, and every client prints what it is handed. The fixture contract keeps only the strings that remain client-composed.
- **Removed:** `apps/plugin/scripts/stop-sync.sh` (the per-turn raw transcript POST — the ping now carries the activity signal and the provisional title), `apps/plugin/scripts/stop-nudge.sh` (replaced by `stop-report.sh`, which pings and prints nothing), the five cadence constants and three counters, the `endOfTurnRubric` fixture, and the extracted facts from the reminder. The facts leave the NUDGE and stay as the FALLBACK: they existed so a model could write a whole 10-20-turn summary from memory, and with the partial writes the sibling change licenses the model describes only the recent stretch, which is still in its window — but `sessions`'s "grounded, checkable facts" requirement is about the summary written when the agent never cooperated, which is a different use of the same function. Their call site moves from the per-turn Stop hook (where `stop-nudge.sh:59-60` records "~0.5s of jq on this synchronous path", and where a measured 790 ms was reached on an 8.36 MB transcript) to `session-end.sh`, which runs once.
- **NOT removed, and the reason is a published measurement:** the shared core's transcript accumulator and its terminal flushes. `plugin-session-protocol` guarantees convergence for opencode via `server.instance.disposed` and for Pi via `session_shutdown`, both fed by that accumulator, both grounded in measurements against real hosts. Deleting it would leave a non-cooperating opencode or Pi session with `summary IS NULL`. What this change removes is the PER-TURN raw sync on the shell clients; the terminal flushes, `flushSessionSummary`, `flushAllFireAndForget` and `scheduleIdleFlush` are untouched. Retiring the accumulator needs its own change that names each host's replacement transcript source.
- **The session opening stays in the client**, wired identically in all five and gated on the `created` flag the ensure already returns (`rembric-plugin-core.mjs:149-154`). It is the only local rule, and it exists for the ONE-TURN session, which under a notice that is always one turn behind would receive nothing at all. It asks for a title and `## Goal` with the other five headings left out, and its wording is decisive: **"before you finish this turn"**, not "now" — so the model does the user's work first and writes as it closes, and turn 1 stops being premature.
- **Two more things stay local, and the split is stated rather than implied.** The recall nudge is a regex over the prompt, and the server does not have the prompt when it decides — the ping that produced the notice happened at the end of the PREVIOUS turn. The resumed-read line is gated on the ensure's `created` flag and is unchanged. Local = recall + opening + resumed-read; server = stretch close. This is complexity moved, not complexity removed.
- **Two accepted defects, recorded because the owner accepted them.** (1) With the server down there are no nudges at all; today they are 100% local — verified, neither `prompt-nudge.sh` nor `stop-nudge.sh` contains `rembric_post` or `curl`. Acceptable because with the server down `memory.save` and `memory.session_summary` would fail anyway, so the nudge would be an instruction to do something impossible. (2) For saving, the server cannot know what is memorable, so it degrades to elapsed time.
- **Two published caps move, and both movements are derived from measurement rather than argued.** The reminder relocates from the `Stop` channel — which `claude-code-plugin` deliberately left uncapped, because `plugin-session-protocol` required that surface to carry "the long form precisely because it has no length budget" — onto `UserPromptSubmit`, which is capped. So the numbers on the receiving channel have to absorb what the sending channel never counted. Measured on this tree: the drafted notice plus its inventory is 468 bytes; a notice turn (sessionId line + notice) totals 674; turn 1 with a recall keyword totals 759 against a published ≤800 sub-budget and 797 today, so that one does NOT move. The two that do: the per-firing-turn ceiling rises 960 → 1088 bytes, because the worst reachable turn is first-prompt (125) + recall (90) + sessionId (204) + notice + 4 newlines and that arithmetic is what fixes the notice's own bound at **640 bytes**; and the ten-turn amortised budget rises 180 → 240 bytes/turn, because it previously governed one channel while the reminder sat on the other. Across BOTH channels the ten-turn cost falls, from a measured 227 bytes/turn today to 151 at one elapsed floor and 236 at two — and to the turn-1 lines alone on a conversation where nothing happened, against today's measured 1880 bytes over twenty turns. The per-line table also changes shape: the `save` (132) and `summary` (400) rows go with their fixtures, a `sessionOpening` row arrives, and the notice gets the first cap in this system asserted against an emitted string rather than a fixture, because it is the first model-facing string that has no fixture to pin.

## Capabilities

### New Capabilities

- `session-nudges` — the server-side gate: the three timestamps and their update rules, the firing condition and the one-per-floor ceiling, the ping contract and its `usedTools` semantics, the composed notice (directive + inventory + the "current sizes, not targets" wording + the permission not to call), the notice's byte cap and elision rule, and the normative split between what the server decides and what stays local.

### Modified Capabilities

- `http-api` — a new `POST /api/<slug>/sessions/:id/turn` endpoint: auth, scope, body schema, response shape, and its `last_activity_at` obligation (it replaces the per-turn `/summary` POST as the shell clients' activity signal).
- `sessions` — `last_work_at`, `last_summary_at` and `last_nudge_at` columns and which write sets each; `last_summary_at` written at the same single precedence site that writes `summary`; the grounded-facts fallback requirement gains its call site now that the per-turn one is gone.
- `plugin-session-protocol` — the per-turn nudge requirement stops governing cadence and text and becomes the client's report-ping-print contract; the end-of-turn reminder requirement is replaced (its transcript-derived facts, its shared turn counter and its "SHALL NOT consult server state" clause all go, and the clause's own escape hatch is what licenses it); the lifecycle table gains the `/turn` row and loses the per-turn `/summary` rows for the shell clients; the sessionId line fires with any write-directing line rather than with "the save or summary nudge"; the shared-core requirement loses the nudge constants and gains the pending-lines cache; the post-compaction rationale at line 720 is corrected for the merge contract.
- `claude-code-plugin` — the hook catalog goes from nine handler entries to eight (`Stop` keeps one, synchronous); the token-budget table's `Stop` rows collapse; the per-line cap table swaps `save`/`summary` for `sessionOpening` and gains the server-composed-notice cap; every firing-turn figure is re-measured.
- `codex-distribution` — the same hook-catalog and nudge-emission changes on the Codex manifest, plus the removal of the Codex `Stop` raw-sync entry.
- `opencode-plugin` — the `chat.message` nudge requirement becomes print-cached-lines; a `session.idle` ping obligation; a tool-part observation obligation; and the compaction handler's rationale at lines 307 and 309 corrected for the merge contract.
- `hermes-agent-plugin` — the per-turn reminder requirement becomes ping-at-`sync_turn`/print-at-`prefetch`; `_SAVE_HINT_EVERY` and `_SUMMARY_HINT_EVERY` go; the tool-observation source is named.
- `pi-plugin` — a report obligation on `agent_settled` and a print obligation on `before_agent_start`; the tool-observation source named together with the reason Pi's own MCP `execute` callback is NOT it; the shared-core import list gains the report call and the line cache.

Not modified, and deliberately: `mcp-api`. The `memory.session_summary` description and the `initialize.instructions` block already carry the merge semantics after `refine-session-summary-writes`; this change reuses that text and adds no obligation to either surface. `apps/plugin/commands/summary.md` still says "This REPLACES the stored summary" and is corrected here as a task rather than a spec delta — no published requirement obliges that sentence, only the `10000` substring and the canonical section list, both of which it keeps.

## Impact

**Server.** `apps/server/src/db/schema/agent-sessions.ts` (three columns) and one migration under `apps/server/src/db/migrations/`; `apps/server/src/db/repositories/agent-sessions-repository.ts` (the ping update, the inventory read); `apps/server/src/services/agent-sessions.ts` (`last_summary_at` at the precedence site, the gate, the floor constant); a new pure module for the notice composition and its cap/elision under `apps/server/src/services/` with a co-located test; `apps/server/src/server/api-router.ts` (the `/turn` route + zod schema); `apps/server/src/test/invariants.test.ts` (the rubric enumeration's surface list changes shape — two plugin surfaces leave it, one server surface joins it).

**Plugin.** Deleted: `apps/plugin/scripts/stop-sync.sh`, `apps/plugin/scripts/stop-nudge.sh`, `apps/plugin/test/stop-sync.test.ts`, `apps/plugin/test/stop-nudge.test.ts`. Added: `apps/plugin/scripts/stop-report.sh`. Modified: `apps/plugin/scripts/prompt-nudge.sh` (prints the cached lines; loses the counter), `apps/plugin/scripts/_api.sh` (`rembric_turn_count`/`_peek` deleted; a pending-lines cache and a transcript-offset marker added), `apps/plugin/scripts/session-end.sh` (gains the facts call), `apps/plugin/bin/rembric-plugin-core.mjs` (nudge constants and `nudgesForTurn` cadence out; `reportTurn` + pending-lines cache in), `apps/plugin/.opencode-plugin/plugin.ts`, `apps/plugin/.pi-plugin/index.ts`, `apps/plugin/.hermes-plugin/__init__.py`, `apps/plugin/hooks/hooks.json`, `apps/plugin/hooks/hooks.codex.json`, `apps/plugin/test/nudge-fixtures.json` (+ its test), `apps/plugin/test/prompt-nudge.test.ts`, `apps/plugin/test/hook-manifests.test.ts`, `apps/plugin/test/resumed-read.test.ts`. `apps/plugin/scripts/_transcript.sh` keeps every function — only its callers move.

**Schema change, migration required.** Three nullable columns added to `sessions` by a plain `ALTER TABLE … ADD COLUMN` — no table rebuild, no `CHECK`, no foreign key, so the rebuild dance and its FK hazard do not apply. **Backward-safe on a populated table:** every existing row gets `NULL`, which the gate reads as "never" and which suppresses the notice until the first ping reports work. No backfill: inferring `last_summary_at` from `session_summary_versions` would be wrong for the byte-identical re-writes that append no row, and a later change retires that table.

**Existing installations.** The first boot after upgrade runs the migration and behaves as before for every session until its client is also upgraded — an old client posts no ping, so `last_work_at` stays NULL and no notice ever fires; it keeps emitting its own local counter-driven nudges, unchanged, because nothing server-side suppresses them. A new client against an OLD server gets `404` on `/turn`, treats it as "no lines" under the existing failed-POST contract, and emits only its local lines. Both mixed pairings degrade to fewer nudges, never to a broken host.

**Rollback.** Downgrading to a pre-change image leaves the three columns in place and unread; SQLite tolerates them and the old code's `SELECT`s are column-named. The plugin rolls back independently — the two tracks release separately — so a rolled-back server with a new client is the mixed pairing above.

**Invariants.** Append-only memory: untouched — no `memory` row is written, read or deleted, and `memory_fts`, `memory_vec` and the three entity tables are not involved. Service-layer scope: the `/turn` handler resolves its project from the URL slug exactly as the other three session routes do and passes the resolved id down; no handler constructs a scope. SQL confinement: the ping update and the inventory read are repository methods; the gate and the notice composition are pure functions in `services/`.
