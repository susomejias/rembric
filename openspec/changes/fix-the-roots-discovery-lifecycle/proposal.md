# Give the per-transport roots-discovery state an owner and a lifetime

## Why

`notifications/roots/list_changed` is handled by clearing a process-global `Set` (`mcp/server.ts:534-535` calls `resetDiscoveryState()`, whose own docstring says "Test-only helper", `roots-discovery.ts:58`). The function actually written for that notification — `refreshRootsAfterChange` (`roots-discovery.ts:156-180`) — has no caller: `grep -rn refreshRootsAfterChange apps/server/src` finds the definition and nothing else. So one client's workspace change re-arms discovery for **every live transport in the process**, because the `Set` is keyed `(tokenId, mcpSessionId)` (`roots-discovery.ts:44`) and the reset takes no key at all.

That the reset is global was recorded five days ago and again this morning (`archive/2026-08-09-route-roots-discovery-over-the-tool-call-stream/tasks.md:88`, "Real defect, separate concern, needs its own evidence and its own change"). A defect confirmed by execution and then left unscheduled is indistinguishable, six weeks later, from one nobody ever found; this change closes that loop rather than adding a third recording of it.

Measured at the real MCP edge (SDK `Client` with `capabilities.roots.listChanged`, a `ListRootsRequestSchema` handler, `client.sendRootsListChanged()`, against a real `createServer` on 127.0.0.1 — four arms, control first):

| Arm            | Setup                                                                       | `roots/list` count | Observable result                                                                                     |
| -------------- | --------------------------------------------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------- |
| **CONTROL**    | one transport, answered discovery, three `memory.context` calls             | **1**              | scope correct on all three; `suggestedSlugs: []`                                                      |
| **CROSS**      | transports A and B both answered; **A** emits `list_changed`; then B calls  | B: **1 → 2**       | B's scope and `source` unchanged (`project:…-b`, `roots`); B's `suggestedSlugs` `[] → ['probe-d2-b']` |
| **EMITTER**    | A's roots change from `probe-d1-old` to `probe-d1-new`; A emits, then calls | A: **1 → 2**       | active project unchanged; `suggestedSlugs` `[] → ['probe-d1-new']`                                    |
| **GONE-QUIET** | A answers once, stops answering, emits `list_changed`, then calls twice     | A: **1 → 3**       | warm call **5 ms**; next two calls **2507 ms** and **2506 ms**; scope still correct                   |

The control passes, so the instrument is live and the other three arms count. Three separate costs fall out, and they are one concern — the lifetime and ownership of the per-transport discovery state — not three:

1. **GONE-QUIET is the expensive one, and today's archived change created it.** The reset discards a _definitive_ outcome. Under the rule that landed this morning (`projects/spec.md:91`: an attempt that produced no answer "SHALL NOT consume that slot"), a transport whose re-armed `roots/list` goes unanswered retries on **every subsequent scope-resolving tool call**, each paying the full 2500 ms budget. Measured: 5 ms → 2507 ms, a 500× per-call regression that persists for the life of the connection. Before this morning a timeout consumed the slot, so the same reset cost one stall; the archived change fixed the misscoping and, through this reset, converted the one-off stall into a permanent one.

2. **CROSS violates a published SHALL.** `projects/spec.md:136-141` — "An answered discovery is not re-issued … **WHEN** further scope-resolving tool calls arrive on the same transport **THEN** the server SHALL NOT issue another `roots/list` for that transport" — is unconditional, and B answered. B is re-asked because _A's_ client changed folders. The blast radius is one extra client round trip per live transport per notification, so it scales with how many connections the process happens to be serving, which no client can see or control. The scope damage the framing suspected is **not** there: B's project and `source` are unchanged, because `applyDerivedSlug` writes suggestions only when a project is already active (`roots-discovery.ts:196-198`). What B does get is an advisory to switch to the project it is already in (`suggestedSlugs: ['probe-d2-b']` while scoped to `probe-d2-b`).

3. **EMITTER shows the specified outcome is reached by the wrong mechanism.** `projects/spec.md:143-147` requires `list_changed` to update `suggestedSlugs` without switching, and it does. So defect 1 is **not** an unspecified gap and **not** a violated promise on the emitting transport: the requirement is met — by clearing a global sentinel and letting ordinary discovery re-run, which is what makes 1 and 2 possible. The memory recorded on 2026-08-04 under `defect/roots-list-changed-never-refreshes` claimed this "blocks writes with a stale slug"; that does not reproduce. Writes are not blocked, the resolved scope never moves, and the refreshed slug does arrive. What the memory got right is that the notification never runs the function written for it. Recorded here because a stale severity claim in memory is worse than no claim.

4. **The sentinel is never evicted.** Nothing removes an entry when a transport closes — `mcp/transport.ts:69-73` deletes its own `sessions` entry on `onclose` and leaves the sentinel. Measured, not asserted: 200 000 entries of the real key shape cost **22.9 MB**, i.e. **≈120 bytes per distinct `(token, mcp-session-id)`**, so at 200 new MCP sessions/day a year of uptime leaks ≈8.7 MB. That is small, and it is not the reason to act. The reason is that after this morning the entry means "this client gave us an answer" rather than "we tried", so it is state with a meaning and no owner — and nothing else keyed identically is evicted either (`SessionRouter.entries` and `discoveryInFlight` use the same `tokenId::mcpSessionId` key, `session-router.ts:44-46`, and have no removal path; `clearSession` only nulls `rembricSessionId`).

## What Changes

- **Wire `refreshRootsAfterChange`; do not delete it.** It is the missing half of defect 1, not debris: it is the only code path that satisfies `projects/spec.md:143-147` without violating `:136-141`, because it re-derives suggestions **without reading or writing the answered sentinel** and can never activate a project (`roots-discovery.ts:167`, `:172`, `:176`). Deleting it would leave `list_changed` implemented by a global reset, which is defects 1, 2 and 4 in one line. Deleting dead code is also a coverage change wearing the costume of cleanup — the function has never had a test, so removing it would silently retire a specified behaviour.
- **Wire it from the lazy resolver path under an in-flight tool call, never from the notification handler.** This is forced, not preferred: `projects/spec.md:87-89` requires `roots/list` to be issued on a stream registered at the moment of the send, and a notification handler has no in-flight tool call to correlate with, so a request sent from there falls back to the optional standalone GET stream — "discarded by the transport with no error, no `onerror` callback and no log at any layer". Issuing the refresh from the handler would re-open the exact hole closed this morning.
- **The notification handler sets a per-transport `refreshPending` flag and resets nothing.** It has no request context, which is why the global reset was written; it does have its own `McpServer`, and `McpTransportManager` builds exactly one server per transport (`mcp/transport.ts:53`), so per-server state _is_ per-transport state.
- **Move all per-transport discovery state off the module global into a record owned by the connection's `McpServer`.** One mechanism fixes defect 2 (there is no global left to reset, so no transport can reach another's state) and defect 4 (the record is released when the server instance is). Chosen over keeping the global `Set` and scoping the reset by key: that needs the request context to be live inside an SDK notification handler (unverified), and still leaves eviction, which would need `tokenId` plumbed into `McpTransportManager` — which does not know the token (`getOrCreate` receives only `requestedSlug`) and could not evict entries a second token created on the same `mcp-session-id`.
- **The refresh slot is consumed by the attempt, not by the answer** — deliberately the inverse of the initial-discovery rule the archived change established (its D3). The consequences are asymmetric: a lost initial discovery permanently misfiles append-only rows, whereas a lost refresh leaves a stale advisory suggestion that activates nothing (`pendingSuggestedSlugs` has exactly one consumer, `project-tools.ts:236`). Retry-until-answered on the refresh path is precisely what produced the measured 2507 ms-per-call stall; consuming on attempt bounds the cost of a notification to one budget expiry.
- **A `list_changed` arriving before any answered discovery runs ordinary discovery, not a refresh.** There is no suggestion to refresh yet, and the `roots/list` that ordinary discovery is about to issue already reflects the new roots.
- **`resetDiscoveryState` is deleted.** With state owned per server instance, the tests that call it get a fresh record per fixture and the helper has no reason to exist. This deletion is safe in the way the `refreshRootsAfterChange` deletion would not have been: it removes a helper whose only purpose was to paper over module-global state, and the state it cleared no longer outlives its owner.
- **`ROOTS_LIST_TIMEOUT_MS` stays 2500. Explicitly deferred, not overlooked.** Its value rested on a diagnosis the archived change refuted, so there is no evidence in either direction, and retuning is blocked on an unanswered question (which of the five clients actually advertise `capabilities.roots` — `archive/2026-08-09-…/design.md:140`). The GONE-QUIET measurement makes the budget _visible_ but does not justify moving it: with the refresh consumed on attempt, one expiry per notification is the whole exposure.
- **Spec: one MODIFIED requirement and one ADDED one.** The MODIFIED one qualifies the once-only guarantee, which is unconditional today and therefore contradicts the `list_changed` scenario sitting six lines below it — a genuine internal contradiction in published text, not a drafting nit. The ADDED one states the refresh contract that no requirement covers today: per-transport isolation, advisory-only, delivered under a tool call, one attempt per notification.

## Capabilities

### New Capabilities

- _(none)_

### Modified Capabilities

- `projects`: **MODIFIED** — "Project auto-detection via MCP `roots` MUST be read-only": the once-only guarantee is qualified as holding absent a `list_changed` refresh, per-transport ownership of the discovery state is stated, and the two scenarios that describe the answered slot and the `list_changed` update are corrected to say when the update is observable. **ADDED** — "The `roots/list_changed` refresh MUST be per-transport, advisory and delivered under a tool call".
- `mcp-api`: **no delta.** Checked rather than assumed: `mcp-api/spec.md:1813` routes the refresh through the same async resolver, whose tool-call-identity obligation (`mcp-api/spec.md`, "The discovery the resolver awaits SHALL be reachable from the tool call that triggered it") the refresh inherits by construction. `mcp-api/spec.md:1122` defines `project.current.suggestedSlugs` as "populated by the most recent `roots/list` derivation that did NOT auto-activate", which stays true. No requirement in `mcp-api` mentions `list_changed`.

## Impact

- **Files.** `apps/server/src/mcp/roots-discovery.ts` (per-server state record; refresh wiring in `ensureRootsDiscoveryRun`; `resetDiscoveryState` deleted), `apps/server/src/mcp/server.ts:516-536` (handler sets the flag; the reset, the dynamic `import()` and the comment that calls the global reset "safe because discovery is idempotent and cheap" all go), `apps/server/src/mcp/roots-discovery.test.ts` (drop the global reset; new arms), `apps/server/src/test/mcp-integration.test.ts` (two-transport arm, refresh arm, no-retry arm), `apps/server/src/test/invariants.test.ts` (assert the discovery module declares no module-level mutable registry). `mcp/_shared.ts` and `mcp/transport.ts` are **untouched** — no signature threading and no eviction hook, which is the point of per-server ownership.
- **No migration, no schema change, no new column, no new MCP tool, no dashboard surface.** All state is in-process and dies with the process.
- **Existing installations.** Nothing to do on first boot after upgrade: the state this change re-homes is rebuilt from cold on every restart by construction, so an installation with hundreds of memories is indistinguishable from an empty one here. No derived data is involved — `memory_fts`, `memory_vec` and the three entity tables are untouched because no `memory` row is read or written. Rollback is a code revert with no data consequence.
- **Behaviour change on the wire, deliberately.** After a `list_changed`, an unrelated connection no longer receives a `roots/list` it did not cause, and no longer sees a suggestion naming its own active project. On the emitting connection the refreshed `suggestedSlugs` still arrives on the next scope-resolving tool call, unchanged from measured behaviour today. A client that stops answering after a `list_changed` pays one budget expiry instead of one per tool call for the rest of the connection.
- **Load-bearing invariants.** None are relaxed. Scope is still resolved only at the service layer through `resolveEffectiveScope`; the refresh writes only `pendingSuggestedSlugs` and can never call `setActiveProject`, so no path added here can change a connection's project, and no append-only rule is touched.
- **Pi is unaffected** and stays the measured negative: `apps/plugin/.pi-plugin/index.ts` sends `capabilities: {}`, so it never advertises `roots` and never emits `list_changed`.
