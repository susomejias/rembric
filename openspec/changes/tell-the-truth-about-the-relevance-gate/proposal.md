# Tell the truth about the relevance gate

## Why

`memory.search` tells every agent that a `abstained:true` response means "no memory cleared the relevance floor". The floor is disabled, has always been disabled, and cannot fire — so the one signal the tool description offers against confabulation is unreachable, and the two states a caller actually meets (a page shortened by the gate that _is_ enabled, and a query that matched nothing at all) are both reported as an ordinary `abstained:false` page.

**The severity is confabulation, not the dead flag.** Measured through the real MCP boundary (bootstrapped server, official MCP SDK `Client` over `StreamableHTTPClientTransport`, production embedder `onnx-community/gte-multilingual-base`), the query `zzqqwx vvbbnm ppllkk xhtqrv` against the 40-row eval corpus returned **8 of 8** requested rows with `abstained:false`. Four nonsense tokens produced a full page of confidently-ranked, wholly irrelevant memories, indistinguishable in the response from a good hit. The dense kNN branch applies no distance floor (`denseRetriever`, `apps/server/src/services/hybrid-search.ts:451`), so for any non-empty scope the fused pool is essentially never empty and the page is essentially never short of `limit` for lack of candidates. This is the exact failure `openspec/specs/mcp-api/spec.md:244` was written against — "An empty result that the model interprets as 'search is broken' or fills in from its own priors is worse than a populated one" — and it is live in the opposite direction: a _full_ result the model reads as evidence.

**`abstained:true` is unreachable.** `export const ABSTENTION_FLOOR: number | null = null` (`hybrid-search.ts:47`); the only `abstained: true` return sits behind `if (abstentionFloor !== null && …)` (`hybrid-search.ts:145`); and the only non-test caller of the gate overrides is `MemoryService.searchWithAbstention`, reached from `memory-tools.ts:961`, which passes none. Control that proves the probe rather than the reading: forcing `abstentionFloor: 0.99` through the same path DOES return `abstained: true` with the floor's reason, so the flag works and simply has no production trigger.

**The state callers actually meet is unreported.** `RELATIVE_LEVEL_RATIO = 0.4` (`hybrid-search.ts:58`) is the gate that ships **enabled**, and it shortens pages constantly: **18 of 24** committed eval queries at `k=8` return fewer than 8 rows, six of them `gated=2` against `ungated=8`. **0 of 24** return an empty page. A caller receiving 2 rows for `limit: 8` cannot tell "the corpus holds only two memories on this" from "six candidates existed and the gate judged them irrelevant" — the difference between stopping and paging on. `apps/server/src/services/memory.ts:440-443` already promises the caller can: "a page shortened by `RELATIVE_LEVEL_RATIO` reports `false`, so a caller can tell 'nothing relevant exists' from 'fewer than `limit` rows were relevant'". As shipped that promise is false — both states are the same response, byte for byte.

**`memory.context` drops the flag entirely.** Its relevance channel calls `deps.memory.search` (`memory-tools.ts:1411`), the wrapper that discards abstention, so the context surface has no abstention or shortening signal at all. Same defect, second surface.

**The CI gate that should have caught this cannot fire.** `checkAbstentionFlags` (`apps/server/src/test/retrieval/run-eval.ts:74-85`) fails the job when the flag disagrees with emptiness. Replacing its predicate with `if (false)` and re-running `pnpm run eval` produced byte-identical output and exit 0 — because no committed outcome exercises either direction: nothing abstains and nothing returns empty. The archived sweep records why in one line: `openspec/changes/archive/2026-08-03-weight-relevance-levels-by-idf/measurements/sweep-after-amendment.txt:56` — "fused pool per query: min 10, max 26". The pool is never empty on this corpus, so the guard has nothing to judge.

**And one of the two published requirements about the flag is unsatisfiable as written.** `openspec/specs/retrieval-evaluation/spec.md:179-182` fails the job on `abstained: false` while returning none; `openspec/specs/memory/spec.md:301` and `:372` both _mandate_ exactly that response. The contradiction was harmless only while both gates were `null`. One of them has to move.

## What Changes

- **`abstained: true` gains its reachable meaning: an empty fused pool.** When both retrieval branches return nothing — an empty scope, a `type`/`status` filter that excludes every row, an FTS-only deployment whose query tokenises to nothing — the response abstains, with its own reason string distinct from the floor's `'no candidate cleared the relevance floor'` (`hybrid-search.ts:102`). Reusing the floor's reason for this state would be a lie about which mechanism spoke. Scoped to the **pool**, not to the page: a deep `offset` over a non-empty pool keeps reporting `abstained: false`, because the corpus did have candidates and the caller merely paged past them. That distinction is the whole of this bullet, and the delta spec states it explicitly on both sides.
- **A new response field says the page was shortened by the gate rather than exhausted by the corpus:** `gateShortened`, present and `true` only when the relative filter removed at least one row from the fused pool AND the returned page holds fewer rows than the requested `limit`. Omitted otherwise. Chosen over the explorer's `poolExhausted` because the inverse framing is ambiguous — a deep-offset empty page also "exhausts" what the caller can reach, and that case must NOT carry the flag. Additive and optional, mirroring the existing `viaEntity` / `entityIndexDraining` / `abstainReason` conditionals, so no client breaks.
- **`memory.context` stops discarding the signal.** Its relevance channel switches to `searchWithAbstention` and reports the ranked pass's verdict as `rankedPass: { abstained, abstainReason?, gateShortened? }`, present **only when the ranked pass actually ran** — the entity pre-pass can fill the channel to its cap and skip the ranked pass entirely (`memory-tools.ts:1410`), and reporting `abstained: false` for a search that never happened would be the same overclaim this change is removing.
- **`SEARCH_DESCRIPTION` stops naming a disabled mechanism** (`apps/server/src/mcp/server.ts:130`). The tail sentence is **swapped, not extended**: the description is 1817 chars against `DESCRIPTION_MAX_LENGTH = 1900` (`server.ts:124`), CI-enforced at `apps/server/src/test/mcp-integration.test.ts:379`, leaving 83 chars — and `openspec/specs/mcp-api/spec.md:2001` records that truncation is a tail cut and that this very sentence IS the tail. The reword documents `gateShortened`, keeps the anti-confabulation instruction that `mcp-api/spec.md:254` mandates verbatim, and adds the one mitigation available without touching retrieval: a full page is not proof of relevance. Exact wording and character arithmetic in `design.md` D5.
- **The eval requirement is narrowed to the half that can catch a bug.** `retrieval-evaluation/spec.md:179-182` keeps failing on `abstained: true` while returning results and stops failing on `abstained: false` while returning none — the latter is behaviour two `memory` requirements mandate. Resolves the contradiction in favour of the shipped, specified retrieval semantics rather than in favour of the harness; recorded as `design.md` D1.
- **A description-content assertion is added.** No test currently asserts any substring of the abstention clause — `grep -rln SEARCH_DESCRIPTION apps/server/src` returns only `server.ts` — so `mcp-api/spec.md:251-254` ("The description steers against confabulation") is specified but uncovered, which is how the sentence came to name a dead mechanism unnoticed. The reword lands with the assertion that would have caught it.
- **NOT changing, stated so it is not read as an omission:** the entity branch keeps `abstained: false` on a miss (it has `entityIndexDraining` for its own ambiguity, `memory.ts:511`), and the no-query listing branch keeps `abstained: false` (it has exact SQL pagination and no gate).

**Explicitly out of scope**, each for a stated reason:

- **Calibrating or enabling `ABSTENTION_FLOOR`.** Not achievable on the committed corpus: the gold-bearing and empty-gold level distributions overlap on `[0.296, 0.307]` (`hybrid-search.ts:55-56`; measured at `archive/2026-08-03-weight-relevance-levels-by-idf/measurements/sweep-after-amendment.txt:61`), so criteria 2 and 3 of `openspec/specs/memory/spec.md:1361` cannot both be met at any value. Its own change, gated on corpus expansion.
- **A distance floor on the dense branch** — the real cure for the garbage query. It is a recall risk that needs its own sweep and its own baselines; guessing it here would be the uncalibrated-gate failure `hybrid-search.ts:42-46` already warns about.
- **`memory/spec.md:1361` criterion 5's 0.05 grid-step requirement**, which the shipped `SWEEP_RATIOS` 0.10 grid (`run-eval.ts:329`) does not meet, and `run-eval.ts:318`'s stale "two grid steps wide" docstring, which quotes a bar that was rewritten in absolute level units. A separate spec-reconciliation pass, precedent commit `4f7adff`.
- **The second unfailable gate in the same area.** All three committed baselines carry `abstentionFalsePositiveRate: 1` as a cap while the measured value is `1.000` — the metric's arithmetic maximum, and `ratchetCaps` clamps proposals with `Math.min(1, …)` (`apps/server/src/test/retrieval/floor-ratchet.ts:136`), so `measured > cap` can never hold. Recorded as known-inert in `design.md` D7 rather than specified here: it becomes fireable only once the corpus contains a query that correctly abstains, which is the deferred follow-up, and speccing a fix this change does not implement is the overclaim it is trying to remove.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `mcp-api`: three requirements change.
  1. _An abstaining search response MUST tell the agent not to invent context_ (`:242`) — gains the empty-pool abstention state with its own reason, the `gateShortened` field and its exclusion of the deep-offset case, and the requirement that the description name both without naming a disabled mechanism.
  2. _`memory.context` MUST offer a relevance channel alongside recency_ (`:695`) — gains the ranked pass's verdict, reported only when that pass ran.
  3. _The four existing memory tools MUST advertise protocol-teaching descriptions_ (`:411`) — the mandated content list gains the shortening signal, and the abstention clause's wording obligation is restated so it can no longer name a gate that is off. The `DESCRIPTION_MAX_LENGTH` requirement (`:2001`) is **not** modified: the cap does not move, and this change satisfies it by swapping text.
- `memory`: one requirement changes — _Recall MUST be able to return nothing_ (`:348`). The floor's paragraph (`:369`) and the shortened-page rule (`:372`) are **narrowed, not reversed**: the shortened page still reports `abstained: false`; the empty **pool** becomes abstention with its own reason; the empty page at a deep `offset` over a non-empty pool is pinned as explicitly NOT abstention, reconciling with `:301`; and the branch gains the obligation to report that the gate, rather than the corpus, shortened a page. The gate-independence of the empty-pool verdict is stated here too, in the paragraph that already governs the both-disabled path (`:374`), rather than in _Retrieval and lifecycle constants MUST be named and bounded in one place_ — the new verdict is not a gate and records no constant, so that requirement needs no delta.
- `retrieval-evaluation`: one requirement change — the abstention-flag agreement scenario (`:179-182`) is narrowed to one direction, and the harness gains a coverage obligation for the guard, since the committed corpus provably cannot exercise it.

Checked and deliberately **not** given a delta:

- `dashboard` — no operator surface renders `abstained` or the new field. Design tokens untouched.
- `http-api` — search is not exposed over HTTP; the session-lifecycle routes are untouched.
- `retrieval-evaluation`'s sweep requirements — the sweep's grid, outputs and determinism are unchanged. Only the flag-agreement scenario moves.

## Impact

**Durable invariants.** None crossed. Append-only is untouched (no `DELETE`, no `content` `UPDATE`, no status flip). Scope-at-the-service-layer is untouched and unchanged: `Scope` is still resolved in `MemoryService` and passed down, and no repository read changes. `topic_key` convergence, fresh-context judgment and derived-never-stored review state are all unaffected. No SQL is added or moved, so the `db/`-confinement invariant is untouched. No new MCP tool — one optional output field on two existing tools.

**Code:**

- `apps/server/src/services/hybrid-search.ts` — a second reason constant beside `ABSTAIN_REASON` (`:102`); the empty-pool return, ahead of the gate block so it holds with both gates `null`; the `gateShortened` computation inside the `relativeLevelRatio !== null` branch; `HybridSearchResult` gains the optional field.
- `apps/server/src/services/memory.ts` — `searchWithAbstention` forwards the new field; the `:436-443` docstring is corrected, since it currently states the promise this change is making true.
- `apps/server/src/mcp/memory-tools.ts` — `memorySearchOutput` (`:363-378`) gains `gateShortened`; the search response (`:1051-1054`) emits it conditionally; the context relevance channel (`:1410-1417`) switches to `searchWithAbstention` and the context output schema (`:480`) and response (`:1481`) gain `rankedPass`.
- `apps/server/src/mcp/server.ts:130` — `SEARCH_DESCRIPTION` reworded.
- Tests: `apps/server/src/services/hybrid-search.test.ts` (the four `abstained === false` assertions at `:658-674`, `:840-862`, `:865-874`, `:898-900` are checked against the new rule — `:898-900`'s empty page 2 has a NON-empty pool and must stay green, which is the control for scoping the new state to the pool); `apps/server/src/test/retrieval/queries.test.ts:55,59-62` (the existing `zzqqwx vvbbnm ppllkk` empty-pool probe gains the abstention assertion it was one line short of); `apps/server/src/services/memory.test.ts:282`; `apps/server/src/test/mcp-integration.test.ts` (the new boundary test and the description-content assertion); `apps/server/src/test/retrieval/run-eval.ts:74-85` (the narrowed predicate) plus a direct test of that predicate over synthetic outcomes.

**Existing installations.** No migration, no schema change, no new column, no index. Nothing derived needs invalidating: `memory_fts`, `memory_vec` and the three entity tables are untouched — no row is written, read differently at the SQL level, or re-scoped, and their regeneration is unchanged. First boot after upgrade on a populated installation performs no work and behaves identically for every query whose pool is non-empty, which on a populated corpus is nearly all of them. Rollback is a plain image downgrade with no data step: a client that saw `gateShortened` simply stops seeing it, and an older server's response validates against an older schema.

**Behaviour visible on first boot** is confined to two responses that were previously indistinguishable from an ordinary page: an empty-pool search now carries `abstained: true` plus a reason, and a gate-shortened page now carries `gateShortened: true`. Both are additive fields on a successful call; no error code changes, no result set changes, no ordering changes. An agent that ignores both fields sees exactly today's behaviour.

**Plugin tree.** No change, verified rather than assumed: `grep -rl abstain apps/plugin/` matches **zero** files. The tool description is server-side and all four clients read it from `tools/list`, and an optional output-schema field is additive for the bridge, which does not interpret response bodies. One shared resource, four clients, nothing to copy.
