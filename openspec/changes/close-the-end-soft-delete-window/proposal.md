# Close the soft-delete window between the `/end` gate and the write

## Why

`POST /api/<slug>/sessions/:id/end` checks the soft-delete gate and then awaits the request body before writing. `api-router.ts:190` calls `rejectIfDeleted(...)`; `api-router.ts:194` calls `readJson(c)`, which awaits `c.req.json()` — the body stream; `api-router.ts:201` calls `agentSessions.end(...)`. A soft-delete landing in that gap is not rejected. The gap is not a few instructions: `sessionEndSchema` (`api-router.ts:74`) admits a `summary` of up to 40,000 characters, so the window spans a whole body upload. `POST /dashboard/sessions/:id/delete` (`dashboard/sessions.ts:478`) soft-deletes with `adminBypass` and no status gate, so an operator pressing Delete while an agent's end-of-session POST is in flight is the realistic trigger.

Measured, not argued. Six arms against the real Hono router (`app.request`) with a `ReadableStream` body that stalls mid-payload and releases only after the interleaved `softDelete` — the stall is released from the handler's own `getById`, so the interleave provably lands after the gate returned and before the service write:

| Arm           | Setup                                     | Status  | Row after                                                                 |
| ------------- | ----------------------------------------- | ------- | ------------------------------------------------------------------------- |
| **CONTROL-1** | `/end`, active, no interleave             | **200** | `status='ended'`, `summary='control one'`                                 |
| **CONTROL-2** | `/end`, soft-deleted _before_ the request | **409** | unchanged (`summary=null`)                                                |
| **RACE-A**    | `/end`, active, deleted mid-flight        | **200** | `status='ended'`, `ended_at` set, `summary` **written**, `deleted_at` set |
| **RACE-B**    | `/end`, `ended`, deleted mid-flight       | **500** | unchanged                                                                 |
| **RACE-C**    | `/summary`, active, deleted mid-flight    | **200** | `summary` **written** onto the soft-deleted row                           |
| **RACE-D**    | `/summary`, `ended`, deleted mid-flight   | **500** | unchanged                                                                 |

Both controls pass, so the instrument is sound and the race arms count. Two distinct defects fall out:

1. **RACE-A and RACE-C mutate a soft-deleted row and answer `200 OK`.** `http-api/spec.md:223` says, unqualified, _"Soft-deleted rows SHALL be rejected with `session_deleted`."_ This is a straight violation of a published SHALL. The cause is that `end()` and `writeSummary()` only consult `deletedAt` inside `writeTerminalFields` (`agent-sessions.ts:264`), which the **active** branch never reaches (`agent-sessions.ts:363`, `:322`). The boundary gate is the only thing protecting an active row, and the boundary gate is stale by the time the write runs.

2. **RACE-B and RACE-D answer `500` for a client-side conflict, undiagnosably.** The service throws `DomainError('session_deleted', …)`; `statusForCode` (`api-router.ts:335-364`) has no `session_deleted` case — the string occurs exactly once in the file, in `rejectIfDeleted`'s hand-written 409 — so it falls to `default: 500`. Worse, `domainErr` returns `c.json` directly for a `DomainError` and only the non-`DomainError` branch calls `httpInternalError`, which is the only thing that logs (`server/error-response.ts:30-33`). The measured bodies carry no `errorId` and nothing reaches the log. An operator sees a 500 with no trace to correlate. `http-api/spec.md:207-210` already pins **409** for exactly this condition on `/summary`, so RACE-D violates that too.

## What Changes

- **Hoist the `deletedAt` check out of `writeTerminalFields` to the top of both `end()` and `writeSummary()`**, immediately after the cross-token mask, where `getById` has just re-read the row inside one synchronous tick. Chosen over adding a second boundary check after `readJson`, because the boundary can never be fresh — any check that precedes the write on a different tick reopens the same window. The service's own re-read **is** the fresh check; there is nowhere later to look. This one move closes RACE-A, RACE-C, and the TOCTOU class on both endpoints, and turns RACE-B/RACE-D into a throw that a status case can map. Also chosen over wrapping the read-and-write in a transaction: the connection is single and synchronous, so the re-read and the `UPDATE` are already un-interleavable; the bug is the _missing_ check, not a missing lock.
- **Add `case 'session_deleted':` to `statusForCode`'s 409 group.** Restores the 409 that `http-api/spec.md:207-210` already requires on `/summary` and gives `/end` the same code. Chosen over routing the throw back through `rejectIfDeleted`'s hand-written response, which would leave the second copy of the mapping that caused the divergence.
- **Fix `writeSummary()` in the same change, not a follow-up.** RACE-C is the same defect on the sibling path reached through the same `rejectIfDeleted` → `await readJson` shape (`api-router.ts:146`, `:150`). Fixing only `end()` leaves a working instance of the class behind a proposal that claims to have closed it.
- **Spec: one clarifying addition, not a new rule.** `http-api/spec.md:223` already forbids the RACE-A outcome, so this is a defect fix. What is genuinely missing is (a) the statement that the rejection is evaluated against a read taken in the same tick as the write, and (b) the 409 mapping for `/end`, which `/summary` states and `/end` does not. `sessions/spec.md:60` already requires the check "at that boundary AND in the service", but it sits under **Terminal session rows MUST accept late summary and title writes** and its scenarios are `GIVEN status='abandoned'` — it mandates the service check that exists without verbatim extending it to the active path. That sentence is extended, and the broader rule is stated once in the `sessions` capability.

## Impact

- **No migration, no schema change, no new column, no MCP tool.** Nothing is written differently; a write that should never have happened stops happening.
- **Existing installations**: no first-boot work, no derived-data invalidation (`memory_fts`, `memory_vec`, the entity tables are untouched — no `memory` row is involved). Rollback is a code revert with no data consequence, because the change only ever _prevents_ an `UPDATE`.
- **Behaviour change on the wire**, deliberately: `/end` and `/summary` against a row soft-deleted mid-request now answer `409 session_deleted` instead of `200` (RACE-A/C) or `500` (RACE-B/D). The plugin hooks suppress output and exit 0, so no client breaks on the new code.
- **No caller is stranded.** Re-verified rather than trusted: the only production callers of `end()`/`writeSummary()` are `api-router.ts:159`/`:201` and `mcp/session-tools.ts:230`/`:266`, all four of which already pre-check with `rejectIfDeleted`; `summarize()` (`agent-sessions.ts:389`) has no production callers at all (`grep` finds it only in `agent-sessions.test.ts`); and the two seed scripts (`seed-dev.ts:312`, `seed-volumetric.ts:691`) end rows they just created. `abandonStale` retires stale-active rows through `abandonInactiveSince`, which filters on `status` alone (`agent-sessions-repository.ts:216-228`) and never calls `end()`, so guarding `end()` cannot strand a soft-deleted active row.
- **MCP is already safe and stays untouched.** `mcp/session-tools.ts` calls `rejectIfDeleted` and `end()` with no `await` between them (`:227-230`, `:263-266`), so it has no window. The hoisted guard is defence in depth there, not a fix, and no `mcp-api` delta is needed.
