## Why

`align-rarity-gate-population` (archived 2026-07-29) corrected both sides of the entity rarity gate to count only `active` memories and deferred two questions to a named follow-up: is `0.15` the right threshold (task 8.1), and is a small-scope floor needed (task 8.2). This change answers both. Re-measuring the distribution to answer them turned up a third fact that changes what the answers can be.

**The gate is broken at both ends of the corpus-size range, and no value of the threshold fixes either end.** The gate is `Lₐ / A > ENTITY_RARITY_THRESHOLD → skip` with `Lₐ` the entity's active link count and `A` the scope's active count (`services/save-time-candidates.ts:195-203`). Both regimes follow from that one line by arithmetic, not by sampling:

| regime    | closed form                                 | at `T = 0.15`                                                              | consequence                                                                |
| --------- | ------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| small `A` | blocks whenever `A < Lₐ/T`                  | one link blocks in any scope with `A ≤ 6`; four links block up to `A ≤ 26` | the channel is **off** on a young project                                  |
| large `A` | one admitted entity may carry `⌊T·A⌋` links | `A ≥ 34` permits `≥ 5` links; `A = 1443` permits **216**                   | one admitted entity can take **every** slot — the gate's own charter unmet |

Both were re-verified on the resident 2055-row dev corpus (1443 active / 601 superseded / 11 archived, 2441 entity links, 32 distinct entities, one project partition). The large-`A` result is not theoretical there: the gate blocks **0 of 32** entities, and **31 of those 32 admitted entities carry ≥ 5 active links**, which is the whole per-save budget (`CANDIDATES_PER_SAVE_MAX` default 5, entity candidates leading unconditionally). `memory-entities/spec.md:354` says the gate exists to bound composition, "so a ubiquitous entity takes every slot and the lexical and dense channels contribute nothing". On the only corpus in hand it permits exactly that, 31 times over.

**And the threshold's value cannot be calibrated by measurement, which is why the first of the two deferred questions has to be retired rather than deferred again.** Three independent reasons, each verified rather than asserted:

1. **No gold signal exists.** The gate sits on the save path. `pnpm run eval` enters retrieval through `searchWithAbstention` and never reaches it — the archived pass confirmed the eval baseline is _unmoved_ by a change to both gate predicates. There is no labelled answer to "should this entity have proposed a candidate", so the sweep-plus-plateau discipline `memory/spec.md:1212-1218` contracts for the abstention floor and `RELATIVE_LEVEL_RATIO` is structurally unavailable here.
2. **The instrument cannot discriminate.** On the dev corpus every `T` in `[0.0194, 0.1303)` takes the _identical_ 32 decisions (6 blocked / 26 admitted) — a plateau 0.11 wide — because the seed's entity assignment is bimodal (26 entities at `≤ 0.0194`, 6 at `0.1303–0.1490`, nothing between). That bimodality is a seed artifact, not a population property, so neither the plateau nor its interior is evidence about real corpora. The 42-item eval corpus carries 2 entity links total and cannot take a gate decision at all.
3. **No `T` fixes either regime.** Lowering it worsens small-`A` (`A < Lₐ/T` grows). Raising it worsens large-`A`. Saturation needs `T < CANDIDATES_PER_SAVE_MAX / A`, which at `A = 1443` is `0.0035` — a value that would block essentially every entity. The proportion form cannot serve both jobs the gate has been given.

Worth recording as a correction to the archived measurement, since re-verification was not ceremonial: the top entity is **two** active links from the gate biting, not one (`215/1443 = 0.1490` admits, `216/1443 = 0.1497` still admits, `217/1443 = 0.1504` blocks).

## What Changes

- **`ENTITY_RARITY_THRESHOLD` stays at `0.15`, and the question "is `0.15` right?" is retired, not deferred a third time.** The value has never been calibrated and — for the three reasons above — cannot be, by any instrument this repo can build today. What changes is that the _reason_ is now recorded with its evidence, together with the two facts that would reopen it (a corpus with a non-synthetic entity distribution, or a labelled save-time candidate fixture). Rejected: bumping the number to the interior of the synthetic plateau (`≈ 0.075`). It would look like a calibration, would be traceable only to a seed artifact, and would tighten the small-`A` dead zone from `A ≤ 6` to `A ≤ 13` for a single link.
- **A floor is added, keyed on the NUMERATOR rather than the denominator: a new compile-time constant `ENTITY_RARITY_MIN_LINKS = 5`, below which the gate does not apply.** The deferred question asked for "no gating below `N` active memories". That form is rejected: every `N` is a guess, and it still blocks a two-link entity at `A = 13`, which is exactly the young-project convergence case the floor exists to protect. The numerator form is instead _derivable_ from the gate's published charter — `memory-entities/spec.md:354` grounds the whole gate in "only a memory that can OCCUPY a slot can starve another channel", and an entity with fewer active links than the per-save budget holds cannot occupy the budget, so blocking it serves no purpose the requirement names. It also subsumes the small-`A` case completely: with three active memories and one link, `Lₐ = 1 < 5` admits, where `1/3 = 0.33` blocks today.
- **The floor's blast radius is bounded by proof, not by hope.** It can only flip a decision where the gate would have blocked _and_ `Lₐ ≤ 4`, which requires `A ≤ 26`. On a large corpus it is a no-op: 31 of the dev corpus's 32 entities carry `Lₐ ≥ 5`, and the remaining one is already admitted. So this is a small-scope fix with no effect at scale, which is what makes it safe to ship without the calibration the threshold cannot have.
- **`ENTITY_RARITY_MIN_LINKS` is derived from `CANDIDATES_PER_SAVE_MAX_DEFAULT` once, at authoring time, and is NOT read from the operator setting at runtime.** `CANDIDATES_PER_SAVE_MAX` is environment-configurable (`config.ts:132-137`, `0..25`, default 5) and may be `0`. Reading it here would make an admission rule environment-settable — the exact reason `CANDIDATE_POOL_SIZE` is not exposed (`memory/spec.md:1203`) — and at `0` would invert the gate into always-applies. The coupling is a documented derivation, not a dependency.
- **This change does NOT restore the composition guarantee at large `A`, and says so instead of implying it.** The saturation finding (31/32) is a defect in the _mechanism_, not in the number: a per-entity proportion gate cannot bound a shared fixed-size budget. Bounding the entity channel's slot share belongs at the merge step, changes the published precedence prose (`memory-entities/spec.md:360`), and needs a different instrument (per-save composition over a real ingest, not a decision table). It is named as a follow-up and seeded with the 31/32 figure, the same way this change was seeded.
- **The measurement instrument is an exhaustive enumeration of the decision function, not a corpus sample.** The gate is `f(Lₐ, A)` over two integers, so a decision table over a grid of `(Lₐ, A)` is complete where a corpus sample is a sample — and it is the only instrument that can drive the gate in _both_ directions, which neither available corpus can. Every reported ratio carries its denominator; this code path has already produced two vacuous zeros caught only by that discipline.
- **One archived test must be rescaled, not relaxed.** The blocked-direction service test added by `align-rarity-gate-population` (`save-time-candidates.test.ts:772`) uses `Lₐ = 2`, which the new floor admits — so it would silently stop pinning the population fix. It is rescaled to `Lₐ = 5, A = 20, S = 14` (active `5/20 = 0.25` blocks; non-archived `5/34 = 0.147` admits) so it keeps failing under the reverted predicate. Separately, `"a very common entity surfaces nothing"` (`:583`) is `Lₐ = 5, A = 5` — exactly at the new boundary. It survives at `5` and would break at `6`, making it the accidental guard on the constant's value; that is recorded so a future bump is not absorbed by re-diluting a fixture.

## Capabilities

### New Capabilities

_None._

### Modified Capabilities

- `memory-entities`: the save-time conflict-detection channel requirement gains a normative link-count precondition (the rarity gate SHALL NOT block an entity whose active link count is below the per-save budget, because such an entity cannot occupy the budget), and its two unconditional statements about common entities — the prose at `:350` and the `"A very common entity generates no candidates"` scenario — are qualified so they stay true under it. Two scenarios are added: a young scope still proposes, and an entity at or above the link floor and over the threshold is still blocked.
- `memory`: the named-constants requirement gains `ENTITY_RARITY_MIN_LINKS`, and `ENTITY_RARITY_THRESHOLD`'s bullet is qualified — it is no longer an unconditional maximum share, and its "so it does not become inert as a corpus grows" clause is corrected, since the gate keeps blocking as the corpus grows but stops bounding composition.
