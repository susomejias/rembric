## 1. The comparator (design.md D1, D3)

- [x] 1.1 In `apps/server/src/services/relations.ts`, export `ANNOTATION_TIER` — a `Record<RelationView['kind'], number>` in the order `conflicts_with` (0), `supersedes` (1), `superseded_by` (2), `pending_conflict` (3), `scoped` (4), `compatible` (5), `related` (6) — and `compareAnnotations(a, b)` applying tier, then `createdAt` descending, then `judgmentId`. The comparator needs `createdAt`/`judgmentId` on every candidate, so widen the internal shape it sorts (both come from the `MemoryRelation` row and are already in hand).
  - The record is keyed by a new exported `AnnotationKind` = `Exclude<RelationKind, 'not_conflict'> | 'superseded_by' | 'pending_conflict'`, not by `RelationView['kind']` verbatim: as written, `RelationView['kind']` admitted `not_conflict`, which task 1.2 requires the record NOT to carry, so indexing it would not typecheck. `RelationView['kind']` is now `AnnotationKind`, which makes the record total at the type level as well as under 1.2's test.
  - The sorted shape is `OrderedAnnotation { view, createdAt, judgmentId }` — a wrapper rather than extra keys on the view, so the two sort columns cannot leak into a response (the handler serialises the view object as-is; zod output schemas do not strip it).
- [x] 1.2 Add a test asserting `ANNOTATION_TIER` covers every member of `RELATION_VALUES` except `not_conflict`, plus `pending_conflict` and `superseded_by` — so a future `RelationKind` addition fails a test instead of silently sorting to `undefined`.
- [x] 1.3 Add a test asserting the order is TOTAL: for a set of relations sharing one `createdAt` millisecond, `compareAnnotations` never returns 0 for two distinct rows, and sorting a shuffled copy converges on one permutation. This is the key that stops the defect surviving inside its own fix (design.md D1).

## 2. Apply the order and report the true total (design.md D3, D4)

- [x] 2.1 Apply `compareAnnotations` in `listForMemories` before `appendCapped`'s per-memory cap, and in `listForMemory` before its `slice(0, limit)`. No repository change and no `ORDER BY`: `listTouchingAny` / `listTouching` already return every touching row unbounded, which is the same reason the comparator lives in the service.
  - `appendCapped` is gone: it existed only to cap while accumulating, which is precisely what cannot happen before the sort. Both methods now accumulate through one shared `toOrderedAnnotation(row, memoryId)` projection, sort, then slice — which also removes the pre-existing duplication of the `superseded_by` derivation between them.
- [x] 2.2 Have both methods return the true per-memory total alongside the capped list. Count **annotation views, not rows**: `listForMemories` builds a view per endpoint present in the input set, so a relation whose source AND target are both in the page contributes one view to each memory's total. No extra query — the full set is already in hand.
  - Both return `AnnotationPage { views, total }`. Asserted by "counts views rather than rows when both endpoints are on the page" in `relations.test.ts`: one `conflicts_with` row between two memories on the same page yields `total: 1` for each, pointing at the other.
- [x] 2.3 In `listForMemory`, count the total AFTER the orphan skip, not as `rows.length`: `listTouching` (unlike `listTouchingAny`) does NOT filter `status='orphaned'` in SQL — the service's loop does. The total must equal the number of annotations the caller could ever be shown, i.e. after the `not_conflict` and `orphaned` exclusions.
- [x] 2.4 Add `relationsTotal: z.number().optional()` to the shared `memoryRow` zod object in `apps/server/src/mcp/memory-tools.ts` and to the single-id `memory.get` output object. - [x] 2.5 Emit `relationsTotal` at all three annotation call sites — `:873` (search rows), `:977` (batch `memory.get`), `:1047` (single `memory.get`) — whenever `relations` is present, truncated or not.   - It is emitted unconditionally, including `0` when the handler was built without a `RelationsService` (in which case `relations` is `[]`), so a caller never has to read the field's ABSENCE as a value.
  - One addition beyond the letter of the task: `fields: ['relations']` now also admits `relationsTotal` to the projection. Without it, the one caller who projects `relations` would be the only one to receive it without its total, contradicting the delta spec's "every row carrying `relations` SHALL also carry `relationsTotal`". It is one line and changes nothing for a caller who does not pass `fields`.

## 8. Follow-up issue bodies that could not be posted

Ready to paste as `gh issue create` bodies. See 7.4 for why they are here rather than in the tracker.

### 7.4 — fix(mcp): memory.search applies `fields` to results but not to expanded rows

`memory.search`'s `fields` projection is applied to `results` rows but not to `expanded` rows, so a caller passing `fields: ['status']` still receives full-content appendix rows.

In `handleSearch` (`apps/server/src/mcp/memory-tools.ts`) the `fieldSet` filter runs inside `memories.map(...)`, while the one-hop expansion builds its rows from the unfiltered `formatRow(row)` and then adds `expandedFrom` / `relationKind`. The token budget `fields` exists to protect is spent anyway, on up to `RELATION_EXPANSION_CAP` (5) full rows. This contradicts `mcp-api`'s projection requirement, which carves out no appendix.

Open questions for the change that fixes it: do `expandedFrom` / `relationKind` survive any projection as identity fields (they are the only thing explaining why the row is in the response)? And does `snippet` have the same hole (it is applied inside `formatRow`, so it should not — assert it).

Found while measuring the annotation-ordering defect (`order-relation-annotations`); independent of it, hence a follow-up rather than a rider.

### 7.5 — fix(entities): canonicalize relative paths, and the env_var:MRR false positive

Two extraction defects found while measuring the annotation graph.

1. **Relative paths are not canonicalized.** `db/client.ts` and `apps/server/src/db/client.ts` become two distinct `path` entities that never join, so an `entity` lookup for one misses every memory that named the other. This contradicts `openspec/changes/archive/2026-07-25-add-entity-index/design.md` Decision 3. Any fix has to decide what canonical means with no repo root to resolve against, and needs an `EXTRACTOR_VERSION` bump plus a re-scan of `memory_entity_scan`.
2. **`env_var:MRR` false positive.** The all-caps heuristic promotes a metric name from prose ("MRR@8") to an `env_var` entity, so the index carries noise no `entity` lookup will ever address. Worth measuring against `src/test/entity-noise/noise-rate.test.ts` before changing the rule.

### 7.6 — docs(spec): annotations do not carry a target snippet

`openspec/specs/mcp-api/spec.md:140` and the `memory` capability's relation-annotation scenarios state that each annotation carries "a short snippet of the target's content". `RelationView` (`apps/server/src/services/relations.ts`) has no such field and never has: an annotation is `kind`, `targetId`, `status`, and optionally `judgmentId` / `reason` / `confidence`. The shipped `relationView` zod output object agrees with the code, not the spec.

Pre-existing overclaim, carried unchanged into `order-relation-annotations`' delta rather than repaired there, because rewording a published requirement inside a change about something else is how a spec drifts unnoticed. Reconcile deliberately: either add the field (it costs a JOIN against `memory` that the annotation reads do not currently do) or delete the claim from both specs.
