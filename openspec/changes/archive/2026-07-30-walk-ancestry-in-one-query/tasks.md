## 8. Defects found by the adversarial review, and what they cost

- [x] 8.1 **S1, HIGH, real regression in shipped code.** `.filter((id) => id !== start.id)` ran AFTER the SQL `LIMIT PREDECESSOR_CAP + 1`, so when the graph cycles back to the requested row that id consumed a probe slot: `truncated` came back **false** with ancestry still unreached. Reproduced against the verbatim old loop — new `{count: 10, truncated: false}` vs oracle `{count: 10, truncated: true}` — and it violated two normative clauses of this change's own delta. `memory.compare({relation: 'supersedes'})` has no cycle guard, so the state is reachable through the public API. Fixed by asking for `PREDECESSOR_CAP + 2`: `UNION` dedupes, so the start id can occupy at most one slot. Regression test added.
- [x] 8.2 **S3: a normative `SHALL` rested on a premise I never measured.** The `data-access` delta required statement counts be taken on a fresh connection "because drizzle reuses prepared statements". Measured: attaching the identical proxy to the connection that seeded a 30-save chain reports the SAME count (4). Drizzle's `db.all(sql…)` and builder `.all()` go through one-time preparation here, so nothing is cached. The scenario is rewritten to require what actually matters — wrap the terminal `all`/`get`/`run` rather than counting `prepare` calls — and the fresh connection is kept as defence, described as such.
- [x] 8.3 **S6: the shipped statement used a construct the published contract does not list.** `data-access` limits raw SQL in repositories to "FTS5 `MATCH`, sqlite-vec functions, `json_each`, PRAGMA, and `VACUUM INTO`". `WITH RECURSIVE` is none of those, and this change ADDED a requirement without MODIFYing that one. Now added to the allow-list via a `MODIFIED` block, with both published scenarios preserved.
- [x] 8.4 **S4: the exact statement counts were harness numbers presented as path numbers.** 4 rises to 5 once the saved row has an embedding, and to 6 with extracted entities (production passes them; the test does not); `memory.get`'s 6 depends on the requested row being `active`, since `findHead` returns early. Documented at both assertion sites; the BEFORE/AFTER delta is what the change rests on, not the absolutes.
- [x] 8.5 **S5: neither new test file called `t.cleanup()`**, leaking 17 temp dirs and open SQLite handles per run, against `createTestDb`'s stated contract. `afterEach` added to both. The vacuous `check([])` case (comparing `[]` to `[]` before any query) replaced with direct assertions.
- [x] 8.6 **S7/S8: a docstring claimed a scope check that does not exist** (callers scope the START row, not the results) — corrected. And `unsafeAncestorIds` had no ceiling: measured 0.042 ms/call at `limit: 10` against **6.08 ms/call** at an unbounded limit on a 5000-deep chain, returning every row. Both call sites pass small constants, but an `unsafe*` method must not depend on that; clamped at `ANCESTRY_HARD_LIMIT = 1000`.
- [x] 8.7 **What the review found nothing on, recorded so the coverage is legible:** equivalence itself is clean — 900 fuzzed comparisons (2–15 node graphs, out-degree 0–3, ~15% dangling, cycles allowed, 1–3 start ids, caps 1/3/10) plus every hand-built adversarial shape returned identical ids AND order. SQLite's `UNION` recursive CTE is FIFO/BFS with first-occurrence dedupe and never reordered. The SQL is fully parameterised (`json_each(?)`, `LIMIT ?`); injection attempts round-trip as data. The plan holds after `ANALYZE` on a 5000-row corpus, which the shipped test cannot show because it runs on a fresh DB with no `sqlite_stat1`. And a duplicated parent inside one `replaces` array is refused at INSERT by the migration-0021 trigger, so duplicate `startIds` cannot arise from `saved.replaces` at all.
