## Why

Every stdio client this repo ships — Claude Code, Codex CLI and opencode — reaches the server through `apps/plugin/bin/rembric-bridge.mjs`, which delegates the whole transport to `npx -y mcp-remote@0.1.38` (`rembric-bridge.mjs:129`; mandated by `openspec/specs/claude-code-plugin/spec.md:36` and pinned by `:279`–`:281`). That package does not implement the MCP spec's session-recovery MUST, and the failure it produces is a hang, not a degraded call.

**Measured 2026-08-15, controlled A/B.** Instrument: a minimal Streamable HTTP stub that terminates each session after its first successful `tools/call` and answers later requests on that id with `404` / `-32001` per the spec; a fresh `initialize` always succeeds. Same host (a real `claude` CLI with an isolated config), same model, same prompt on both arms — only the transport chain varies.

- **Native** — Claude Code's own `"type":"http"` MCP client, no bridge: `tools/call(s3) → 404 → initialize → s4 → retry ok`. Transparent, **~7 ms**.
- **Bridge → `mcp-remote@0.1.38`**: `tools/call(s7) → 404 → silence`. **No `InitializeRequest` ever reaches the stub.** The process hangs until an external `timeout` kills it (**exit 124**). Reproduced 3× — twice against the real server, once against the stub.

The spec is unambiguous (2025-06-18, Session Management): the server "**MAY** terminate the session at any time, after which it **MUST** respond … with HTTP 404", and "When a client receives HTTP 404 in response to a request containing an `Mcp-Session-Id`, it **MUST** start a new session by sending a new `InitializeRequest`." Claude Code's own client obeys it; the transport we interpose in front of it does not.

**This costs users today, with no new mechanism required.** `McpTransportManager` keeps its `(server, transport)` pairs in a plain in-process `Map` (`apps/server/src/mcp/transport.ts:37`), and `http.ts:386-392` correctly answers `404`/`-32001` for an `mcp-session-id` it does not hold (commit `c2affef`). So **every server restart invalidates every live session id** — including the dashboard's one-click self-update — and each bridge-connected session then wedges on its next tool call. The bridge's silence is the measured, host-independent half; what each host does with a request that is never answered is measured for Claude Code only.

**There is no version to upgrade to.** `0.1.38` is the latest published `mcp-remote` (verified against the registry). Its dist has exactly two `404` code paths — OAuth metadata discovery (`chunk-65X3S4HB.js:20148,20226`) and an initial-connection transport-strategy fallback to legacy SSE guarded by `shouldAttemptFallback` (`:20529`) — and neither is a session-terminated → re-init path. The defect is upstream `geelen/mcp-remote#106`, open and unanswered since 2025-06-07; our A/B is posted there as corroboration (`#106#issuecomment-5299283302`). Issue #348 carries the full trail.

**And the defect is not the only cost — it is the one that finally makes the dependency indefensible.** Measured 2026-08-15 against a request-logging stub, driving `initialize` + `notifications/initialized` + `tools/list` through `npx -y mcp-remote@0.1.38 <url> --allow-http --header 'Authorization:Bearer …'`, the server-side request log reads, in order: `GET /mcp`, `GET /.well-known/oauth-protected-resource/mcp`, `GET /.well-known/oauth-protected-resource`, `GET /.well-known/oauth-authorization-server`, and only then `POST /mcp initialize`. **Four HTTP requests and 25 ms elapse before the first MCP frame**, on loopback against a stub that answers each discovery probe instantly with `404`; over a real network those are three extra round trips on every session start. Its stderr also reports `Using automatically selected callback port: 45400` — an OAuth callback listener bound on every start, for a flow this deployment never uses. And the `initialize` frame that reached the stub carried `clientInfo.name = "probe-host (via mcp-remote 0.1.37)"` where the host had sent `"probe-host"`: the host's identity is rewritten, and the version it appends is **wrong** (0.1.37 while running 0.1.38). None of this is configurable, and all of it is paid on every session start of every client.

**The two-piece shape is itself a consequence of the same root.** `rembric-bridge.mjs` exists to do the things a foreign engine could not be told to do — read `.rembric`, build the path-scoped URL, warn about an old server — and then hand off. Its spec says so plainly: "purely a URL-building entrypoint" (`:37`). Roughly half its 159 lines are not URL building at all; they are the cost of wrapping someone else's program: `spawn`, `stdio: 'inherit'` relay, `child.on('error')`, exit-code forwarding, and re-raising the child's terminating signal in our own process (`:135`–`:158`). With the engine owned, none of that has a reason to exist.

## What Changes

- **The end state is one published piece, not two.** `@rembric/mcp-bridge` absorbs the entire client side: `.rembric`/slug resolution over the `CLAUDE_PROJECT_DIR > PWD > process.cwd()` chain, URL building, the stderr diagnostics, the advisory `MIN_SERVER_VERSION` `/healthz` check, bearer injection, the stdio↔Streamable-HTTP transport, and the `404`→re-init. Client manifests spawn it directly — `command: "npx"`, `args: ["-y", "@rembric/mcp-bridge@<pin>"]` — and ship inside the plugin tree, so a release updates the pin and the package atomically. **Rejected: keeping the wrapper.** The split existed only because the engine was third-party; with the engine owned, the wrapper's reason dissolves, and a design that would never have been written from scratch is not one to preserve out of momentum.
- **What that deletes, concretely:** the child-process machinery — `spawn`, the `stdio: 'inherit'` relay, `child.on('error')`, exit-code forwarding, and terminating-signal re-raising — and one process per session. Today a session is `node(bridge) → npx → node(mcp-remote)`; after, it is `npx → node(bridge)`. `--allow-http` disappears along with its normative clause (`:36`), because plain HTTP is not a special case for `fetch`; the OAuth discovery probes and the callback port disappear because bearer-only is the whole auth surface; and the third-party pin's **diff-audit** burden on every bump collapses into our own release train, keeping the exact-pin discipline while removing the "read someone else's changelog" step.
- **opencode uses its measured config hook for compatibility.** When `mcp.rembric` exists, `plugin.ts` replaces its in-memory command with exact `npx -y @rembric/mcp-bridge@<plugin version>`, preserving the user's environment and file. Fresh installs print the npx snippet; the installer never writes `opencode.json`. Existing launcher files are left as user-owned residue and are not copied, versioned, or removed.
- **The engine is hand-rolled with zero runtime dependencies.** It owns only newline-delimited stdio framing, `fetch` with a bearer header, and `data:` line parsing on the response stream — not SSE resumability (this server offers no resumable streams), not OAuth, not the server half of the protocol. `apps/plugin/.pi-plugin/index.ts` already ships that same surface with `dependencies: {}`. **Rejected: building on the official `@modelcontextprotocol/sdk` transports**, which was specified first and reversed on measurement — it installs 93 packages / 25 MB against `mcp-remote`'s 80 / 7.0 MB (`npm install --ignore-scripts`, clean directory, 2026-08-15), because `express`, `hono`, `cors`, `jose`, `eventsource` and `express-rate-limit` are `dependencies` rather than peers. A replacement that installs more than the delegate it removes defeats part of its own purpose, and none of that surface is reachable from a stdio proxy. The one mechanism with no precedent in `.pi-plugin/` — relaying a server-initiated `roots/list` and posting the host's answer back — was measured working before this was settled (`measurements/gate-arm3-roots-relay.log`).
- **The recovery is narrow, deliberate, and already has a reference implementation in this repo's history.** On an HTTP `404` to a request that carried an `mcp-session-id`: discard the id, re-initialize once, retry the original request once. `404` **only** — `401`/`403`/`429`/`5xx` keep failing unchanged — and never a loop. Retrying a write is safe because the server's refusal fires at the transport boundary (`http.ts:386`) **before any tool handler runs**, so the retried call cannot have been half-applied. Commit `ea09360` implemented exactly these semantics for the Pi client, with tests and green-then-red mutation proofs, before being reverted with its parent change; this change reuses that reasoning and those mutation gates.
- **The bridge forwards the host's `initialize` rather than substituting its own identity**, so the server records the real `clientInfo` instead of the rewritten string measured above. This is a **requirement**, not a side effect, and it drives the architecture: a raw message pipe that lets the host's `initialize` through verbatim, not an SDK `Client`+`Server` pair that re-initiates its own session and stamps its own identity — which is precisely how `mcp-remote` mangles the field.
- **The bearer moves out of `argv` and into the environment.** Today the bridge passes `--header "Authorization:Bearer ${token}"` as a process argument (`rembric-bridge.mjs:142-143`), readable by any local process via `ps` / `/proc/<pid>/cmdline`. The bridge takes **no arguments at all**: `REMBRIC_SERVER_URL`, `REMBRIC_API_TOKEN` and the optional `REMBRIC_PROJECT_SLUG` fallback all arrive through the environment the host already supplies. **OAuth is an explicit non-goal** — bearer-only, recorded as a deliberate boundary so nobody re-adds `mcp-remote`'s largest subsystem by increments.
- **The canonical `rembric-dotenv.mjs` moves into the package**, because slug resolution is now the package's job and the module must ship in its tarball. It remains **exactly one** implementation: the opencode plugin and the Pi extension import it from its new location, and the bash (`_api.sh`) and Python (Hermes) parsers stay separate under the standing cross-language rule. `rembric-plugin-core.mjs` does not move — it is session-protocol logic and the bridge must not touch it.
- **The advisory server-version check moves with everything else, unchanged in behaviour and still a single implementation.** One fire-and-forget `GET /healthz`, warn-never-block, silent on any failure. The bridge imposes **no** hard floor: against a server predating `c2affef` — which answered `400` for an unknown session id — the `404` path simply never fires and behaviour degrades to exactly today's, never worse. What keeps thin-transport skew safe is MCP's own runtime negotiation (tools via `tools/list`, protocol version in `initialize`), and staying transport-only is what preserves it.
- **Exact pin, never a floating tag, carried by release-please.** The existing prohibition (`claude-code-plugin/spec.md:279-281`) extends verbatim and gets sharper now that we own the package: with `@latest`, `npx` re-resolves on every session start, so an npm-account compromise is arbitrary code execution on every user machine at the next session start. The pin appears in the two client manifests, the in-memory opencode hook, the printed snippet, and the package's own `version`; executable invariants keep them equal. **Two mechanical unknowns block the manifest half and are verified before it is attempted, not after**: whether release-please can rewrite a pin embedded in a JSON `args` array (JSON carries no comments, and the `generic` updater is annotation-driven), and whether `npx` resolves at all under Codex's `Command::env_clear()` spawn semantics. Both have recorded fallbacks.
- **The source lives at `apps/plugin/mcp-bridge/` and becomes a real pnpm workspace member.** Inside `apps/plugin/` because release-please attributes a release by the paths of the commits under the component's `path` — the reason `.pi-plugin/` sits there (`pi-plugin/spec.md:448-450`). Unlike `.pi-plugin/`, it joins `pnpm-workspace.yaml::packages`: that exclusion was accepted for the untested extension surface, while this package needs workspace linting and executable recovery tests. Its runtime dependency surface remains empty.
- **Zero runtime dependencies, so the published tree is exactly one package.** The default in `supply-chain-hygiene` is zero, and this package keeps it rather than spending the exception. Not to be confused with bundling: vendoring a third-party package to report zero hides its version from a consumer's advisory tooling, which is precisely why confirming `mcp-remote`'s `404` behaviour meant reading `chunk-65X3S4HB.js` instead of a dependency tree. First-party code has no upstream version for tooling to miss. The risk taken on is that a future protocol revision must be implemented by hand rather than inherited from an SDK upgrade — bounded, because the `2026-07-28` revision removes sessions, the GET stream and server-initiated requests, making a proxy strictly simpler.
- **The A/B becomes a standing test.** With the source in-repo the whole chain — stdio client, bridge, and an HTTP server that terminates sessions — runs in-process under vitest with no `npx` and no network, so the 2026-08-15 experiment stops being something somebody once ran.
- **Consulting change, non-blocking: the conformance fix goes upstream to `geelen/mcp-remote` as a PR referencing #106.** It implements a spec MUST and is the only path by which `@rembric/mcp-bridge` could ever be retired.
- **BREAKING**: none at any wire, on-disk or user-configuration surface. No server change, no migration, no schema change, no derived-data invalidation (`memory_fts`, `memory_vec` and the entity tables are untouched). The four load-bearing invariants — append-only memory, scope enforced at the service layer, `topic_key` convergence, fresh-context judgment — are not in this change's path: the bridge handles transport frames and never inspects tool payloads. Existing opencode installs keep working through the measured config hook; Claude Code and Codex manifests are replaced by the ordinary plugin update. The user-visible changes are that a call which used to hang now succeeds, and that `clientInfo.name` reaching the server becomes the host's real name.

## Capabilities

### New Capabilities

- `mcp-bridge` — the `@rembric/mcp-bridge` package as the whole client-side piece: where it lives and why, its workspace membership, its zero-argument environment contract (`REMBRIC_SERVER_URL`, `REMBRIC_API_TOKEN`, optional `REMBRIC_PROJECT_SLUG`), project-directory and `.rembric` slug resolution with its fallbacks, URL building and the stderr diagnostics, the advisory `/healthz` version warning as a single implementation, the zero-dependency raw message pipe, verbatim passthrough of the host's `initialize` and `clientInfo`, the session-terminated recovery semantics in full (404-only, once, handshake-only replay, and what is deliberately **not** restored), the absence of any hard server-version gate, the exact-pinned package launch, the `npx` resolution guarantee, and the non-goals: no OAuth, no general-purpose ambitions, and a compatibility matrix bounded to this server × the stdio clients — with Codex and Windows recorded as unverified, each with its reason.

### Modified Capabilities

- `claude-code-plugin` — `## MCP server declaration` switches to the exact-pinned `npx` package command; `## MCP bridge contract` (`:33`–`:42`) is re-homed in `mcp-bridge`; and the pin requirement (`:279`–`:315`) becomes a manifest-pinning requirement while its `/healthz` advisory moves with the bridge.
- `codex-distribution` — now needs its own delta rather than inheriting silently: its Codex-specific MCP requirement switches from the plugin-cache launcher to an exact-pinned `npx` package command, retains `env_vars`/`PWD`, and records the `PATH` resolution check required by Codex's `Command::env_clear()` semantics.
- `opencode-plugin` — owns three things this change moves: the canonical location of `rembric-dotenv.mjs` and its single-implementation invariant (`:38`–`:56`), the measured in-memory config hook, and the install script's fetch/copy list. New installs print the `npx` form; existing launcher configs are upgraded by the hook without rewriting user files.
- `hermes-agent-plugin` — the README config block this capability requires (`:298`, `:319`) documents `npx -y mcp-remote@latest` (`apps/plugin/.hermes-plugin/README.md:62`): the defective package, a floating tag, a bearer in `args`, and a stale `plugin/bin/` path. It becomes the pinned `@rembric/mcp-bridge` with everything in `env`. Hermes is also the reason the bridge honours `REMBRIC_PROJECT_SLUG` as a fallback: its slug cascade (`:423`–`:434`) already defines that precedence, and with no URL argument the env var is how a Hermes user expresses a default slug.
- `plugin-session-protocol` — `:565`–`:575` states the "one JS/TS implementation" contract over one set ("every JS/TS client"), while its invariant test scans `apps/plugin/*.mjs` as a git pathspec (`*` matches `/`) and therefore now reaches the bridge. The delta separates the two halves, which must apply to different sets: **no second definition** covers every scanned file including non-clients; **must import the core** covers clients only — requiring a transport to import session-protocol code would be worse than useless.
- `pi-plugin` — its shared-parser requirement is amended so the Pi extension imports the canonical dotenv module from `apps/plugin/mcp-bridge/`, while all published scenarios and the no-local-copy contract remain intact.
- `development-environment` — its lint/test requirement is amended so the real bridge workspace is explicitly linted and its tests are explicitly included by Vitest; the deleted `bin/rembric-bridge.mjs` is removed from the live shipped-bridge lint requirement without weakening the existing root-command, coverage, or installer guarantees.
- `open-source-distribution` — the `plugin` component's `extra-files` carriers are enumerated exhaustively (`:271`, `:273`) and the release-identity requirement enumerates the surfaces the version must agree with (`:121`). The bridge package and its two manifest pin sites join; the measured opencode hook and printed snippet are checked by the executable pin invariant. npm becomes a second published-package surface. "Exactly two packages" and "exactly two manifest entries" stay verbatim true.

**Docs carrying the old transport** — `apps/plugin/README.md:185,187`; `apps/plugin/.opencode-plugin/README.md:99`; `apps/plugin/.hermes-plugin/README.md:62,73`; `docs/agents.md:246,370,520`.

**Invariant tests to update** — `apps/server/src/test/invariants.test.ts`: `REMBRIC_DOTENV_MJS`/`REMBRIC_BRIDGE_MJS` are hard-coded constants asserted to be in the scanned set (`:814`–`:816`, `:914`–`:916`), so the move reds them by design; the published-package block is written around the single constant `PI_PACKAGE_JSON` (`:988`–`:1042`) and must cover both packages; the shared-helper scan (`:878`–`:986`) now reaches the bridge, whose sources must not redefine anything `rembric-plugin-core.mjs` owns — `diag` and `truncate` are the live collisions.

Each needs its own change.
