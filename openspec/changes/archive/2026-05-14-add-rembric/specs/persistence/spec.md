## ADDED Requirements

### Requirement: The data store MUST be SQLite with extensions

The server SHALL use a single SQLite database file (default `~/.rembric/data.db`, override via `REMBRIC_DATA_DIR`) opened via `better-sqlite3`, with the `sqlite-vec` extension loaded and FTS5 enabled. WAL journal mode SHALL be enabled at initialization.

#### Scenario: Cold start with missing data dir
- **GIVEN** `REMBRIC_DATA_DIR` points at a path that does not exist
- **WHEN** the server starts
- **THEN** the server SHALL create the directory with mode 0700, create the DB file, load `sqlite-vec`, enable WAL, and apply all pending migrations

#### Scenario: sqlite-vec failed to load
- **WHEN** the server is started and `sqlite-vec` cannot be loaded
- **THEN** the server SHALL exit with a non-zero code and a clear error message instructing the operator about installation requirements

### Requirement: The schema MUST be managed by Drizzle ORM

All table definitions SHALL live as TypeScript files under `src/db/schema/`. Migrations SHALL be generated by `drizzle-kit generate` and applied by the server on startup. Hand-written raw-SQL migrations SHALL be permitted for FTS5 and sqlite-vec virtual-table setup; these SHALL live in `src/db/migrations/` alongside the generated migrations.

#### Scenario: A schema field is renamed
- **WHEN** a contributor renames a column in `src/db/schema/memory.ts`
- **THEN** running `drizzle-kit generate` SHALL produce a new migration capturing the rename, and the TypeScript compiler SHALL surface any consumer that references the old name

#### Scenario: Schema drift in CI
- **WHEN** the CI schema-drift test runs
- **THEN** it SHALL apply all migrations to a fresh DB, compare the resulting schema to the Drizzle definition, and fail if they differ

### Requirement: Migrations MUST be applied idempotently on startup

The server SHALL apply pending migrations on every startup. Re-running a migration that has already been applied SHALL be a no-op. The migrations runner SHALL hold an exclusive lock for the duration of migration application to prevent concurrent runners.

#### Scenario: Two servers start simultaneously against the same DB
- **WHEN** two processes attempt to start against the same data directory
- **THEN** only one SHALL acquire the migration lock; the other SHALL wait or exit with a clear error and SHALL NOT corrupt the schema

#### Scenario: Startup after all migrations applied
- **WHEN** the server starts and the migrations table indicates all migrations have been applied
- **THEN** the server SHALL skip migration application and proceed to serve traffic

### Requirement: FTS5 and sqlite-vec virtual tables MUST stay in sync with `memory`

`memory_fts` and `memory_vec` SHALL be maintained automatically as memories are inserted, updated, or transitioned. FTS5 sync SHALL be implemented via SQL triggers on the `memory` table; vector sync SHALL be performed by the embedding worker.

#### Scenario: Saving a memory updates FTS5 immediately
- **WHEN** a row is inserted into `memory`
- **THEN** a corresponding row SHALL exist in `memory_fts` with the indexed `content` and `tags` before the transaction commits

#### Scenario: Saving a memory with embeddings disabled
- **WHEN** `EMBEDDING_ENABLED = false` and a row is inserted into `memory`
- **THEN** `memory_vec` SHALL NOT receive a row for this memory, and consolidation candidate detection SHALL fall back to FTS5

### Requirement: The schema MUST encode the append-only contract

The schema SHALL declare `memory.content` immutable in convention and SHALL provide no UPDATE-capable code path for it. Status SHALL be an enum constrained at the application layer to `active | superseded | archived`. The `replaces` column SHALL be a JSON array.

#### Scenario: Schema review
- **WHEN** a code reviewer inspects `src/db/schema/memory.ts`
- **THEN** the schema SHALL clearly mark `content` as the immutable field and `status` as enum-restricted

### Requirement: The DB file MUST be portable and backup-friendly

The DB SHALL remain a single SQLite file (plus the transient WAL/SHM files) that can be backed up by stopping the server and copying the file, or by using SQLite's online backup API.

#### Scenario: Cold backup
- **GIVEN** the server is stopped
- **WHEN** the operator copies `data.db` to another location
- **THEN** the copy SHALL be a valid, openable SQLite database with no further steps required
