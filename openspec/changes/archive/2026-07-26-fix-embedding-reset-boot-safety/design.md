## Context

Two derived indexes carry an out-of-band recipe marker in the data dir: `memory_vec` with `embedding-state.json` (`embeddings/state.ts`) and the three entity tables with `entity-state.json` (`services/entity-state.ts`). Both markers exist because the in-database bookkeeping records THAT a row was processed, never under which recipe — so a recipe change has to be detected from outside the database and force a whole-index rebuild.

Both files were originally written in the same order: wipe the index, then record the new identity, with an unwrapped boot call. Commit fc6e2ff fixed that on the entity side after establishing the failure mode: on a full or read-only data dir the marker write throws after the wipe has committed, the boot aborts, and every restart repeats it. The embedding side was left as it was and is still that way in 0.24.13.

The embedding side is worse in two ways. The wipe is destructive of model inference (14–15 ms per memory, drained at 25 rows per 30 s tick — ~10 min to recover a 500-memory install, ~3.3 h at 10k) rather than of pattern matching (under 2 ms per memory). And `ensureVectorModel` runs at `bootstrap.ts:167`, before the `EmbeddingWorker` is constructed and before the listener binds — so when it throws, the process dies with `memory_vec` empty and no drain ever runs. The index does not degrade; it goes to zero and stays there until an operator frees disk.

Constraints in play: `memory_vec` is derived data regenerable from `memory` alone (which is what makes any wipe legitimate and any lost wipe recoverable); all SQL stays under `db/`; repositories never open transactions; there is no kv/settings table to hold state inside the database.

## Goals / Non-Goals

**Goals:**

- No reachable interleaving in which the vector index is empty while `embedding-state.json` asserts the current recipe.
- Marker maintenance can never abort the boot.
- A failed or interrupted reset converges on a later boot without operator action beyond restoring writability.
- Zero migration, zero schema change, and no behaviour change on the happy path.

**Non-Goals:**

- Relaxing the model-load fail-fast rule. A model that cannot load still aborts the boot with a non-zero exit (`memory` spec line 123). Only the identity marker becomes non-fatal.
- Making the drain faster, self-scheduling, or aware of the reset. The 30 s / 25-row shape is unchanged; how long a rebuild takes is not this change's problem.
- Moving recipe identity into the database.
- Fixing the analogous entity-side hazard (see D6).
- Any change to what triggers a reset. The two identity axes (`EMBEDDING_MODEL_ID`, `EMBEDDING_INPUT_VERSION`) and their comparison are untouched.

## Decisions

**D1 — Two-phase marker, not just marker-first ordering.**
`{modelId, inputVersion, pending: true}` is written before the wipe and flipped to `pending: false` after it commits; `readMarker` treats `pending: true` as a mismatch. Alternative considered and rejected: copy the entity side exactly (single write before the wipe, no `pending`). That prevents the boot-block and the destroy-on-every-retry loop, which is the severe half — but it converts the failure into the inverse hazard, the one `memory-entities/spec.md:241` names explicitly: "the recipe marker is already on disk by the time the wipe runs, so a partial wipe leaves the index inconsistent with a marker asserting it was rebuilt and nothing ever notices." The entity side mitigates that with an atomic wipe, which bounds _partial_ failure but not _total_ failure. Two-phase narrows the window to the durability layer rather than leaving it open at the program-order layer, costs one extra `writeFileSync` on the reset path only (never on the happy path, which still short-circuits on the first read), and needs no coordination between a file and a transaction. It does **not** eliminate the hazard outright, and an earlier draft claiming so was wrong: `writeMarker` never fsyncs and `db/client.ts:66` sets `synchronous = NORMAL`, so a host crash seconds after a reset can lose the `DELETE FROM memory_vec` commit while the kernel has already flushed the settled marker — leaving a matching marker over an old-recipe index. Closing that needs the flip fsynced after a `wal_checkpoint`, or the flip deferred until the drain reports completion. Out of scope here; the pre-fix code has the same exposure, so this change is no worse on that axis and strictly better on the boot-blocking one. It is a strict superset of the entity guarantee, which is why the entity requirement is left untouched rather than contradicted.

**D2 — The pending write is re-attempted on every boot, and it gates the wipe.**
The algorithm is uniform: on any mismatch — including a marker that already carries the right identity but `pending: true` — write the pending marker first, then wipe. This is what makes the residual failure bounded rather than periodic. If the data dir is persistently unwritable, the pending write throws _before_ `deleteAll()`, so the number of wipes performed is zero, not one per boot. The only path to a second wipe is a data dir that was unwritable at the flip and writable again later, which costs at most one extra full re-embed and then converges. Alternative considered: skip the wipe when the identity matches and only `pending` is true, on the theory that the wipe probably already happened. Rejected — it cannot distinguish "wipe never ran" from "wipe ran and the drain has since refilled", and guessing wrong the first way leaves old-recipe vectors in the index permanently, which is exactly the mixed-embedding-space state the `memory` spec forbids.

**D3 — `ensureVectorModel` returns `{wiped, markerWritten}` and does not throw for marker I/O; the call site is wrapped anyway.**
Two distinct facts need to reach the log: N vectors were wiped, and the marker did not persist. If the flip write throws out of the function, `wiped` is lost and the operator sees only a generic warning — while the drain is about to spend hours rebuilding. Returning the outcome keeps both loggable. The `try/catch` at the call site still goes in, mirroring `bootstrap.ts:200-206`, because `repos.vectors.count()` and `deleteAll()` can also throw (disk, corrupt vec table) and a boot must not die for that either; when it fires, the marker is still `pending: true`, so the next boot retries. Alternative considered: throw and let the wrapper handle everything uniformly. Rejected for the lost-`wiped` reason above.

**D4 — No `fsyncSync` on the marker.**
The marker is advisory, and every way of losing an unflushed write converges. Host crash losing the pending marker but not the wipe (WAL already fsynced): next boot sees the OLD identity, mismatches, writes pending, wipes an already-empty table, flips. Host crash losing the flip: next boot sees `pending: true`, retries. Neither state is wrong, only redundant, and the redundant work is a `DELETE` over an empty table. Alternative considered: `openSync` + `writeSync` + `fsyncSync` + `renameSync` for atomic durable replacement. Rejected — it buys nothing the retry does not already provide, and it adds a temp-file path to a boot step that must be as boring as possible.

**D5 — `pending` is optional and absent means `false`.**
A marker written by any shipped build has no `pending` field, and on an upgraded install it must keep matching so the upgrade performs no reset. This mirrors how the same file already handles the pre-v2 `inputVersion` absence, except in the opposite direction: absent `inputVersion` deliberately mismatches (it means "content-only recipe"), absent `pending` deliberately matches (it means "a build that had no interrupted-reset state to record"). Both defaults are correct and the asymmetry is intentional; it is the kind of thing worth one line of comment in `readMarker` and nothing more.

**D6 — The entity-side residual is named, not fixed here.**
`ensureEntityExtractor` writes the marker, then calls `resetEntityIndex` inside a transaction. If `truncateAll` fails _entirely_ — the transaction rolls back — `memory_entity_scan` stays populated under a marker asserting the new `EXTRACTOR_VERSION`, so the next boot returns `{reset: false}` and the entity index stays on the old recipe silently and forever. Real, and the same class as this defect, but the failure is silent-wrong rather than boot-blocking and the rebuild it costs is sub-2 ms per memory, so it is deferred on **scope**, not on spec cost. An earlier draft of this section claimed fixing it "means editing `memory-entities/spec.md:241`". That is false: two-phase preserves marker-before-wipe — the pending write still precedes the wipe — so `:241`'s premise and both mitigations it prescribes survive untouched. The active `tighten-entity-extraction-precision` change reaches the same conclusion independently (its D5: no requirement text needs modifying) and its `memory-entities` delta carries no marker requirement at all. The real blocker is that this change is implemented and smoke-verified while that one already owns `entity-state.ts`. Recorded in `tasks.md` under Deferred.

**D7 — The `persistence` scenario is corrected in passing.**
`persistence` spec line 95 says a model-identity mismatch ends with "the recorded identity updated on completion". That is untrue of what ships (the identity is recorded at reset time, long before the backfill finishes) and untrue of this change. Left as-is it reads as a contradiction of the new requirement, so it is restated to say the identity is recorded when the wipe commits, and that a matching marker means "no pre-change vectors remain", not "the backfill is finished". No behaviour depends on the correction; it exists so the two specs agree.

## Risks / Trade-offs

- [Risk] A transiently-unwritable data dir triggers one extra full re-embed (wipe → flip fails → writable again → wipe → flip). At 10k memories that is ~3.3 h of degraded dense recall, twice. → Mitigation: D2 bounds it to _one_ extra occurrence rather than one per boot, and the `markerWritten: false` log names the file so the operator can act before the second boot. Search keeps working throughout on the lexical branch, per the existing requirement.
- [Risk] `pending: true` widens what counts as a mismatch, so a bug in the flip write would silently convert every boot into a full re-embed. → Mitigation: the flip is the last statement on the reset path with nothing after it to fail; the happy path never reaches it (it returns on the first read); and the "matching marker is a no-op even with vectors present" test already in `state.test.ts` fails loudly if a normal boot starts wiping.
- [Trade-off, the load-bearing one] Not aborting the boot means the server can now serve dense search over an index that predates the running recipe. Pre-fix the process died before binding, so this state was unreachable; it is the availability-for-ranking-correctness trade this change makes. It bites only on the intersection of two conditions — the identity actually changed AND the marker is unwritable — but in that window `hybridSearch` fuses the dense branch by RANK (`fuseRRFWithScores`), not by cosine, so old-recipe neighbours occupy ranks 1..k and displace correct lexical hits, and the low cosine cannot even trigger abstention because it only loses a `Math.max`. → Mitigation: `memory.doctor` now warns explicitly when a reset is owed and rows exist. That warning is the whole point: without it `embeddings.backlog` reads 0 (every row HAS a vector, just the wrong one) and the doctor reports healthy, which is the same class of lie this change exists to remove. NOT mitigated: the results are still wrong until a boot settles the marker. Degrading to lexical-only while a reset is owed would fix that properly and is deliberately out of scope — it needs a runtime flag threaded into `hybridSearch`, which is a ranking change, not a boot-safety one.
- [Trade-off] The two markers now use different mechanisms — two-phase here, single-phase-plus-atomic-wipe on the entity side. → Accepted because the guarantees are ordered, not conflicting (D1), the cost asymmetry between the two indexes justifies the stronger one on the expensive index, and D6 records the convergence work rather than leaving the divergence unexplained. A reader of either file finds the other referenced.
- [Trade-off] A restored snapshot could carry `pending: true` and force a reset the operator did not ask for. → Accepted, and it is the safe direction: `persistence` spec line 747 already states that a MISSING marker is safe and a SURVIVING MATCHING marker is the trap. `pending: true` behaves like a missing marker, so this can only ever turn the documented trap into the documented safe case.

## Migration Plan

None required — no schema change, no migration file, no data transformation.

First boot after upgrade on a populated install: `embedding-state.json` exists with the current model id and input version and no `pending` field, so it reads as a match (D5), `ensureVectorModel` returns `{wiped: 0, markerWritten: true}` before touching the database, and nothing is rebuilt. An install whose marker is absent or genuinely stale performs exactly the reset it would have performed before, now with the pending write in front of it.

Derived-data invalidation: none. `memory_fts`, `memory_vec` and the three entity tables are untouched by the upgrade itself.

Rollback: safe in both directions. An older build reading a marker with `pending: false` ignores the unknown field (`readMarker` only inspects `modelId` and `inputVersion`) and treats it as a match. An older build reading `pending: true` also treats it as a match — which is the pre-fix behaviour, i.e. it may skip a reset the newer build would have retried, leaving mixed embedding spaces until the next identity change. That is a downgrade hazard, not an upgrade one, and it is bounded to installs that were mid-interrupted-reset at the moment of the downgrade.

## Open Questions

- Whether the `markerWritten: false` case should also surface on the dashboard maintenance view rather than only in the boot log. It is the one failure this change deliberately makes non-fatal, and a warning that scrolled past in `docker compose logs` is easy to miss. Default taken: log only, because every other boot-time degradation in this server is log-only and adding a first dashboard surface for one of them is a wider decision than this fix. Worth revisiting if the diagnostics view grows a general "boot warnings" panel.
