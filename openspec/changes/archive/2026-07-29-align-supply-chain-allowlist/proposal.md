## Why

`.npmrc::ignore-scripts=true` makes lifecycle-script execution default-deny, so `pnpm-workspace.yaml::allowBuilds` is the repo's entire install-time code-execution surface. A reader auditing that surface from the published contract is currently told the wrong number.

**Measured.** `pnpm-workspace.yaml:14-21` declares **seven** entries — four `true` (`husky`, `better-sqlite3`, `sqlite-vec`, `onnxruntime-node`) and three `false` (`esbuild`, `sharp`, `protobufjs`). `openspec/specs/supply-chain-hygiene/spec.md:13` publishes **four** ("The current allowlist values are: `husky: true`, `better-sqlite3: true`, `sqlite-vec: true`, `esbuild: false`"), omitting all three added later. The number that matters is the `true` count: **3 published against 4 actual**, and the omitted one — `onnxruntime-node`, pulled by `@huggingface/transformers` — is the largest native dependency in the tree and the newest grant of arbitrary install-time code execution on every contributor workstation and CI runner. An auditor reading the spec concludes the blast radius is a git-hook installer plus two small SQLite bindings.

**A second published spec is not merely incomplete but false.** `openspec/specs/development-environment/spec.md:295` enumerates the same three and then asserts normatively: "These three are the only third-party lifecycle scripts the repo permits to run." Four are. Its scenario at `:306` states "**AND** only the lifecycle scripts of `husky`, `better-sqlite3`, and `sqlite-vec` SHALL execute" — a fully checkable THEN clause that the shipped repo **fails today**. This is the failure mode `CLAUDE.md` warns about directly: a spec that overclaims is worse than a missing one, because the code silently disagrees with the contract.

**Six stale statements of one fact, across four tracked files, none of which any rule compares to the file:**

| location                                             | claim                                                                   | reality                                |
| ---------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------- |
| `openspec/specs/supply-chain-hygiene/spec.md:13`     | 4 entries, 3 `true`                                                     | 7 entries, 4 `true`                    |
| `openspec/specs/development-environment/spec.md:295` | 3 `true` + "These three are the only"                                   | 4 `true`                               |
| `openspec/specs/development-environment/spec.md:306` | scenario: "only … `husky`, `better-sqlite3`, `sqlite-vec`"              | `onnxruntime-node` also runs           |
| `openspec/specs/development-environment/spec.md:270` | requirement header names the `onlyBuiltDependencies` allowlist          | pnpm 11 replaced it with `allowBuilds` |
| `CONTRIBUTING.md:17`, `:153-155`                     | "one of three packages", "the three set to `true`"                      | four                                   |
| `.npmrc:2`                                           | "Exceptions are declared in pnpm-workspace.yaml::onlyBuiltDependencies" | key is `allowBuilds`                   |

**The process was not bypassed — the enumeration rotted anyway, and that is the whole point.** The three entries landed in `70a0915` (`feat(server)!: in-process embeddings`, PR #99, 2026-06-05) under a full OpenSpec change: `archive/2026-06-05-embed-embeddings-in-process/tasks.md:7` consulted `.agents/skills/npm-security-best-practices/` and named the `allowBuilds` addition explicitly; `design.md:87` recorded the native-dependency risk; `proposal.md:34` restated it. Every governance requirement in `supply-chain-hygiene` was satisfied. What the change did not carry was a `supply-chain-hygiene` delta spec — and nothing anywhere compares the prose count to the file, so the divergence was invisible. **54 days and 42 `server-v*` releases (plus 16 `plugin-v*`) have shipped since, every one of them publishing the wrong surface.**

**No existing gate can see this.** `scripts/check-spec-provenance.mjs` (landed `2026-07-28-enforce-spec-archive-provenance`) enforces exactly one direction: a published-spec edit must be paired with an archive arrival. The reverse — a config edit that should have forced a spec edit — is outside its predicate by construction, and its own design (D10) states out loud that it enforces provenance, not truth. `openspec validate --all` is structural and passes both specs today. `apps/server/src/test/invariants.test.ts` reads `pnpm-lock.yaml` for nothing and `pnpm-workspace.yaml` not at all.

Re-typing seven entries into two specs restores accuracy for exactly as long as the tree stands still. The next native binding resets the clock.

## What Changes

- **Both published specs stop enumerating the allowlist.** Membership is stated once, in `pnpm-workspace.yaml::allowBuilds`, where each entry already carries its justification as a trailing comment. The specs state the _property_ — default-deny, exceptions single-sourced, each exception justified in place, membership test-pinned — and name the file as the sole enumeration. Rejected: re-typing seven entries into two specs, which leaves the mechanism intact. The history argues against it — the `development-environment` enumeration arrived with `2026-05-18-harden-npm-supply-chain`, the `supply-chain-hygiene` one with `2026-05-22-add-dependabot-and-engine-strict`, and `2026-05-20-restructure-monorepo-apps-layout` went to the trouble of requiring the block "remain in place verbatim" (`specs/development-environment/spec.md:5`, `tasks.md:7.1`). Careful custody of the copies did not stop them rotting two weeks later.
- **Add a pinned inventory + assertion**, following the `apps/server/src/test/schema-inventory.ts` idiom created for precisely this failure (two hand-maintained inventories drifted inside one branch): `apps/server/src/test/supply-chain-inventory.ts` holds the expected `true` set, and `invariants.test.ts` parses `pnpm-workspace.yaml` and fails when the two disagree. Adding a `true` entry therefore cannot land silently — it reds `pnpm test` until the author edits a tracked, reviewable constant whose failure message points at `supply-chain-hygiene`. This converts the existing "adding a `true` entry is a security-relevant decision" prose from an honour system into a gate.
- **Pin the `true` set exactly; do not pin `false` membership.** A `false` entry is an explicit _deny_ — strictly safer than absence, and pnpm surfaces newly-flagged transitives over time, so forcing a test edit per deny is friction with no security value. Asymmetry argued in design D2.
- **Require every entry to carry a non-empty trailing justification comment**, `true` and `false` alike, asserted by the same test. This is the thing a reader actually needs and a bare list never gives: _why_ does this package need to run code at install. All seven already have one, so the assertion passes on landing and holds thereafter.
- **Detect dead exception surface**: every `true` entry must resolve to a package present in `pnpm-lock.yaml`. An exception kept after its dependency leaves grants nothing today and silently re-grants execution if the package returns as a transitive. **Honest measurement: 7 of 7 entries are present in the lockfile today, so this check finds nothing on landing** — it exists to make a future removal visible rather than to fix a current defect.
- **Fail closed on an unparseable `allowBuilds` block.** The `SHADOWS` lesson in `schema-inventory.ts:88-95` (a prefix rule silently swallowed an unclassified table) applies: a line the scanner cannot classify is an error, never a skip.
- **Fix the three non-spec copies in the same change**: `CONTRIBUTING.md:17` and `:153-155` stop counting and point at the file; `.npmrc:2` names `allowBuilds` instead of the retired `onlyBuiltDependencies`. `CLAUDE.md:76` also claims "lockfile-lint in CI", which `supply-chain-hygiene` explicitly forbids as a substitute (it cannot parse `pnpm-lock.yaml`) and which `.github/workflows/ci.yml` does not run — corrected in the same pass since it is the same paragraph and the same drift class.
- **Not in scope**: changing `allowBuilds` itself. No entry is added, removed, or flipped. Whether `sharp: false` and `protobufjs: false` still need to be listed at all is a dependency question, not a documentation one, and is deferred below rather than settled here.

## Capabilities

### New Capabilities

_None._ A `supply-chain-hygiene` capability already exists and owns the dependency threat model; `development-environment` owns the repo's file-shape and CI-gate requirements. Both are amended in place.

### Modified Capabilities

- `supply-chain-hygiene`: **MODIFIED** the default-deny requirement — the inline enumeration (`husky: true`, `better-sqlite3: true`, `sqlite-vec: true`, `esbuild: false`) is replaced by a single-source rule naming `pnpm-workspace.yaml::allowBuilds` and requiring a justification per entry. **ADDED** one requirement — the allowlist's `true` membership MUST be pinned by an executable inventory that fails on unreviewed change.
- `development-environment`: **MODIFIED** the `.npmrc`/`allowBuilds` requirement — drops the false "These three are the only third-party lifecycle scripts the repo permits to run" and the enumeration, and repairs the scenario THEN clause the repo currently fails. **RENAMED** the `packageManager` requirement header to name `allowBuilds` rather than the retired pnpm 10 `onlyBuiltDependencies`.

## Impact

- **New**: `apps/server/src/test/supply-chain-inventory.ts` (the pinned `true` set, the `allowBuilds` block parser, the source reader, and the violation checks — sibling to `schema-inventory.ts`) and `apps/server/src/test/supply-chain-inventory.test.ts` (the parser's unit cases plus every negative case, driven against mutated in-memory copies of the real files).
- **Modified**: `apps/server/src/test/invariants.test.ts` (one describe block asserting the working tree has no violations: inventory equality both directions, justification-comment presence, lockfile resolution of each `true` entry, the `allowBuilds` key-name rule, `.npmrc::ignore-scripts=true`, and the two image-build channels below), `CONTRIBUTING.md`, `.npmrc` (comment only — the `ignore-scripts=true` directive is untouched), `CLAUDE.md`, and at archive time only `openspec/specs/{supply-chain-hygiene,development-environment}/spec.md`.
- **Added during apply, after a review found the gate one file short of its own policy**: the `development-environment` requirement gains the image-build channels. `apps/server/Dockerfile` is _read_ (not modified) so the assertion can check that every stage running `pnpm install` COPYs `.npmrc` first, and that `pnpm rebuild`'s explicit argument list is a subset of the pinned `true` set. The second is the more load-bearing of the two: `pnpm rebuild <pkg…>` executes lifecycle scripts regardless of `allowBuilds`, and the repo's invocation runs from `/prod-out`, outside the `WORKDIR` holding the copied `.npmrc`, so nothing constrained it before. Today's arguments (`better-sqlite3`, `sqlite-vec`, `onnxruntime-node`) are all pinned, so this finds nothing on landing — it closes the path by which a fourth name could have been added with no allowlist entry and no failing test. This also replaced a clause the requirement had been re-publishing falsely: `runtime` is distroless and runs no `pnpm install` at all.
- **Unchanged, deliberately**: `pnpm-workspace.yaml`, `pnpm-lock.yaml`, `package.json`, `.github/workflows/ci.yml`, `apps/server/Dockerfile`. No dependency is added, removed, or bumped, so the `npm-security-best-practices` skill's dependency-addition path (practices #7, #14, #15, #16) is consulted and produces no action; its practice #1 is the requirement being restated. `.npmrc` is edited, which is why the skill was consulted before any edit per `CLAUDE.md`.
- **No load-bearing invariant crossed**: no migration, no schema change, no new MCP tool, no SQL, no plugin-tree file, no dashboard token, no runtime code at all. Existing installations carry no state this change touches — nothing to migrate, no derived table (`memory_fts`, `memory_vec`, `memory_entities`, `memory_entity_links`, `memory_entity_scan`) to invalidate, first boot after upgrade is indistinguishable, and rollback is deleting a test file.
- **Deliberately deferred, so it is not silently lost**: (a) whether `sharp: false` and `protobufjs: false` are still needed as explicit denies — a dependency-tree question requiring a `pnpm install` observation of what pnpm actually flags, not a spec edit; (b) a diff-scoped CI gate that reds a `pnpm-workspace.yaml` change carrying no `supply-chain-hygiene` delta — the natural inverse of `check-spec-provenance.mjs`, rejected here because the working-tree assertion closes the same hole with no base-ref resolution (design D4); (c) extending the pinned-inventory idiom to `minimumReleaseAge`, `blockExoticSubdeps` and `minimumReleaseAgeExclude`, which are single scalars the specs quote correctly today and which have not drifted.
