## Why

`session_summary_versions` exists to make one specific failure recoverable, and the sibling change `refine-session-summary-writes` removes that failure at its source. Keeping the table after that is paying for a net under a hazard that no longer falls the same way.

**What the table was for, in its own words.** `2026-08-13-session-summary-full-rewrite` introduced it because a curated write replaced the whole document and nothing could put the displaced text back — `proposal.md:15`: _"This is what makes the replace recoverable: the text that was displaced is still a row, which is the only recovery mechanism this repo has."_ The premise of that sentence is whole-document replacement.

**The premise is what the sibling change spends.** `refine-session-summary-writes` makes an absent `##` section mean "unchanged" (`specs/sessions/spec.md`, "A curated session-summary write MUST be merged section-wise with the stored summary"), and refuses a curated write carrying no `##` heading against a sectioned stored summary. After it, a section cannot vanish by being forgotten, and the degenerate write — one flat paragraph replacing six sections — is rejected outright rather than stored. **Recoverability stops coming from a historical copy and comes from preservation by omission.** That is the argument this change substitutes wherever a published requirement currently rests on the version rows.

**Nothing on a recall path reads the table.** Verified by enumeration on this tree, not by reading intent:

- `memory.context` reads the `sessions.summary` column and nothing else; there is no version read anywhere in `apps/server/src/mcp/memory-tools.ts`.
- The only two readers are `apps/server/src/dashboard/sessions.ts:323,327` (the operator's `SUMMARY HISTORY` section) and `apps/server/src/mcp/session-tools.ts:420`, reached only when `memory.session_get` is called with an explicit positive `limit` — a surface the `sessions` capability itself already calls EXCEPTIONAL (`openspec/specs/sessions/spec.md:772`).
- `db/diagnostics.ts` and `dashboard/maintenance.ts` do not name the table. It is not in the startup shrink guard's operator-visible set.

**What it costs to keep.** One table and its migration; five repository methods (`insertSummaryVersion`, `latestSummaryVersion`, `adminListSummaryVersions`, `adminCountSummaryVersions`, `listSummaryVersionsInScope`, `apps/server/src/db/repositories/agent-sessions-repository.ts:380-453`); a service transaction wrapper, `updateAndVersion` (`apps/server/src/services/agent-sessions.ts:298-321`), that exists only to make the append atomic and collapses to a bare `updateById` without it; a `limit` argument on `memory.session_get` with its own bound, its own zod `describe()` and its own published `mcp-api` requirement; a dashboard section with 28 lines of dedicated CSS; two whole test files (`migrations-0033.test.ts`, 188 lines; `dashboard/session-summary-history.test.ts`, 168 lines); four invariant grep rules; and two published requirements in `sessions` plus rationale weight in `dashboard`, `data-access`, `mcp-api`, `persistence` and `plugin-session-protocol`.

## What Changes

- **The table is dropped by a new migration, and `0033_session_summary_versions.sql` STAYS on disk.** The runner iterates the files present in the directory and skips those recorded in `_migrations` (`apps/server/src/db/migrate.ts:95-110`), so deleting an already-applied migration is silently tolerated on an upgraded install and silently divergent on a fresh one — the two would end with different `_migrations` contents. The repo already has the create-then-drop precedent in `0011_summary_length_check.sql` / `0012_drop_summary_length_check.sql`, and `migrations.test.ts` pins the filename list. The new migration is one `DROP TABLE`: `session_summary_versions` is a CHILD of `sessions`, never a parent, so the table-rebuild dance is not involved, and the runner's standing `PRAGMA foreign_keys = OFF` → `BEGIN IMMEDIATE` → body → `PRAGMA foreign_key_check` → `COMMIT` sequence applies unchanged with no pragma of its own.
- **BREAKING for stored history: every existing version row is destroyed, irreversibly.** This is the whole point of the change and it is not recoverable by any mechanism this repo has — `consolidation_ops` records identifiers, never payloads. Rejected: renaming the table to a `_retired` suffix (keeps the storage, which is the thing being retired, and pins it in the schema inventory forever) and exporting the rows to a file first (a new operator surface, a new format, and a promise to read it back that nothing would honour).
- **`memory.session_get` loses its `limit` argument, and that is a hard-error migration note, not a silent one.** MCP tool input schemas here are strict — `mcp-api`, "Every MCP tool input schema MUST refuse an unknown property rather than ignore it" (`openspec/specs/mcp-api/spec.md:2682`) — so a model still carrying the old description and sending `limit` is REFUSED with the transport's invalid-parameters error rather than having the property dropped. The blast radius is bounded: no shipped client sends `limit` (it is a model-facing argument only, and the description already calls it exceptional), and the refusal names the tool and the property, which is the behaviour that requirement exists to produce. Nothing else about `memory.session_get` moves.
- **`updateAndVersion` collapses into `updateById` at all three call sites** (`apps/server/src/services/agent-sessions.ts:276`, `:371`, `:422`). A `db.transaction()` wrapping one statement is not a transaction anyone needs; the service's other transaction (`purgeEmpty`, `:727`) keeps the `TransactionRunner` dependency alive.
- **The dashboard's `SUMMARY HISTORY` section goes, with its CSS and its test file.** Its own published rationale is conditional on the table: `dashboard/spec.md:1583` — _"Without a reader the table is storage nobody consumes."_ With no table there is nothing to read, so the requirement is removed rather than rewritten.
- **Three published requirements in `plugin-session-protocol` are re-argued, not just de-referenced.** Each currently justifies an obligation with the version rows; each gets the preservation-by-omission argument in its place, and where that argument does not reach as far as the old one, the requirement says so instead of overclaiming. This is the substantial part of the change and it is detailed in `design.md` D4–D6.
- **ACCEPTED RISK, stated by the owner and recorded here so it is not discovered later: a clobber INSIDE a section stops being recoverable.** The sibling change protects a section the write omits; it does not protect a section the write carries. A curated write sending `## Accomplished` with one line, against a stored `## Accomplished` of ~640 characters, replaces that section outright and leaves no copy of what was there. Condensing a section is legitimate and is exactly what the sibling change asks for at a 10 000-character cap; substituting a thin line for a dense one is loss, and the server cannot tell them apart without content analysis it deliberately does not do. **The owner accepts this knowingly.** No guard is added here — a shrink guard was already rejected on the record in `2026-08-13-session-summary-full-rewrite` because a correct summary legitimately shrinks, and the sibling change re-rejected it.
- **Sequencing is a hard dependency, in three directions.** This change MUST archive after `refine-session-summary-writes`: its delta text is authored against that change's post-archive spec state (it modifies a requirement that change ADDs, and re-modifies a scenario that change already touches). `measure-summary-clobbering` phase 1 — which reads versions 14 and 15 of a real session out of the operator's deployment — was to be captured before this change reached that deployment; **that change was discarded unstarted, the capture never happened, and the only remaining protection for those rows is the operator's pre-upgrade `sqlite3 .backup`.** And `server-gated-session-nudges`, though it correctly rests no BEHAVIOUR on the table, carries three textual references that this change would leave dangling (a **One site** cross-reference and two version-row mentions in its `sessions` / `session-nudges` deltas); whichever of the two archives second repoints them. None of the three is a code coupling; all three are ordering facts that are cheap to honour and expensive to notice afterwards.
- **Out of scope, deliberately.** The write contract itself (`refine-session-summary-writes` owns it) and the nudge system (its own change). **No new table and no new column** — the anchor-retention instrument in `measure-summary-clobbering` is a separate change with its own storage, and this change neither depends on it nor blocks it.

## Capabilities

### New Capabilities

None. This change removes behaviour and re-argues the requirements that leaned on it.

### Modified Capabilities

- `sessions` — REMOVES both version-row requirements ("Every curated session-summary write MUST append a version row in the same transaction" and "`session_summary_versions` rows MUST be append-only, and removable only with their session"); MODIFIES "`memory.session_get` returns a session's full summary by id" (drops `limit`, `SESSION_GET_VERSIONS_MAX` and the three version scenarios), "A session summary MUST follow the documented structure" (the last-final-wins scenario stops promising a recoverable version row and names the accepted risk at its exact locus), and the sibling change's "A curated session-summary write MUST be merged section-wise with the stored summary" (its **One site** cross-reference repoints to "Terminal session rows MUST accept late summary and title writes…", which publishes that property independently at `openspec/specs/sessions/spec.md:1029`).
- `dashboard` — REMOVES "The session detail view MUST list the summary version history, capped".
- `persistence` — REMOVES "Migration `0033_session_summary_versions.sql` MUST create the summary-version table additively, with no backfill"; ADDS the drop-migration requirement (one `DROP TABLE`, no rebuild, `0033` retained on disk with the reason, the irreversibility of the row loss, and what a downgrade does).
- `data-access` — MODIFIES "Repositories per aggregate own all SQL for their tables" (the `agent-sessions` aggregate stops owning a second table; the write-ordering paragraph and the summary-version SQL-confinement scenario go with it).
- `mcp-api` — REMOVES "The `memory.session_get` description MUST disambiguate `limit` and mark the read exceptional". The `memory.session_summary` description requirement needs no edit from this change: the sibling change already rewrites its `idempotentHint` paragraph without a version-row clause.
- `plugin-session-protocol` — RENAMES and MODIFIES "Every client with a compaction event MUST inject the read-then-rewrite directive, and where no such event exists the version history MUST be the accepted mitigation" (the title itself names the retired mechanism); MODIFIES "A process that resumes a pre-existing session SHALL be told ONCE that a stored summary may exist" (`:671`) and "Sessions MUST converge on a non-null summary when the agent cooperates OR the transcript is reachable" (`:107`). **A fourth MODIFY, of "The summary reminder MUST be delivered at the end of the turn…" (`:866`), was dropped at archive time**: `server-gated-session-nudges` archived first and retired that requirement outright, replacing it with "Every client's end-of-turn handler MUST report the turn exactly once and MUST NOT emit on the host's end-of-turn channel", which carries no version-row clause for this change to repoint. Keeping the block would have ADDED a duplicate requirement asserting the very end-of-turn emission the published one forbids.
- `session-nudges` — MODIFIES "The session-summary reminder MUST be gated on the server by three timestamps, never by a turn counter". Added at archive time for one repoint: its `last_summary_at` bullet cites the removed version-row requirement's **One site** clause, which now points at "Terminal session rows MUST accept late summary and title writes, and MUST NOT change status except through `resume`" — the requirement that publishes that property independently. The capability did not exist when this change was proposed.
- `mcp-api` — also RENAMES "The `instructions` block MUST state that a curated summary write replaces the stored value" to "…MUST state what a curated summary write replaces and what it keeps". Title-only; the body already taught the merge and explicitly warned that the replacing half alone is the wrong reading.

New co-located `apps/server/src/db/migrations-00NN.test.ts`; `apps/server/src/db/migrations-0033.test.ts` deleted (two of its five tests drive `AgentSessionsService` and `adminListSummaryVersions`, so it cannot survive as a checkpoint pin). `apps/server/src/db/migrations.test.ts` filename fixtures at `:632` and `:1110` gain the new entry.

**Schema / data layer.** `apps/server/src/db/schema/agent-sessions.ts` — the `sessionSummaryVersions` table, its doc comment (from `:110`) and the `SessionSummaryVersion` / `NewSessionSummaryVersion` types (`:143-144`). `apps/server/src/db/repositories/agent-sessions-repository.ts:380-453` — five methods and their imports. `apps/server/src/db/repositories/agent-sessions-repository.test.ts` — the fixture insert at `:174` and the three describe blocks at `:206`, `:218`, `:225`.

**MCP.** `apps/server/src/mcp/session-tools.ts` — `SESSION_GET_VERSIONS_MAX` (`:54`), the `limit` field of `sessionGetSchema` (`:58-66`) and the `versions` branch of the handler (`:416-426`, plus the `...(versions !== undefined && { versions })` spread in the response object). `apps/server/src/mcp/server.ts` — the import at `:73` and the `memory.session_get` description at `:360`. `apps/server/src/test/mcp-integration.test.ts:22,2428`.

**Tests and inventories.** `apps/server/src/test/invariants.test.ts:155-176` — four forbidden-pattern rules. `apps/server/src/test/schema-inventory.ts:30` — the `SOURCE_TABLES` entry (verified safe for `migrations-0031.test.ts`'s census, which filters to tables present at that checkpoint). `apps/server/src/test/schema-drift.test.ts:163-166,233` — the named unique index and the autoindex. `apps/server/src/scripts/seed-dev.ts:311-322` — the deliberate draft curation whose only purpose is to give the history section a second row; `apps/server/src/scripts/seed-dev.test.ts:80-111` — the two-versions test.

**Plugin.** No plugin file changes. No protocol field, no HTTP contract change, no per-client behaviour, no shared-resource duplication risk. Release consequence: a `server` bump only.

**Existing installations.** The migration is one `DROP TABLE` on a populated file and is backward-safe for every other table — `sessions.summary` is untouched, and `PRAGMA foreign_key_check` is clean before `COMMIT` because the dropped table is a child, not a parent. On first boot after upgrade the table is gone; the dashboard session detail page renders without the history section; a `memory.session_get` call carrying `limit` is refused by input validation. No derived data is invalidated: `memory_fts`, `memory_fts_vocab`, `prompts_fts`, `memory_replaces`, `memory_vec` and the three entity tables all derive from `memory` / `prompts` and are untouched. The startup shrink guard's operator-visible set (`memory`, `projects`, `sessions`, `tokens`, `prompts`) does not include the dropped table, so it cannot trip.

**Rollback BREAKS, and this is the one place it does.** Running a pre-drop image against a post-drop file leaves `_migrations` carrying the drop and the table absent, so the older code's `INSERT INTO session_summary_versions` fails and takes the whole curated-write transaction with it — `memory.session_summary` stops working, and the dashboard session detail page 500s on its history read. Recovery is to roll forward, or to recreate the table by hand from the `0033` DDL (still on disk, empty). Stated as a scenario in the `persistence` delta rather than left to be found.

**Invariants.** Append-only memory: untouched — no `memory` row is written or deleted, and the two allow-listed physical-purge `DELETE`s are unchanged. The append-only pins this change removes are the four covering `session_summary_versions` itself; the `memory`, `sessions`, `prompts` and `memory_relations` pins in the same family stay exactly as they are. Scope at the service layer: untouched — the one scoped read being removed (`listSummaryVersionsInScope`) is deleted, never widened. SQL confined to `db/`: preserved — every statement removed is inside `db/repositories/`, and no new statement is added outside it.
