## Why

The Pi coding-agent harness (`pi.dev`, `@earendil-works/pi-coding-agent`) cannot reach Rembric at all, and nothing already in the tree can be pointed at it. Every existing client gets its tools through `apps/plugin/bin/rembric-bridge.mjs`, a stdio↔HTTP MCP proxy that presupposes a host which speaks MCP. Pi does not: its own documentation states, verbatim at `packages/coding-agent/docs/usage.md:303` of the harness repository, _"It intentionally does not include built-in MCP…"_. So the bridge is not merely inconvenient there — it has no consumer. **Measured at HEAD: the server registers 23 MCP tools (`apps/server/src/mcp/server.ts`, 23 `registerTool` call sites, `:211`–`:501`); zero of them are reachable from this harness today.**

The gap is closable at unusually low cost, and that was verified rather than assumed. Against **Pi 0.84.1** and the real MCP server started in-process over a temporary SQLite file, a prototype extension performed the full round trip: `tools/list` → 23 tools → `pi.registerTool` × 23 → a proxied `memory.save` returning `isError=false` → **a row confirmed present in the database by an independent `memory.get`**, with a discriminating control (`memory.get` on a fabricated id) returning `not_found`. The registration path needs no per-tool code: the extension enumerates at runtime and proxies `execute` → `tools/call`, so the tool surface is described in exactly one place — the server — and **the plugin duplicates none of it**. The 23 real `inputSchema` objects use only `$schema additionalProperties description enum items maxItems maxLength maximum minItems minLength minimum properties required type` — **zero** `$ref`/`definitions`/`anyOf`/`oneOf`/`allOf`/`format`/`default` — and Pi's own JSON Schema validator both accepts them and discriminates (a valid payload passes; an unknown property, an invalid enum member and a missing `required` field each reject). Because Pi validates arguments against our schema _before_ invoking `execute`, `additionalProperties: false` is enforced twice and the server never receives a malformed argument object.

Two measurements make this client behave _better_ than one we already ship, and both change what the code has to do:

- **`session_shutdown` is awaited, not fire-and-forget.** Pi's shutdown path is `await runner.emit(...)` with no timeout: a 300 ms `await fetch` completes, a 10 s one completes, and even a full MCP `tools/call` issued from inside the handler completes. SIGTERM and SIGHUP both reach it. Control that must fail: SIGKILL runs nothing. **Consequence: this client needs no equivalent of the opencode dispose-time fire-and-forget flush** (`apps/plugin/.opencode-plugin/plugin.ts::disposeFlushFireAndForget`, whose comment records that opencode kills the subprocess before async handlers finish).
- **The four `apps/plugin/commands/*.md` files work verbatim** as Pi prompt templates (frontmatter `description` plus `$ARGUMENTS`), exposed through a single manifest key. Control: with the package uninstalled the `/command` stays literal text. So the slash-command surface is shared with zero new files.

**One measurement constrains the client instead of easing it, and it is the reason the registration path is not a straight pass-through.** Against a real provider — an OAuth-authenticated Codex provider, model `gpt-5.6-terra` — registering the 23 tools under the server's canonical dotted names makes the provider refuse the whole request (`Invalid 'tools[4].name': string does not match pattern … '^[a-zA-Z0-9_-]+$'`), the harness exits 1, and **not one** tool is usable: inert, not degraded. Discriminating control: the same run with the tool payload suppressed exits 0, isolating the tool definitions from credentials, network and harness. So the extension registers each tool under a provider-safe name (`.`→`_`) and issues `tools/call` under the canonical one — measured to round-trip, with the call reaching the server under its own name. The `inputSchema` still travels **verbatim**, `$schema` and `additionalProperties: false` included, because the same run accepted it.

Publishing to npm is a **deliberate reopening of a decision this repo made once and recorded**: `openspec/changes/archive/2026-05-17-remove-cli-and-npm-distribution/proposal.md:9` retired npm publication ("**BREAKING (distribución):** Eliminar la publicación a npm en GitHub Packages"), and its tasks removed the publish job, `publishConfig`, `bin`, `files` and `prepack` (`tasks.md:8.1`, `6.1`, `6.5`, `6.6`). That decision's stated grounds were _"sin consumidores externos: el repo es privado"_ — publishing an operator CLI nobody outside the repo could install. Both premises have since expired: the repository is public, and here the package **is** the distribution channel — Pi's package gallery lists by the `pi-package` keyword with no admission process, so an npm package is the only way a Pi user discovers and installs Rembric. That sunset left **no live prohibition** in `openspec/specs/` (its deltas touched only `projects`, `consolidation`, `sessions`); the single live constraint is `openspec/specs/open-source-distribution/spec.md:48`, which forbids the README from referencing "npm package", and this change reconciles it explicitly rather than quietly.

## What Changes

- **A fifth client ships as `apps/plugin/.pi-plugin/`, and it is the first npm-published artifact in this repo.** Location follows the per-client manifest-directory convention, and the deciding mechanism is **release attribution, not path resolution**: release-please attributes a release to a component by the paths of the commits under that component's `path`, so only a directory inside `apps/plugin/` makes a Pi-only commit bump the shared plugin version at all. The carrier is therefore the plain component-relative entry `".pi-plugin/package.json"`. **Rejected: `packages/pi/`** — it would be a real pnpm workspace member (nicer, and D5 enumerates exactly what that would have bought and cost). It is _not_ rejected because a carrier cannot be written outside the component: a leading-slash `extra-files` path resolves against the repo root and does reach outside — verified in the source of the version CI runs, undocumented but real; only `..` traversal is impossible. It is rejected because a `packages/pi/` commit would never _cause_ a plugin release, which is the lock-step guarantee itself. Cost accepted and recorded: `apps/plugin/.pi-plugin/` does not match `pnpm-workspace.yaml::packages` (`apps/*`, `packages/*`), so `pnpm -r` does not reach it and ESLint ignores it (`eslint.config.js:17`) — the same condition `apps/plugin/.claude-plugin/package.json` is already in, where its `"@rembric/plugin": "workspace:*"` dependency is dead letter.
- **The extension speaks MCP itself; the tool surface is discovered, never enumerated.** It opens Streamable HTTP against `${REMBRIC_SERVER_URL}/mcp/<slug>` with a Bearer token, calls `tools/list`, and registers each returned tool with `pi.registerTool`, proxying `execute` to `tools/call`. Registration uses a **provider-safe name** (`.`→`_`) with the canonical name retained for the call, because a real provider was measured refusing the canonical dotted names outright. **Rejected: doing that mapping in a `before_provider_request` payload hook** — it cannot work, since the model would then name the sanitised tool and the harness would resolve it against its own registry, which has no such entry. **Rejected: forking or extending `rembric-bridge.mjs`** — the bridge exists to bolt stdio MCP onto a host that already has an MCP client, which is precisely what this host lacks. **Rejected: a hand-written tool list** — 23 tools duplicated in a second place is the drift `CLAUDE.md`'s one-copy rule exists to prevent, and the runtime enumeration makes the duplication structurally impossible.
- **`@rembric/pi` carries the unified `plugin` version as one more `extra-files` carrier.** **Prohibited by this proposal: a new release-please component or an independent npm version line** — that is exactly the fragmentation `unify-plugin-release-track` retired after its cascade/anchor model produced phantom release PRs. `.release-please-manifest.json` keeps exactly two entries.
- **The documented install command carries no version pin: `pi install npm:@rembric/pi`.** Measured against the harness's documented behaviour: a package spec that names a version is treated as pinned and is **skipped** by `pi update --extensions` and `pi update --all`. Documenting a version therefore freezes that user permanently, which is a worse failure than a floating install.
- **Publication runs as a new gated job in `.github/workflows/release-please.yml` with provenance via trusted-publishing OIDC and no long-lived token.** The gate is `steps.release.outputs['apps/plugin--release_created']`, the plugin analogue of the `apps/server` output that already exists at `:36`; the workflow gains `permissions: id-token: write`, which it currently lacks. **Rejected: `NPM_TOKEN`** — a long-lived credential with publish rights, for a repo whose entire supply-chain posture is default-deny.
- **Shared resources are materialised into the tarball by an explicit CI step, not by `prepack`.** Measured with a positive and a negative control: whether a `prepack` script runs depends on the **cwd** of the publish command, because the project `.npmrc` is resolved from the nearest `package.json` — so the root's `ignore-scripts=true` does not cover a package published from its own directory, but does cover one published from the root. A build step whose execution depends on where it was invoked from is not a build step. The change therefore uses a CI step plus a `files` allowlist plus an asserted `npm pack --dry-run`, and **touches neither `.npmrc` nor the lifecycle-script requirements of `supply-chain-hygiene`** on that account.
- **Generic session-protocol logic is extracted to `apps/plugin/bin/rembric-plugin-core.mjs` before the fifth client is written, and `agent` becomes a required parameter with no default.** Roughly 138 lines of `apps/plugin/.opencode-plugin/plugin.ts` are client-agnostic: the nudge constants and texts, `stripPrivateTags`, `truncate`, `diag`, the HTTP client, the transcript accumulator, `buildSummaryBody`/`flushSessionSummary` and the idle debounce. A default value for `agent` would let the new client register sessions under the wrong agent string persistently and irreversibly (`sessions.agent` is written once per session), so the parameter is mandatory and the type declaration enforces it.
- **`supply-chain-hygiene` gains an outbound half.** Its Purpose is explicitly inbound-only today (`:5`: "what a third-party package is allowed to do to this repo") and mentions neither provenance, nor publish-credential shape, nor `files`. Publishing our own package opens a surface with no policy at all; this change writes the policy rather than leaving it implicit in a workflow file.
- **The TUI gains a third install backend.** Pi is neither a per-client shell script (opencode, Hermes) nor a marketplace CLI (Claude Code, Codex): its install is the client's own CLI against a public registry. The TUI's `--agent` set, its four detection adapters and its status table all grow a fifth row.
- **BREAKING**: none at any wire or on-disk surface. No server change is required — `sessions.agent` is `text('agent').notNull()` with no enum and no CHECK (`apps/server/src/db/schema/agent-sessions.ts:51`), so `'pi'` is already a legal value. No migration, no schema change, no derived-data invalidation.

## Capabilities

### New Capabilities

- `pi-plugin` — where the extension tree lives and exactly which files it contains; how it carries the unified `plugin` version; its relationship to the two-track release model and the lock-step guarantee; the npm publication root and what enters the tarball; and the runtime MCP proxy as the tool-discovery mechanism (no enumerated tool list, ever), including the provider-safe registration name and the canonical name the proxied call carries.

### Modified Capabilities

- `open-source-distribution` — the release-identity and two-track requirements enumerate exactly four client carriers (`:104`, `:248`, `:250`, `:252`, `:268`, `:274`); a fifth carrier joins them, while "**exactly two** packages" and "**exactly two** manifest entries" stay verbatim true because `.pi-plugin/` is an `extra-files` carrier of the `plugin` component, not a component. The README requirement at `:48` is reconciled: a **published npm package that is a supported client's install path** is distinct from the retired "npm package" install of the server, and the prohibition is restated so it forbids the dead mechanism without forbidding the live one.
- `tui-installer` — `:11` fixes the orchestrator at two backends; `:43` and `:396` fix the literal `--agent` set `claude,codex,hermes,opencode`; `:170` fixes four version-detection adapters and promises the table's "update available" never lies. A fifth client fits none of those, so the delta names the third backend, extends the set, and **states where Pi's installed version comes from — or, if it cannot be obtained with a guarantee, says so explicitly rather than letting the table assert something it cannot know.**
- `plugin-session-protocol` — `:193` requires the per-turn nudge strings byte-identical across clients, and `:351` requires `<private>` redaction with identical observable semantics in every client. A fifth client that misses either is a privacy hole and a calibration hole, so both requirements' client sets grow. The delta also records that this client's session close is **awaited rather than best-effort**, and the one edge where it is not.
- `supply-chain-hygiene` — a new outbound requirement: mandatory provenance, trusted publishing instead of a long-lived token, a `files` allowlist asserted by a dry-run pack, and a rule about lifecycle scripts in packages **we** publish (as distinct from packages we consume). - `hermes-agent-plugin` — factual repair only: `:42` and `:327` assert "all four clients share the one `plugin` version".
- `opencode-plugin` — factual repair plus one real move: `:85` and `:441` assert "all four clients"; and the "single source of truth" requirement (`:29`–`:56`) must cover the newly-shared core module, since `stripPrivateTags` becomes a second cross-client helper that must exist exactly once.

## Risks

- **A real provider refuses the canonical dotted tool names, which is now a design constraint rather than an open hole.** Measured against an OAuth-authenticated Codex provider (model `gpt-5.6-terra`): registering the server's dotted names verbatim makes the provider reject the **entire** request — `Invalid 'tools[4].name': string does not match pattern … '^[a-zA-Z0-9_-]+$'` — the harness exits 1, and **no** tool is usable, so the client is inert rather than degraded. Discriminating control: the same run with the tool payload suppressed exits 0, which isolates the tool definitions from credentials, network and harness; and the harness itself neither validates nor normalises the name, so the dot reaches the provider intact. **Consequence for the design:** the `.`→`_` mapping lives in `pi.registerTool`, with the canonical name retained for `tools/call` — measured to round-trip to the server under its own name. A `before_provider_request` payload rewrite cannot serve this purpose at all, because the model would name the sanitised tool and the harness would look it up in a registry with no such entry. The same run cleared the schema half: the `inputSchema` is accepted **verbatim**, `$schema`, `additionalProperties: false` and the harness's own `"strict": false` included, so nothing is stripped. **What stays open:** other providers (Anthropic, Gemini, OpenAI in strict mode) are unmeasured, and the policy is to measure the one that fails rather than to sanitise ahead of evidence (`design.md` D8, OQ1).
- **Ctrl-C does not fire `session_shutdown` in either mode.** In print mode SIGINT is not registered (`dist/modes/print-mode.js:32` reads `const signals = ["SIGTERM"]`, with SIGHUP wired separately). In the interactive TUI it was measured under a pty: with keys at t=4 s and stdin held open to t=14 s, Ctrl-C left the handler firing at 13.6 s — the stdin EOF, byte-identical to the no-keys control — while Ctrl-D fired it at 3.6 s, proving the byte channel worked and the interrupt was simply not an exit. A naive first probe reported Ctrl-C as working and was an instrument artefact; the control that must fail is what caught it. Ctrl-D, SIGTERM and SIGHUP are all awaited, so the loss is bounded to one turn by the per-turn flush.
- **Publishing to npm is practically irreversible.** There is no unpublish after 72 hours or once a dependent exists. The gallery listing is itself a public artifact: it displays download counts and recency, so an abandoned package advertises its own abandonment.
- **The `@rembric` npm scope is not claimed.** Zero published packages does **not** prove the organisation name is free; the only way to know is to attempt to create it. This is an **operational prerequisite for the owner, not a code task**, and it blocks the publish job (not the rest of the change).
- **Fifth-client cost is permanent.** Every future nudge, redaction or protocol change must land in five places or in the shared core. The core extraction plus the widened single-implementation invariant is the mitigation, and the invariant is what makes it enforced rather than remembered.
