## Why

`memory.search` is FTS5/BM25-only (purely lexical). It cannot bridge languages or paraphrase: a Spanish query never finds an English-stored memory (and vice versa), and a query like "¿qué bebidas prefiero?" misses "me gusta el café solo" because no words overlap. Rembric is used as a general-purpose memory (dev _and_ personal: preferences, people, places), so content is mixed — natural-language paraphrase (where lexical fails) plus proper nouns and identifiers (where exact match wins). The multilingual embedding model (`gte-multilingual-base`, 768-dim) is **already loaded in-process and already producing vectors for every active memory**, but those vectors are used only by save-time candidate detection — never by search. This change connects existing pieces; it does not add a subsystem.

This change should be read as a local SQLite implementation of the established hybrid-search pattern used by engines such as Elasticsearch (RRF retriever), Azure AI Search (full-text + vector merged by RRF), and Qdrant (prefetch retrievers + FusionQuery), adapted to Rembric's single-process/single-SQLite-file invariant.

## What Changes

- `memory.search` gains a **standard hybrid retrieval path** on the text-query branch, modeled after established search-engine patterns rather than a bespoke Rembric ranking system: a lexical retriever (FTS5/BM25) and a dense retriever (sqlite-vec kNN) each over-fetch into a bounded **rank window**, and their ranked id lists are fused with **Reciprocal Rank Fusion (RRF)**. This mirrors the documented Elastic/Azure/Qdrant pattern: independent retrievers/prefetches → RRF/fusion → one ranked result set — expressed in the repo's flat idiom (a module-level helper + a pure fusion function, mirroring `findSaveTimeCandidates`), not a class hierarchy. The no-query branch (listing by `created_at`) is untouched — pure SQL, real `offset`/`limit`, zero added latency. **BREAKING (internal):** `MemoryService.search` becomes `async` (the embedder is async), so its call site must `await`.
- New **scoped** repository method `knnByQueryVector(...)` in `VectorsRepository` that does kNN against an **arbitrary** query vector (today's `knnByCosine` only finds neighbors of an _existing_ memory row and stays as-is for save-time).
- **`memory_vec` is rebuilt** with a scope-derived **partition key** plus `status` and `type` metadata columns, so the kNN can pre-filter scope/status/type _inside_ the vector index using sqlite-vec's documented metadata/partition-key model. The rebuild uses a **vec0-specific recipe** (NOT the generic table-rebuild dance — `ALTER…RENAME` and `INSERT…SELECT *` are broken on a virtual table; see design D5). `partition_key`/`status`/`type` are set by `insertEmbedding` at insert time (vec0 forbids triggers _on_ the vtable and NULL metadata); `status` is kept in sync by a trigger on the base `memory` table. JSON `tags` are not duplicated into the vector table; tag filtering is exact on the FTS branch and bounded/best-effort on the dense branch's over-fetched pool.
- RRF fusion (~6 lines, hand-written, **zero new dependencies**) with an industry-style **rank window** (`rank_window_size = min(limit + offset + margin, RANK_WINDOW_CEILING)`, not `k = limit`, so recall isn't capped); top-K result shape; `status`/`type` filters pushed into both branches, with `tag` documented as exact on lexical and bounded by the dense branch's rank window.
- The FTS branch is **sanitized and fault-isolated**: the raw query is tokenized before `MATCH` (an accented/punctuated NL query like `"¿cómo toma el café?"` otherwise throws an FTS5 syntax error and would crash the whole search), and an FTS failure degrades to vec-only.
- **BREAKING** (contract): on the hybrid (text-query) branch, `offset` becomes best-effort over the fused pool rather than a SQL `OFFSET`. `offset` remains exact on the no-query listing branch. Documented in the search requirement.

### Modified Capabilities

- `memory`: ADD a hybrid-search requirement (dense vector ⊕ lexical FTS, RRF-fused on the text-query branch using the standard retriever/rank-window vocabulary) and a vector-index requirement (partition key + `status` + `type`, lifecycle-mirroring, scoped kNN). MODIFY "Embeddings MUST be computed in-process…" (vectors now also back `memory.search`, not only candidate detection; `memory_vec` carries a partition key + `status` + `type`) and MODIFY "Stale vectors MUST be re-embedded after a model change" (re-embed explicitly covers active + superseded vectors, so the guaranteed semantic search set never mixes embedding spaces). Archived rows remain lexical-searchable but are outside the semantic-search guarantee after model changes. The vector index is a derived, recomputable-from-`content` index that mirrors lifecycle metadata — not append-only-bound.

## Impact

- **Specs**: `openspec/specs/memory/spec.md` — 2 ADDED (hybrid search; vector index) + 2 MODIFIED (embeddings in-process; re-embed after model change).
- **DB migration**: new migration rebuilding `memory_vec` as `vec0(memory_id, partition_key, status, type, embedding FLOAT[768])` via the **vec0-specific recipe** (stash to a temp table → `DROP TABLE memory_vec` → `CREATE VIRTUAL TABLE` at the final name → explicit-column reinsert; NO `ALTER…RENAME`, NO `SELECT *` — both verified broken on vec0). Backfill derives `partition_key` (`project_id`, or `'__global__'` for global) + `status` + `type` from the joined `memory` row (**no re-embedding**). A base-table trigger (`AFTER UPDATE OF status ON memory`) keeps `memory_vec.status` in sync. A corrective comment goes in the NEW migration (0002 is immutable).
- **Code**: `apps/server/src/db/repositories/vectors-repository.ts` (new scoped `knnByQueryVector`; `insertEmbedding` gains `partitionKey`+`status`+`type`; `similaritySample` scoped to `status='active'` for calibration), `apps/server/src/db/repositories/memory-repository.ts` (scoped BM25 ranked-id reader for the search path), `apps/server/src/services/memory.ts` (`search` becomes `async`; the repos `Pick` widens to add `'vectors'`; gains an optional lazy `embedQuery` callback; delegates the text-query branch to a module-level `hybridSearch` helper — mirroring `findSaveTimeCandidates` — that runs: whole-token-preserving + operator-neutralizing sanitize + embed query → two fault-isolated queries → RRF over-fetch → `last_seen_at` touch; relations stay attached in the MCP layer as today), bootstrap wiring (thread the lazy `embedQuery` into `MemoryService`; ~18 existing construction sites keep compiling because `embedQuery` is optional, degrading to FTS-only when unset), `apps/server/src/mcp/tools.ts` + `mcp/server.ts` (`await` the now-async `search`; widen `embedNow`/`ToolDeps.embedNow` to thread `scope`/`projectId`/`status`/`type`), `apps/server/src/services/embedding-worker.ts` (`findMissingEmbeddings` projects `project_id`/`scope`/`status`/`type`; drain target stays `status != 'archived'`). New pure `fuseRRF` helper. Tests updated: `memory.test.ts` raw `memory_vec` insert (5-col) + now-async `search` assertions; `schema-drift.test.ts` only if `memory_vec` is added to `EXPECTED_COLUMNS` (note vec0 reports empty-string column types; the table is otherwise tolerated by `EXPECTED_TABLES`'s `toContain`). No SQL leaves `db/`.
- **Embedder**: `embedder.embed()` is now called on the search hot path (~15ms per text query, only when a query is present). Reverses the "consolidation only; not on the agent retrieval hot path" note in `0002_vec_setup.sql`.
- **Invariants touched**: scope-at-service (the hybrid branch resolves `Scope` in the service and passes a partition token down; the new readers are scoped, no `admin*`/`unsafe*` prefix); append-only (untouched for `memory`; clarifies `memory_vec` is a derived, recomputable index that mirrors lifecycle). `topic_key` and fresh-context judgment unaffected.
- **Clients**: uniform tool-level change — affects all MCP clients equally (Claude Code, Codex, Hermes, opencode, ChatGPT connector); not client-specific despite being noticed via ChatGPT.
- **Performance** (validated empirically, sqlite-vec 0.1.9 / better-sqlite3 / 768-dim, p50; an early benchmark mislabeled in-scope vs in-partition and was corrected under adversarial review): naive `vec_distance_cosine`+JOIN is O(n) (10k=98ms, 50k=543ms — does not scale). The partition-key MATCH cost scales with rows **in the matched partition**, not the corpus: it shards _across_ scopes/projects (a scoped search hits its small partition in ~1.4ms) but a single large partition is still brute-force. Honest single-partition p50 (the global scope is one partition): 10k=1.3ms, 50k=6.8ms, 100k=14.2ms, 250k=36.2ms, 500k=71.8ms — add ~15ms embed for total text-query latency (~16ms / ~22ms / ~29ms / ~51ms / ~87ms).
- **Out of scope** (future): cross-encoder reranker (single-model-in-process posture); ANN/IVF index — unnecessary for the realistic personal envelope (≤~100k in a partition → ≤~30ms total), reopened only if a single partition grows past the low hundreds of thousands; sub-partitioning the global scope does not help (an unfiltered global kNN must scan the whole space regardless).
