## Why

`memory.save` ranks candidate pairs, keeps five, silently discards the rest — and the rest is the **majority**, not a tail.

Measured over the eval corpus with the real embedder, calling the shipped `findSaveTimeCandidates` directly:

```
candidates found per memory:              427 total, mean 11.2, p50 10, p90 15, max 15
memories exceeding the default cap of 5:  38/38  (100%)
captured by the top-5:                    190/427 (44%)  →  56% of detected pairs are dropped
```

**Provenance caveat, stated because it changes what the number means:** this was measured post-hoc with the whole 38-row corpus present, so it is the **steady-state / re-derivation** figure, not the count each save faced at its own moment — memory #1 had no predecessors at all. It is nevertheless the right model for production, which holds **99 active memories**: a new save there meets a mature corpus. It is not a save-time measurement and this proposal does not present it as one.

Two ceilings produce that 56%. In `services/save-time-candidates.ts`:

1. **`poolSize`, hard-coded 20** (`:92`, `opts.poolSize ?? 20`). It bounds each channel _before_ ranking: `LIMIT 20` on the vec kNN, `LIMIT 20` on the FTS5 bm25 query, and `LIMIT 20` **per extracted entity** on the entity channel. Grep confirms **no call site anywhere sets it** — 20 is the only value that has ever run.
2. **`perSaveMax`, default 5** (`CANDIDATES_PER_SAVE_MAX`, env-settable, `.min(0).max(25)`), applied at `:232`, which is literally `return all.slice(0, opts.perSaveMax)`.

Only the survivors reach `createPending` (`mcp/memory-tools.ts:669`), so the other 56% get no row and no `judgmentId`. Every recovery surface is keyed on a `judgmentId`: `memory.judge` takes one and nothing else; `memory.context.pendingJudgments[]` reads pending rows, so a pair with no row cannot age into it; `/dashboard/judgments` is a view over that table — **no row means invisible there by construction**, and no dashboard view could show a pair that was never written.

**The cap is not the bug.** It is an attention budget: each surfaced candidate is a pending judgment somebody must close, and this instance's queue reached 52 with the un-aged pairs unreachable from every MCP surface (`archive/2026-07-28-surface-pending-judgment-inventory`). At mean 11.2 candidates per save, recording the tail as rows would roughly double every save's pending output, and the sibling `order-relation-annotations` measured what a deep queue does downstream: **1154 of 1164 annotations on an undrained corpus are `pending_conflict`**. Recording the tail is therefore rejected outright.

**And nothing loses information, which is what scopes the change.** What falls off the cap is the fact "memory N resembles memory X". That fact is **derived data** by the test the sibling change `record-graph-retrieval-rejection` publishes: a derived table's contents are determined by exactly two inputs — the current rows of the source tables and a recipe pinned in the shipped image behind a version marker (`design.md:45`) — and "derived iff dropping it loses no information" (`D4`). Similarity qualifies on every count: `memory.content` and `memory.title` are immutable under the append-only invariant (never `UPDATE`d), FTS5 and the entity extractor are deterministic recipes behind `EXTRACTOR_VERSION`, and the embedder is pinned by `EMBEDDING_MODEL_ID` / `_REVISION` / `_DTYPE` / `_DIMS` / `EMBEDDING_INPUT_VERSION`. An **agent's verdict** on a pair is the opposite — source data, irreproducible, and that is what earns a row.

A dropped candidate therefore loses no verdict. It loses a **prompt**, and the prompt regenerates for free because its input is immutable:

```
top perSaveMax → rows + judgmentIds → fresh-context judgment   (unchanged from today)
the tail       → ZERO rows          → candidatesDetected + on-demand re-derivation
```

**Two caveats, because this is not free.**

1. **Re-derivation does not recover fresh context.** The agent that just wrote the memory knows things a later agent does not, and that is the entire rationale for the save-time channel. The tail genuinely loses _judgment quality_, not information. The mitigation is that the five kept are not an arbitrary five: the explicit precedence at `save-time-candidates.ts:223-231` puts entity-sourced candidates first and then ranks by the reported similarity, so the five whose fresh-context judgment is worth most are the five retained.
2. **Re-derivation returns the _current_ set, not the save-time set.** Memories that did not exist then are included; superseded and archived rows are excluded; an `EMBEDDING_INPUT_VERSION` bump changes the vectors, and `record-graph-retrieval-rejection` is explicit that the guarantee is re-derivability rather than bit-exactness (`design.md:65`). **This is a feature, not a defect**: the question a later agent asks is "what does this memory conflict with _now_", and a stale snapshot of a pool computed against a smaller corpus answers a question nobody has. The spec claims re-derivability and never reproducibility.

Finally, the number is not only a loss report. **At mean 11.2 candidates per save, a save with fifteen candidates almost certainly wants a `topic_key`, not fifteen edges.** `memory.suggest_topic_key` already exists. Converging a fragmented topic fixes the modelling instead of judging the symptom, and that guidance is plausibly the highest-value output of this change.

## What Changes

- **`memory.save` reports `candidatesDetected` beside `candidates[]`** — the number of distinct pairs detection ranked, i.e. `all.length` at `save-time-candidates.ts:232`, the array whose tail the `slice` discards. Always present, so a caller never has to distinguish "complete" from "field omitted". It is free: the array is already in memory at the moment the cap is applied, which is where the count is taken. No new query, no repository change.
- **Pool-bounded semantics, honestly named.** The number is a **lower bound** on how many memories in scope resemble the saved row, never a scope-wide total: each channel scans a bounded pool, and because the entity channel loops that bound per extracted entity, the number can also exceed 20. The measurement anchors both halves of this: with p90 and max both **15** against a `poolSize` of 20, a pool-bounded count would have been **exact for every row of that corpus** — which is the argument for the cheap option — _and_ that corpus is 38 rows, smaller than the pool, so exactness is a property of corpus size rather than of the field. At production's 99 active rows, and certainly beyond, the bound begins to bind and the "at least" wording stops being pedantry.
- **`candidatesDetected`, not `candidatesTotal`.** A deliberate divergence from `pendingJudgmentsTotal` (`mcp-api/spec.md:483-513`) and the sibling's `relationsTotal`, both of which are true scoped counts and earn the suffix; borrowing it for a lower bound would borrow credibility this number cannot back, and would teach an agent that a `*Total` in this API may under-report. It follows the `pendingJudgmentsTotal` **idiom** in every other respect: a number rather than a flag, never the returned list's length restated, no companion boolean (truncation is `candidatesDetected > candidates.length`). It is explicitly not `predecessorCount` (`memory/spec.md:950,957`), which reports the bound that was applied — the array length restated.
- **Rejected: a genuine cross-channel COUNT.** For the lexical channel a true count is not expensive but **undefined** — `memory/spec.md:1017` contracts that admission "SHALL instead be by rank position within the already-correctly-ordered candidate pool", so the pool bound _is_ the admission rule and "how many FTS candidates exist" has no answer independent of it. For the dense channel it is a full-partition distance scan (`tune-hot-query-paths` design.md Q4 records `knnByQueryVector` at ~42 ms at 50k, `k` not the lever), on the single synchronous SQLite connection shared by every MCP client, the HTTP API, the dashboard and `/healthz`. Only the entity channel could answer cheaply, and summing per-channel counts over-counts because the merge dedupes by target id.
- **Rejected: reporting only the fact of truncation.** A boolean is derivable and gives an agent nothing to decide with; six-of-five is noise, fifteen-of-five is a fragmented topic.
- **Rejected: exposing `poolSize` as a knob.** Instead `CANDIDATE_POOL_SIZE = 20` becomes a named exported constant and joins `memory`'s named-constants requirement, which already forbids operator or per-request configurability for exactly this class of value. For the lexical channel the pool bound _is_ the admission rule, so exposing it would make an admission rule operator-settable — the thing that requirement exists to prevent — and it is a recall internal with no visible effect on the response (raising it changes _which_ five are best at the cost of three wider scans), so an operator turning it would be tuning blind. `CANDIDATES_PER_SAVE_MAX` stays the single knob, because an attention budget is something an operator can reason about. The `poolSize?` option survives as an internal test seam, never a request parameter.
- **No new MCP tool, and no new read: the re-derivation surface already exists.** Checked before anything was proposed. `memory.search({query})` over the memory's own text covers the lexical and dense channels — the agent holds that text, it just wrote it — and `memory.search({entity})` (`mcp-api/spec.md:1596`) covers the entity channel. A "re-run detection for memory M" tool would cost a full description against a budget this repo deliberately cut 17.1 KB from, and `surface-pending-judgment-inventory` already rejected a new tool for the same reason. What differs is stated in the spec rather than papered over: search is RRF-fused and returns ranked memories, not pairs carrying `judgmentId`s, so the re-derived set is similar but not identical to the detector's pool, and recording a verdict on a re-derived pair is `memory.compare`.
- **The tool description carries the recipe, and every ask it names is one the schema accepts.** `memory.save`'s description gains: what `candidatesDetected` counts and that it is a lower bound; that only the returned `candidates[]` carry `judgmentId`s, so a high number is not a queue the agent just created; that a high number usually means a `topic_key` is warranted (`memory.suggest_topic_key` first) rather than many edges; and that the unsurfaced remainder is re-derivable with `memory.search` and recordable with `memory.compare`. Raising the surfaced count is named as an **operator setting, not an argument**, so no caller is taught an ask that returns `-32602` — the exact mistake `surface-pending-judgment-inventory` had to correct after documenting a total that its own parameter rejected. Budget verified, not assumed: `SAVE_DESCRIPTION` measures **1172** against `DESCRIPTION_MAX_LENGTH = 1900`.
- **Rejected: a response-level hint or a `suggestTopicKey` flag.** It needs a threshold nobody has calibrated, and `memory/spec.md:1125-1134` requires any gate to ship disabled until a committed harness sweep proves a plateau — a bar this change neither meets nor wants to meet. It is also advice the server would synthesise from a number the agent can read itself. The description is read once per session; a hint is payload on every save.
- **`memory.capture_passive` reports the summed `candidatesDetected`.** It runs the identical curation path per extracted learning (`mcp-api`'s "MUST use the same curation path as `memory.save`"), and bulk capture is where truncation compounds. Omitting it would let the two save paths describe one pipeline differently.
- **One dead branch is deleted, because the arithmetic depends on its absence.** `candidatesDetected − candidates.length` is only "what the cap dropped" while nothing filters between the slice and the response. Today nothing does: the `if (supersededByTopicKey && c.targetId === supersededByTopicKey.id) continue` at `memory-tools.ts:668` is **unreachable**, because `saveWithTopicKey` puts the superseded id into the new row's `replaces[]` (`services/memory.ts:229,246`) and `findSaveTimeCandidates` passes `saved.replaces` into `excludeIds` for all three channels. Removing it makes the invariant structural rather than accidental.
- **One published contradiction is resolved while the requirement is open.** `memory/spec.md:505` says candidates are "ordered by max(vec, fts, entity) score descending"; `memory-entities/spec.md:354` says "entity-sourced candidates SHALL lead the merged list"; the code (`:228-231`) does the latter. `candidatesDetected` means nothing unless "the survivors are the best N by a stated precedence" is true, so the stale clause becomes a cross-reference rather than being re-published. Precedent: `archive/2026-07-25-reconcile-specs-with-shipped-behaviour`.
- **`.env.example` loses two lines documenting knobs that do not exist.** `CANDIDATE_VEC_THRESHOLD=0.85` and `CANDIDATE_FTS_THRESHOLD=0.4` (`:33-34`) are absent from `config.ts` — they became engine constants. They sit in the exact block an operator reads when deciding whether candidate detection is configurable, which is this change's subject.

**Slot efficiency was proposed, measured, and rejected. It is not in this change.** Three skips were considered and all three are dead; the numbers are recorded in `design.md` D5 so nobody re-proposes them. Skipping candidates that share the saved row's `topic_key` and skipping candidates already in `replaces[]` are **structurally impossible** on the two channels that filter `status = 'active'` (`memory-repository.ts:138`, `:380`; `vectors-repository.ts:66`): both mechanisms set their target to `superseded`, so such a row cannot be active and never reaches the pool. Measured 0 of 190 surfaced slots for each — a weak measurement (only 2 of 38 rows carried a `topic_key` or a non-empty `replaces[]`), so it is the logic that is decisive, not the count. A near-duplicate skip is worse than unsupported: the highest candidate similarity anywhere on the corpus was **0.850**, so a 0.95 threshold was unreachable and its 0% is "untested", not "disproven" — a requirement written on that evidence would be a guess. `listNotConflictTargetsForSources` remains the only suppression that fires, and it is already implemented.

Two verified modelling holes are **recorded as follow-ups with their evidence** (`design.md` Open questions 2 and 3), not folded in:

- **A pair can hold only one verdict.** `RelationsService.compare` looks up `findBySourceAndTarget` and overwrites via `markJudged(existing.id, …, { requirePending: false })`; the schema FSM comment (`db/schema/memory-relations.ts:22`) states "judged → (terminal — re-judging overwrites the same row in-place)". So `conflicts_with` **and** `scoped` cannot both hold for one pair — a plausible real case ("these contradict, but they apply to different environments"). The nuance survives only in free-text `reason`, which is not filterable, and `/dashboard/judgments` filters on `kind` (`adminListWithContent`), so the unrepresentable second kind is invisible to the operator too. Excluded because widening verdict cardinality is a schema-shape question that changes the closed-verdict-set contract, and nothing here requires it. This change cannot worsen it — it records no additional pairs.
- **There is no unique index on `(source_id, target_id)`.** Only `memory_relations_judgment_id_unique` exists, plus three non-unique indexes; `createPending` inserts with no pair check. **Save-time cannot self-duplicate** — detection dedupes by target id and each save's source is the new row, systematically newer than every target — so this change cannot make it worse. `compare` can assert any direction, so `(A,B)` and `(B,A)` can coexist with contradictory verdicts, and the sibling `order-relation-annotations` makes that visible: `listForMemories` annotates both endpoints, so one memory can show two annotations for the same counterpart with conflicting kinds, no longer hidden by scan order. Excluded because every fix is non-trivial: a unique index needs the SQLite table-rebuild dance _plus_ a pre-dedupe that decides which existing verdict wins (a data decision, not a migration), a normalised direction would break the POV-dependent `supersedes`/`superseded_by` derivation, and the cheap service guard is subtler than it looks — `applySupersedesSideEffect(sourceId, targetId)` supersedes the target, so merging `(B,A)` into `(A,B)` would invert which memory gets superseded.

Explicitly **non-goals**:

- Raising the `perSaveMax` or `poolSize` defaults, or recording the tail as rows.
- Changing the ranking precedence — entity-leads-then-similarity is published (`memory-entities/spec.md:354`).
- GraphRAG or graph retrieval — evaluated and rejected (`record-graph-retrieval-rejection`).
- Widening `include_relations` — measured and rejected (`order-relation-annotations` D5).
- **Batching `memory.compare`.** `memory.judge` batches to 25 (`relations-tools.ts:62`); `compare` has no array form, so per-pair recovery costs one call per pair. The spec therefore does **not** present `compare` as a bulk escape hatch — it names `topic_key` convergence as the primary answer and `compare` as the single-pair one. A batched `compare` is a real follow-up (parity with `judge`'s per-item-transaction contract and partial-failure response shape), filed rather than folded in.
- Any eval-harness metric, query type, corpus or baseline change. `pnpm run eval` is a non-regression check here; the harness is used as a measurement corpus, but nothing it scores changes.
- Any plugin change: two additive response fields, no input-schema change, no new tool.

## Capabilities

### New Capabilities

(none)

### Modified Capabilities

- `memory`: two MODIFIED requirements. "`memory.save` MUST surface candidate conflicts at save-time" gains the pool bound as a named constant, the pool-bounded lower-bound semantics of the reported count, the statement that a dropped candidate loses no source data and is re-derivable via `memory.search`, and the corrected ordering cross-reference. "Retrieval and lifecycle constants MUST be named and bounded in one place" gains `CANDIDATE_POOL_SIZE`, so the last unnamed bound in the save path stops being invisible to review.
- `mcp-api`: one ADDED requirement — `memory.save` and `memory.capture_passive` MUST report how many candidates detection produced. Owns the field name, its lower-bound semantics, its always-present rule, the absence of a companion boolean, the `CANDIDATES_PER_SAVE_MAX = 0` case, and the description recipe (including that it must not name an ask the schema rejects). This capability owns tool contracts and already owns the `pendingJudgmentsTotal` precedent; the detection behaviour stays in `memory` and is not restated. Added rather than folded into "memory.save MUST accept a `topic_key` and surface candidates" so that requirement's enumerated response shape is not rewritten — the shape `mcp-api/spec.md:1679` used when the entity channel added a `source` value.

`memory-entities` is **not** modified: the entity channel's contract, its rarity gate and its precedence are all unchanged.

## Impact

- `apps/server/src/services/save-time-candidates.ts` — exported `CANDIDATE_POOL_SIZE = 20` replacing the inline `?? 20`; `findSaveTimeCandidates` returns the pre-cap count alongside the capped list, taken at the point the cap is applied
- `apps/server/src/mcp/memory-tools.ts` — `saveMemoryWithCandidates` threads the count out; `handleSave` returns `candidatesDetected`; the save output schema gains one number (the per-candidate `candidate` zod object is untouched); `SAVE_DESCRIPTION` gains the recipe; the unreachable `supersededByTopicKey` skip is deleted
- `apps/server/src/mcp/observability-tools.ts` — `handleCapturePassive` sums the per-item counts
- `apps/server/src/services/save-time-candidates.test.ts` — the count's arithmetic; that it is taken before the cap; the pool-bounded ceiling; the `perSaveMax = 0` case
- `apps/server/src/mcp/memory-tools.test.ts`, `observability-tools.test.ts` — end to end: more detected than the cap reports the larger number and still returns exactly `perSaveMax`; none reports 0; a bulk capture reports the sum
- `apps/server/src/test/mcp-integration.test.ts` — the description stays under `DESCRIPTION_MAX_LENGTH`
- `.env.example` — the two stale `CANDIDATE_*_THRESHOLD` lines removed
- `openspec/specs/{memory,mcp-api}/spec.md` — published at archive time only (`pnpm run check:spec-provenance` is CI-gated)

Existing installations: **no migration, no schema change, no derived-index invalidation.** `memory_fts`, `memory_vec`, `memory_replaces` and the three entity tables are untouched; `EXTRACTOR_VERSION` and `EMBEDDING_INPUT_VERSION` are not bumped. Deploy is a plain image upgrade. **No pending row is created, altered or removed by the upgrade**, and no save behaviour changes: the same detection runs, the same five candidates surface, the same `judgmentId`s are minted. The only difference visible to any caller is one additional number per save response. The existing judgment queue is exactly as deep the moment after as the moment before. Rollback is a plain image downgrade: the older code stops emitting the field, and since it is output-only nothing can break on its absence — no client reads it, because it does not exist yet.

**No backfill is possible, and the proposal says so rather than implying otherwise.** Historically dropped pairs left no row, no journal entry and no log line. What they did leave is their inputs: the memory rows are immutable, so any pair that mattered is re-derivable on demand via `memory.search` — which is the argument above, and the reason no backfill is needed rather than an excuse for its absence.

Invariants: **append-only untouched** — no row is written, updated or deleted that is not written today; the count is read off an in-memory array. **Scope-at-the-service-layer untouched** — the count is computed inside `findSaveTimeCandidates`, downstream of the `(scope, project_id)` filter every channel applies, so it can only ever count in-scope pairs; no scope decision moves. **Data-access confinement preserved** — no new SQL, no repository change, no query added. **Fresh-context judgment untouched** — the same mechanism surfaces the same pairs with the same `judgmentId`s, closed the same way by `memory.judge`. **`topic_key` convergence untouched** — the deleted branch is unreachable (proved above), so its removal cannot alter which candidates a topic-key save surfaces, and the description change actively steers agents toward `topic_key` rather than around it. **Derived-never-stored review state untouched** — no column, no counter, no persisted state of any kind.
