## Why

`computeRelevanceLevel`'s lexical component is unweighted token coverage, and the committed calibration grid proves that quantity does not measure relevance on question-shaped queries — it measures English. On the 24-query eval corpus the two classes overlap: `measurements/sweep.txt` in `openspec/changes/archive/2026-07-28-rescore-relevance-abstention/` reports `lowest gold-bearing = 0.333, highest abstention = 0.455 -> NOT separable: the classes overlap on [0.333, 0.455], so no floor abstains on every empty-gold query without rejecting a gold-bearing one`. Both offenders are function-word artefacts: `q-abstain-global-changelog` scores 0.455 on "how does the user want changelog entries written for a release" because `how/does/the/user/want/for/a` appear in nearly every global memory. That change's own conclusion, `archive/2026-07-28-rescore-relevance-abstention/tasks.md:58`, is `**The trigger has fired.**`, and its open task 8.7 (`tasks.md:102`) names the remedy: "the follow-up is a better level function, not a better threshold, and IDF weighting is the specific candidate (a stopword list is the cruder alternative; prefer the one that needs no curated list)". `ABSTENTION_FLOOR` has therefore been `null` since it was written — `apps/server/src/services/hybrid-search.ts:46` — and `abstentionFalsePositiveRate` reads 1.000 against a committed cap of 1 that cannot bind (`test/retrieval/baselines/hybrid.json`).

This is not a threshold-tuning change. The escalation criterion was recorded in advance at `archive/2026-07-28-rescore-relevance-abstention/design.md:114` — "Escalate to IDF-weighted coverage only if the sweep shows plain coverage does not separate the abstention queries from the gold-bearing ones; IDF re-introduces corpus dependence and is a step backwards unless the data demands it." The data demanded it.

## What Changes

- **The level's lexical component becomes IDF-weighted coverage** — the share of the query's _information_ present in the row, not the share of its tokens. Rejected alternatives: a curated stopword list (per-language for a deliberately bilingual corpus, and a second invisible retrieval knob — the same rejection `archive/2026-07-28-rescore-relevance-abstention/design.md:115` already recorded); minimum-should-match on the lexical branch (`tasks.md:100`, removes recall unmeasured); and raising the floor to out-run the function words, which is the "better threshold" 8.7 explicitly rules out.
- **Document frequency is read from the FTS index, not from the candidate pool.** A new `fts5vocab('memory_fts', 'row')` virtual table supplies per-term document counts; the document total is `count(*)` over `memory`. Pool-local document frequency was measured-and-reasoned into rejection (design D2): the pool over-represents rows containing the query's rare terms, so pool-derived frequency is _anti_-correlated with true rarity for exactly the discriminative terms, and it makes the gate's input a function of the gate's own candidate set — the family of error `openspec/specs/memory/spec.md:358` already forbids.
- **The `df` lookup is keyed on SQLite's own terms, not on a JS imitation of them.** Measured on SQLite 3.53.2: for the sample `Migración de cron programada; validación — Atlas's pipeline? v1.2 rate-limit UTF_8 CamelCase`, FTS5 yields `atlas | camelcase | cron | de | limit | migracion | pipeline | programada | rate | s | utf | v1 | validacion | 2 | 8` while the shipped `tokenizeWords` (`hybrid-search.ts:534`) yields `migración | de | cron | programada; | validación | atlas's | pipeline? | v1.2 | rate-limit | utf_8 | camelcase`. Only 3 of 11 shipped tokens are FTS5 terms, so a frequency lookup keyed on today's tokens scores 8 of them as maximally rare — silently. There is no 1:1 repair (`rate-limit` is two terms). **Reimplementing `unicode61` in JS was tried, shipped in this change's first pass, and does not work either** (`design.md` D3b): the rules disagree in at least three independent ways plus a folding table that is neither all-or-nothing, and the residual absent-term rate runs 17% (Arabic) to 100% (Japanese, Cyrillic with `й`/`ё`) while Spanish measures 0% — which is why the committed en/es corpus cannot see it. The query text is therefore tokenised **by SQLite**, through an FTS5 table whose declaration is derived from `memory_fts`'s own, and the query's terms and their document frequencies come back in ONE `LEFT JOIN` that _replaces_ the existing `term IN (…)` read. Marginal cost 0.10 ms (owner) / 0.49 ms (re-measured) per query at 50 000 rows, statement-level instrument, against a 1.0 ms budget.
- **What that does NOT fix is stated in the requirement rather than papered over.** Row membership — which of the query's terms a candidate row contains — stays a JS tokenisation, because sourcing it from the index was priced at 7.8–28.9 ms per search against the same 1.0 ms budget (`design.md` D3b). The asymmetry is contracted: a query-side fabrication assigned the _maximum_ weight to an arbitrary term, while a row-side disagreement can only under-count a row's coverage, never fabricate a weight, never raise a level, and never touch the cosine the level is the max of. Rejected alternative: weighting an absent term the _minimum_ (`?? documentCount`) — implemented, and it disarms abstention, which is the one thing abstention exists for.
- **Save-time candidate `similarity` stays unweighted.** `openspec/specs/memory/spec.md:1135` requires it be "a corpus-independent lexical overlap measure"; IDF is corpus-dependent by construction. The two paths keep sharing one tokeniser and one plain-containment function, and the weighted level is a separate function built on top — so they cannot disagree about what a token is, and cannot be accidentally unified.
- **The relative filter is re-calibrated, not carried over.** `RELATIVE_LEVEL_RATIO = 0.4` (`hybrid-search.ts:57`) was chosen plateau-interior against _unweighted_ levels; changing the quantity underneath it invalidates that grid. The full `(floor, ratio)` sweep is re-run and 0.40 is kept only if it is still plateau-interior on the new grid.
- **`ABSTENTION_FLOOR` is decided by the new sweep, not in advance.** If a value clears all five criteria at `openspec/specs/memory/spec.md:1251-1257`, this change enables it. If not, it stays `null`, the grid is committed, and that is a successful outcome — the precedent is `DIVERSITY_CAP` at `hybrid-search.ts:59-67`, off because the corpus structurally cannot supply its evidence.
- **Three published claims that the shipped code already contradicts are reconciled.** `openspec/specs/memory/spec.md:1249` states "Three gates ship disabled (`null`): the abstention floor and `RELATIVE_LEVEL_RATIO` … and the per-session `DIVERSITY_CAP`" and `:369` states "Both gates SHALL be disabled by default", while `hybrid-search.ts:57` ships `RELATIVE_LEVEL_RATIO: number | null = 0.4` (enabled by operator decision, `archive/2026-07-28-rescore-relevance-abstention/tasks.md:103`). The scenario at `:407-410` ("SHALL issue no additional database read on their behalf") is consequently unreachable in the shipped configuration. These sit inside the two requirements this change already modifies.
- **BREAKING** for result composition, not for any API: with the ratio live, changing the level function changes which rows `memory.search` returns on every call. No schema, no tool signature, no plugin work.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `memory`: the relevance level's lexical component is IDF-weighted; the term statistics' source, scope and cold/tiny-index behaviour are specified; **the `df` lookup key is pinned to the index's own tokenizer output, and the row-membership half is pinned as an application tokenisation whose disagreement can only under-count** (this replaces the requirement that first shipped in this change claiming full agreement, which was false as implemented — `design.md` D3b); save-time similarity is pinned as explicitly unweighted; the gate-calibration criteria state the plateau width in level units; the false "both gates ship disabled" claims are corrected. **No published scenario is retired.** Two are rewritten in place under their published titles: "A gate decision does not change when the corpus grows" loses "the level of a row depends only on that row and the query", which index-global document frequency falsifies, and "Abstention is off by default" states its precondition as the gates' own state rather than resting on the requirement's false "both gates SHALL be disabled by default". The titles are kept because both remain accurate — the abstention floor does still ship `null`; it is `RELATIVE_LEVEL_RATIO` that does not, and that is corrected in the requirement body where it is stated.
- `retrieval-evaluation`: the sweep reports the weighted component and the statistics that produced it (document total and per-term document frequency), and a level-function change SHALL be justified against the previous committed grid on an unchanged corpus and query set.
- `persistence`: the `fts5vocab` term-statistics table is declared, classified as derived with no stored contents and no version marker, and its behaviour across an FTS rebuild and an FTS drop-and-recreate is pinned. **The query-tokenising table is pinned as a per-connection temporary object** — no migration, no durable schema entry, contentless, created after migrations so it inherits the tokenizer they left behind, and emptied between queries.

Checked and deliberately NOT modified: `mcp-api` (no input or output schema changes; `similarity: number; // 0..1, max(vec, fts) normalized` at `openspec/specs/mcp-api/spec.md:160` keeps its range and its meaning; `abstained` / `abstainReason` already exist), `dashboard` (no operator surface), `memory-entities` (entity extraction has its own tokenisation and does not import these helpers).

## Impact

Code:

- `apps/server/src/services/hybrid-search.ts` — `tokenizeWords`, `tokenSet`, `relevanceComponents`, `poolLevels`, `ABSTENTION_FLOOR`, `RELATIVE_LEVEL_RATIO`, and the stale "gate window" docstring at `:40`.

No `memory` schema change, no backfill. The amendment adds, in the same module, the query-tokenising table's startup derivation from `sqlite_master` and the single `LEFT JOIN` read that _replaces_ `termDocumentFrequencies`' `term IN (…)` shape. No second migration: the tokenising table is a `temp.` object created at startup, so it never enters the durable schema.
- `apps/server/src/test/retrieval/run-eval.ts` — the sweep's leader table and grid; the stale `SWEEP_RATIOS` docstring at `:322-326`, which still describes a pool-narrowing mechanism `archive/2026-07-28-rescore-relevance-abstention/tasks.md:49` records as removed.

Invariants: append-only is untouched (no `memory` writes, no new columns); scope-at-service is untouched for rows, and the new term statistics are index-global aggregates with a spec clause forbidding them from becoming a row-returning channel; `topic_key`, judgment freshness and derived-review-state are not involved. Existing installations get one DDL-only migration and no first-boot work; rollback is a downgrade with no state to unwind.
