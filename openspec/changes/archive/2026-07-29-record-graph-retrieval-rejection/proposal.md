## Why

Two decisions worth months of investigation exist only inside a Rembric instance, which is exactly the kind of knowledge the repo cannot afford to hold there: an investigation concluding the server must not acquire an LLM-built graph retrieval layer, and a benchmark (2026-07-29) that separately killed the two cheap variants of it. Neither travels with a clone, a fork, or a new contributor.

The absence is already costing. `memory-entities/spec.md:454` is the one published requirement that tried to foreclose this class, and it fails at both jobs:

- **It expires by construction.** Its title is "Entity retrieval MUST NOT be added as a fusion stream **in this change**". Once archived there is no "this change", so the requirement reads as scoped to a change nobody can identify — a published requirement outlives the change that introduced it.
- **Its evidence cannot be checked.** Its body asserts that "adding a graph stream to a BM25-plus-vector fusion reduced Recall@5, NDCG@10 and MRR against BM25 alone in its own author's benchmark". Neither this investigation nor a prior one located that benchmark. The conclusion it supports is well-supported by _other_ literature; the citation is not. A requirement resting on a figure no reader can verify invites the next contributor to dismiss the requirement rather than the figure.

And the requirement names a technique, which is the deeper defect. A verdict about GraphRAG ages the moment the technique is renamed. The property that actually caused the rejection does not age: **every derived index in this database is reproducible from `memory`**. That property is what a restore relies on, what makes drift detectable, what lets a bad extraction be corrected retroactively over an established corpus — and an LLM-built index fails it automatically, because its contents are not a function of the memory rows plus a recipe pinned in the image. Publishing the property forecloses the whole class without betting on a name.

The property is also already true, in five places, and nowhere stated as one thing: `memory_fts` and `prompts_fts` are external-content FTS5 tables whose rebuild is one built-in statement (`INSERT INTO memory_fts(memory_fts) VALUES('rebuild')`, used by `0016`/`0020`); `memory_replaces` is trigger-maintained with a migration backfill from `json_each(memory.replaces)`; `memory_vec` re-derives on an `EMBEDDING_MODEL_ID`/`EMBEDDING_INPUT_VERSION` marker mismatch; the three entity tables re-derive on an `EXTRACTOR_VERSION` mismatch. Five separate requirements each say "this one is derived". None says a new one must be.

## What Changes

- **`persistence` gains one requirement: every derived table SHALL be reproducible from source tables by a pinned recipe with no third input.** Phrased as the closure property, not as a verdict on a technique — "no input outside (a) the current source rows and (b) a recipe pinned in the image and identified by a version marker on disk". The in-process embedder satisfies it (model id, revision, dtype and text recipe are all pinned and recorded); a language model at index time does not. Chosen over three alternatives: a `retrieval-evaluation` requirement (that capability governs the harness, not the schema — a reader looking for a storage rule would not find it there), a `data-access` requirement (that capability governs where SQL may execute, an orthogonal axis), and a new capability for one requirement (overhead, and it would orphan the five existing derived-table requirements it generalises).
- **The requirement is made assertable by a table-classification registry in `apps/server/src/test/invariants.test.ts`.** Every table in the migrated schema is classified `source` or `derived`; each `derived` entry names the mechanism that reproduces it, and the test asserts that mechanism is present in the file or migration it names — the "allow-list anchors" idiom the suite already uses for the purge `DELETE`s. Completeness is asserted against `sqlite_master`, not against a hand-kept list, so a table added by a future migration and left unclassified fails a test rather than passing unnoticed. Chosen over leaving the requirement review-only, and over extending `schema-drift.test.ts::EXPECTED_TABLES` (that assertion deliberately tolerates extra tables, so it is structurally incapable of catching an unclassified one — and it is currently missing `memory_replaces` and `prompts_fts`, which is the same gap in miniature).
- **The requirement's boundary is stated in the requirement, not left to inference.** `memory.content`, `sessions.summary`, `confirmations.reason` and `memory_relations.reason` are agent-authored, irreproducible, and **source** — the requirement does not reach them. A table is derived if and only if dropping it loses no information. Without that sentence the requirement reads as forbidding half the product.
- **`memory-entities`' fusion-stream requirement is retitled and re-evidenced, keeping its conclusion.** Retitled to drop "in this change". Its unverifiable figure is replaced by three sources that were checked: GraphRAG-Bench (arXiv 2506.05690), where plain RAG _wins_ fact retrieval 60.9% against 36.9–60.14% for graph methods; Mem0 (arXiv 2504.19413), the closest analogue by domain, whose graph variant _loses_ on single-hop (65.71 vs 67.13) and multi-hop (47.19 vs 51.15) at 2× search latency; and this repo's own measurement that there is no headroom to buy — recall@8 is 1.000 against an arithmetic ceiling of 1. The gate it imposes (a measured improvement on the harness, in a dedicated change) is unchanged and now has a reachable bar attached.
- **No behaviour changes.** No migration, no schema change, no derived-index invalidation, no `EXTRACTOR_VERSION` or `EMBEDDING_INPUT_VERSION` bump, no MCP tool, no plugin file, no dashboard token. The only executable artifact is one test.
- **The research is recorded in `design.md`**, with each figure labelled measured / cited / owner-reported / unverified, and with the falsifiers that would reopen the decision. There is no `docs/adr/` in this repo; the archived change folder is the decision-record slot, and `pnpm run check:spec-provenance` makes archiving a change the only way published spec text arrives, so one folder does both jobs.
- **Explicitly not proposed:** deleting the fusion-stream requirement; any absolute no-LLM veto (the owner's standing position is that an LLM in the server is acceptable against a drastic, demonstrated improvement — recorded in `design.md` D6 so a future proposal knows it must argue with numbers rather than be dismissed by citation); query telemetry (the missing instrument, named as a falsifier, not built here).

## Capabilities

### New Capabilities

(none)

### Modified Capabilities

- `persistence`: gains **Requirement: Every derived table MUST be reproducible from source tables by a pinned recipe** — the closure property generalising the five existing per-table derived-data requirements, with its source/derived boundary stated and its enforcement point named.
- `memory-entities`: **Requirement: Entity retrieval MUST NOT be added as a fusion stream** — retitled (drops "in this change"), and its unverifiable benchmark claim replaced with three checkable sources plus the local no-headroom measurement. The prohibition and its escape hatch are unchanged.

`retrieval-evaluation` is deliberately **not** modified. Its no-language-model clause (`:11`) already forbids an LLM in ingestion, retrieval or grading, and it is a property of the _harness_; restating a storage rule there would create two requirements that can drift. `data-access` is not modified: it governs where SQL executes, not what a table's contents may depend on. `memory` is not modified: no read or write behaviour changes.

## Impact

- `openspec/specs/persistence/spec.md` — one new requirement, published at archive time only (`pnpm run check:spec-provenance` is CI-gated).
- `openspec/specs/memory-entities/spec.md` — the `:454-461` requirement replaced in full (title + body + scenarios), same publication path.
- `apps/server/src/test/invariants.test.ts` — one new `describe` block: the source/derived table registry, its completeness assertion against `sqlite_master`, and one anchor per derived table asserting its named rebuild mechanism still exists. This is the change's only executable artifact.
- `apps/server/src/db/schema/entities.ts` — its header comment (`:13-24`) already states the property for its own three tables; a spec cross-reference may replace the prose, but no code changes. No new comment blocks (repo comment policy).
- `openspec/changes/record-graph-retrieval-rejection/design.md` — the decision record itself: verdict, three reasons ranked, the two measured variant rejections, the invariant collisions, the owner's standing position, the falsifiers, and the source list with per-source verification status.
- Cross-references the sibling change `order-relation-annotations` (validated, unarchived) for the annotation-ordering defect the same benchmark exposed, and for the widening rejection recorded there as its D5. Neither change depends on the other; this one does not restate those numbers beyond the pointer.

Existing installations: nothing to migrate and nothing to invalidate. No table, index, trigger, marker or row is touched, so the first boot after upgrade is indistinguishable from the boot before it, and rollback is a plain image downgrade. The one new test runs against a freshly migrated temp database like its neighbours in the suite, so it cannot fail on a populated install without also failing in CI. Derived data (`memory_fts`, `memory_vec`, `memory_replaces`, `prompts_fts`, the three entity tables) stays exactly as it is — the change asserts a property those tables already have rather than changing how they are built.

Invariants: none violated. Append-only untouched (no write path exists in this change). Scope-at-service-layer untouched. `topic_key` convergence untouched. Fresh-context judgment untouched. Derived-never-stored review state untouched — and the new requirement is its storage-layer sibling, so the two are cross-referenced rather than merged. SQL-confined-to-`db/` untouched: the new test reads `sqlite_master`, and test files are already exempt from that gate. No new MCP tool, so no plugin work across the four clients.
