## Why

`memory.session_start` adopts an already-`active` session for the caller's `(tokenId, projectId)` instead of minting a second row, and that adoption is correct — it is what stops a defensive model call from forking a parallel session on top of the one the host's `SessionStart` hook already registered. What is not correct is that the adopt branch consumes `args.agent` nowhere and the response reports nothing about it. Verified by static read against `origin/main`:

- `sessionStartOutput` (`apps/server/src/mcp/session-tools.ts:79-86`) declares `sessionId`, `scope`, `projectId`, `startedAt`, `title`, `reused` — there is no `agent` field.
- The adopt branch (`apps/server/src/mcp/session-tools.ts:207-213`) sets `reused = true` and calls `deps.agentSessions.touchActivity(session.id)`. `agent` appears only in the `else` branch, as `agent: args.agent ?? 'unknown'` (`:219`), so an adopted row keeps whatever `agent` it was created with.
- The emitted payload (`:242-249`) is `{ sessionId, scope, projectId, startedAt, title, reused }`.

So a caller that passes `agent: 'pi'`, receives `reused: true`, and is now writing into a row labelled `claude-code` has no field in the response that says so. The discard is not merely undetected, it is undetectable — and it is permanent: `sessions.agent` is immutable by contract (`openspec/specs/sessions/spec.md:11`, "SHALL never mutate the `agent`, `token_id`, `started_at`, or `project_id` of an existing session"), with a CI invariant scenario forbidding `UPDATE agent_sessions SET agent = ?` outright (`:26-30`). There is no repair verb, so once a session is misattributed it stays misattributed for its whole life, and every memory and summary version anchored to it inherits the wrong attribution.

Issue #337 reports the reachable trigger: four `claude -p` processes sharing one token and the default project, each calling `memory.session_start` with a distinct `agent`, all four receiving the same `sessionId` with `reused: true`, and nine summary version rows interleaved under one row still labelled with the first caller's `agent`. Nothing enforces one token per agent — the dashboard issues per-agent tokens and `docs/agents.md` recommends them, but the installer prompts per client without objecting to the same value pasted five times.

The published contract already contains the argument for the fix. `mcp-api` requires `reused` precisely because callers need to know whether adoption happened (`openspec/specs/mcp-api/spec.md:2807`: "`reused` is the only signal distinguishing 'you are now attached to the host's session' from 'you just created a parallel session'"), and the same capability's description/response requirement asserts that a closed-form `Returns:` list "SHALL name every field the `outputSchema` marks required" (`:2529`, `:2560-2565`). If `reused` answers _whether_ a session was adopted, the response owes the caller _whose_ session it now is. That is one step of the same argument, not a new one.

## What Changes

- **Report the attribution rather than repair it.** Add a REQUIRED `agent: z.string()` to `sessionStartOutput` and populate it from the resolved row on both branches. Rejected: **refusing the reuse on `agent` mismatch** (#337 Option 2) — a host-registered row plus a model that names itself differently is the ordinary case the reuse exists to serve, so refusal breaks the legitimate path to punish the pathological one; and **adding `agent` to the reuse key** (#337 Option 3) — it genuinely separates agents and thereby resurrects the duplicate-session bug the reuse was introduced to prevent. Repairing the row on adopt is not on the table at all: `sessions.agent` is immutable per the `sessions` capability, and an `UPDATE … SET agent` is a build failure by invariant test.
- **Read the value from the row, not from the branch.** The response field is one expression, `session.agent`, evaluated after the if/else. `findActiveForTransport` returns the whole `AgentSession` (`apps/server/src/services/agent-sessions.ts:497-511`) and `start()` returns the inserted row, so what is reported is by construction what is stored — a per-branch value could drift from the column while still looking right. No service method, repository method, query or schema change is needed.
- **`agent` only; not `description`.** `args.description` is discarded on the same branch, but it is nullable, carries no attribution, and a `null` in the response is ambiguous between "the row has none" and "yours was dropped". Recorded as deliberately deferred in `design.md` (D2) and in `tasks.md`, not silently omitted.
- **Extend the description in lock-step, and re-measure it.** `mcp-api`'s description/response requirement makes a required field the `Returns:` list omits a defect, and `apps/server/src/test/mcp-integration.test.ts:811-825` pins the required list to exactly six names and asserts every one appears in the text — so the schema edit reds that test until `apps/server/src/mcp/server.ts:305` names `agent` too. The description must also say what the field means on `reused: true`, otherwise the model reads it as an echo of its own argument. Length is re-measured from a real `tools/list` response and the pin at `:746` updated; no clause needs reclaiming (`DESCRIPTION_MAX_LENGTH = 1900` at `apps/server/src/mcp/server.ts:128`, the repo's pinned measurement for this tool is 616, so 1284 chars of headroom).
- **Additive on the published contract, so no compatibility marker applies.** The MCP SDK validates `structuredContent` against the schema published at registration in the same process (stated in `openspec/specs/mcp-api/spec.md:2529`'s remedy paragraph), so schema and payload move together and no caller can observe one without the other. The column is `NOT NULL` (`apps/server/src/db/schema/agent-sessions.ts:51`), so the field is never nullable and never absent — no existing field changes type, name or meaning.
- **No new MCP tool, no touched load-bearing invariant.** Append-only memory, service-layer scope enforcement, `topic_key` convergence, fresh-context judgment, derived-never-stored review state and SQL-confined-to-`db/` are all untouched. Scope resolution in the handler is unchanged.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `mcp-api`: one MODIFIED requirement — "The MCP server MUST expose four session-lifecycle tools". `memory.session_start`'s response gains a REQUIRED `agent` field reporting the attribution the resolved row actually carries, which on `reused: true` MAY differ from the `agent` argument the call passed; the requirement records why the adopt path cannot honour a differing argument and must therefore report the one in force. Two published scenarios are updated (the response enumeration, and the description's required-field list) and one is added (adoption reports the row's `agent`, with the fresh-mint control).

## Impact

- MCP surface: `apps/server/src/mcp/session-tools.ts` (`sessionStartOutput` gains `agent: z.string()`; the `ok(…)` payload gains `agent: session.agent`) and `apps/server/src/mcp/server.ts:305` (the `memory.session_start` description's `Returns:` list plus one clause on what `agent` means under `reused: true`).
- Tests: `apps/server/src/test/mcp-integration.test.ts` (the required-list pin at `:811-825`, the description-length pin at `:746`, and an end-to-end assertion on the live transport), `apps/server/src/mcp/session-tools.test.ts` (adopt-with-a-different-`agent` plus the fresh-mint control).
- Specs merged at archive time: `openspec/specs/mcp-api/spec.md`.
- Deliberately untouched: `apps/server/src/services/**` and `apps/server/src/db/**` (no new method, no query, no column, no migration), `apps/server/src/server/api-router.ts` (the HTTP `POST /api/<slug>/sessions` response has the analogous omission — `{ …, created }` with no `agent`, `:124-132` — and is out of scope; see `design.md` D5), the whole `apps/plugin/` tree (no client reads this response — grep for `reused` across the repo finds it only in `apps/server/src/mcp/server.ts` and two server test files), and `apps/server/src/dashboard/**`.
- Existing installations: no migration, no schema change, no derived-data invalidation (`memory_fts`, `memory_vec` and the three entity tables are untouched), no HTTP contract change, no release-track consequence beyond a `server` bump. First boot after upgrade behaves identically except that `memory.session_start` returns one more field; sessions already misattributed stay misattributed — this change makes the condition visible, it does not retro-repair rows, and by the `sessions` capability it must not. Rollback removes the field and restores the silent discard; nothing persisted depends on it.
