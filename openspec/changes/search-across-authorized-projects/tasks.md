Confirm the behaviour by test whichever way it lands. — **RECORDED with the reason it was named at all, and with the published sentence that makes it a hazard.** `topic_key` is unique per `(scope, project_id, topic_key)` among active rows, so widened, one key legitimately has N active rows — one per project. The narrow branch's **published** description is what a client reads: `memory.search`'s `topic_key` argument (`apps/server/src/mcp/memory-tools.ts:129-135`) says it "returns the topic's whole history — the active row plus every row it superseded — because that is what tells you whether the topic already converged before you save a synonym key". - [x] 7.20 **MEASURED AND DELIBERATELY NOT TAKEN: the `adminBacklogCount` partial-index optimisation** (design D18). Phase 1 gave the two backlog reads a `project_id IS NOT NULL` predicate, because a row with no project is in no scope and the drains must not hot-loop on a row they cannot place. It is not. `dd5435f` deleted it as a **correctness** defect — it "filtered one side of its subtraction and not the other, so a scanned legacy row was subtracted from a total it was never in — an empty backlog reported while `findMissingScans` still returns rows", silent because zero passes the negative-value guard. `EntitiesRepository.adminBacklogCount` (`apps/server/src/db/repositories/entities-repository.ts:316`) is now unconditionally the anti-join and says so: "A subtract-two-counts shortcut undercounts here: it would take the scan count over every row while the total excludes project-less ones." **So D18's recorded fix is no longer drop-in:** subtracting a project-less count from a bare `COUNT(*)` restores the fast path on one side only and reintroduces exactly the asymmetry `dd5435f` removed. Whoever picks it up must filter the scan side too (its own partial index, or a join) and must **re-measure**, because D18's figures were taken against a statement shape that no longer exists in the tree.
