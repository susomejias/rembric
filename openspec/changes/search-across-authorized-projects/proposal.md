## Why

An agent working across several repositories cannot ask one question of all of them. `memory.search` resolves to exactly one project and no argument widens it — measured at the wire against production 0.26.0, `memory.search({all_projects: true})` returns JSON-RPC `-32602 unrecognized_keys`, because every tool input schema has been `.strict()` since `2ebb5a3`. The operator's only workaround is N sequential searches, one connection each, with the agent merging the results by hand.

The capability has been proposed and refused three times, each time for a reason that has since expired or is closed by this change:

- **"It is an admin privilege test."** `grant-tokens-multiple-projects` D13 retired that framing: with set tokens the widening is a **set enumeration** — the projects the connection's token may read — which `apps/server/src/mcp/project-tools.ts:205` already computes as `.filter((p) => isAuthorized(ctx, 'read', { scope: 'project', projectId: p.id }))`. The admin case falls out as the special case where the set is every project.
- **"The eval cannot detect over-widening."** Still true, and it is the real blocker. Re-measured at HEAD in `archive/2026-08-05-retire-the-global-scope/tasks.md` 16.15: under a mutation dissolving `scopeWhere`'s project branch — i.e. total loss of scope isolation — **MRR@8 rises 0.828 → 0.859 and `pnpm run eval` stays GREEN**. The harness would report the loss of isolation as an improvement. The structural cause is measurable today: of 24 committed queries, 8 carry no gold, 12 carry `|gold| = 1` and 4 carry `|gold| = 2`, against `K_VALUES = [5, 8]` (`run-eval.ts:31`). With `|gold| ≪ k` the Precision@k denominator is pinned at `k`, and the committed baseline confirms the saturation: `ceilings["8"].precisionAtK` is `0.15625` and the floor is `0.10625` — `measured − 0.05` — so P@8 sits **exactly at its arithmetic ceiling** and R@8 at `1.0`. Once recall is 1.0 it does not matter which rows fill the holes. `FLOOR_METRICS` (`floor-ratchet.ts:18`) and `CAP_METRICS` (`:23`) gate five metrics, none of which can move when foreign rows displace nothing.
- **"`Scope` will have collapsed to one arm by then."** It has not. `apps/server/src/services/scope.ts:17` is still `export type Scope = { kind: 'global' } | { kind: 'project'; projectId: string }`, and the arm is alive in the type across `SCOPE_GLOBAL`, `memoryMatchesScope`'s branch (`scope.ts:36`), `scopeWhere`/`scopeCondition` (`db/repositories/scope-clause.ts:19`, `:26`), `GLOBAL_PARTITION_KEY` and `partitionKeyFor` (`:6`, `:44`), six `opts.project?.kind === 'global'` branches in `memory-repository.ts` (`:770`, `:922`, `:950`, `:968`, `:999`) and one in `prompts-repository.ts:194`, with live construction at `dashboard/memories.ts:587,611`, `scripts/seed-volumetric.ts:529` and `test/retrieval/ingest.ts:68`. Migration `0031` left zero global memory rows in production, but the retrieval corpus still holds **10 global-scoped memories and 4 global-scoped queries** — so the phantom arm is not merely typed, it is exercised by the only harness that gates retrieval quality.

Adding a widening on top of that union would repeat the shape of **GHSA-cc4j-ch4r-9pf5**: a widening value travelling beside `Scope` that no downstream layer can validate. `openspec/specs/auth/spec.md:224` already forbids it in advance — "Any future widening SHALL therefore carry its authorization decision with it, or be constructed at exactly one site that has already made that decision" — and `:252` binds this proposal from the moment it is written.

Two costs make the feature worth its price now rather than later. The dense branch is bound to one partition (`vectors-repository.ts:131`, `AND partition_key = ${opts.partitionKey}`, with the comment at `:116` explaining the `k =` form exists "so the partition shard is scanned, not the whole corpus"), and fusion is Reciprocal Rank Fusion (`hybrid-search.ts:139`), which orders by rank **position** — so N per-project result lists would give every project a rank-1 row and weight a three-memory project like the best home match. And set tokens, shipped today, make legitimate cross-project reads ordinary rather than exceptional, so the ranking question stops being hypothetical.

## What Changes

- **`Scope` collapses to one arm before anything else is built.** `Scope` becomes `{ kind: 'project'; projectId: string }` and the global arm, `SCOPE_GLOBAL`, `GLOBAL_PARTITION_KEY`, `partitionKeyFor`'s sentinel branch and the two `scopeWhere`/`scopeCondition` global branches are deleted, along with the option-bag global arms in `memory-repository.ts` and `prompts-repository.ts`. This is the **type half** of the release-N+1 work `retire-the-global-scope` scheduled at `tasks.md` 16.1. The **schema half** — dropping `memory.scope`, the five scope-bearing indexes and `memory_entities_identity_idx`, and flipping `sessions.project_id`/`prompts.project_id` to NOT NULL — is deliberately **NOT** in this change (D2): `openspec/specs/memory/spec.md:1619` already states "Its removal is a separate change", and the timing depends on an unresolved rollback-window judgement (`retire-the-global-scope` open question 1) that a retrieval feature has no business deciding.
- **The widening is a distinct type that a write cannot hold, not a boolean beside the scope.** `Scope` stays one arm and remains the parameter of every write and every non-search read; a separate `SearchScope = Scope | { kind: 'authorized-projects'; projectIds; homeProjectId }` is accepted only by the search path. Handing a widened scope to `memory.save` is a **compile error**, not a runtime refusal. This is a stronger answer than issue #304's own proposal (a third field on `Scope`), which would have left the widened value constructible anywhere a `Scope` is.
- **Semantics are the token's reach, not a privilege test.** The widened set is exactly the projects `isAuthorized(ctx, 'read', { scope: 'project', projectId })` admits, reusing the live filter at `project-tools.ts:205`. A `*`/`read:*` token reaches every project; a `projects`/`read:projects` set token reaches its members; a `project:<id>` token reaches one, so its widened search is byte-identical to its narrow one. **This supersedes the 2026-08-02 "solo `*` / `read:*`" decision, which predates set tokens.**
- **The harness gains the power to detect over-widening BEFORE the tool ships**, and the proof is that the over-widening arm goes RED. New gold sets with `|gold| ≥ k`, high-scoring cross-project distractors, and a new gated cap `foreignScopeRate` — the fraction of returned rows whose `project_id` is outside the query's own scope, capped at 0 for every non-widened query. **`avgTokensReturned` is deliberately NOT promoted to a cap** (D9): `retrieval-evaluation/spec.md:116` reserves that for its own change and its scenario at `:157` says any claim that the token axis is gated "SHALL be treated as a spec defect". A token cap is a blunt proxy; `foreignScopeRate` measures the thing itself.
- **Ranking is pure relevance over one globally-ordered list per branch, with no home-project boost.** Measured (see `measurements/vec-partition-capability.md`): sqlite-vec 0.1.9 accepts `partition_key IN (…)` with bound parameters and with a `json_each` subquery, applies `k` per named partition, and `ORDER BY distance` merges them into one globally distance-ordered list — so RRF ranks stay comparable with no fudge factor. Cost is ≈ linear in the total rows scanned — at 50 000 vectors over 8 partitions, ratios of 1.00 / ≈2.03 / ≈4.05 / ≈8.09 for 1 / 2 / 4 / 8 partitions, reproduced across four independent runs with under 8% spread on every arm. Two alternatives are refuted by the same measurement: N separate per-partition queries cost the **same** (indistinguishable over those four runs) while producing N rank-1 rows, and dropping the partition predicate entirely is **dominated** — never faster than `IN (all 8)` while returning one eighth as many rows, and ≈1.4× slower in two runs of four. **That last arm is bimodal and the first single run over-claimed a stable 1.41× penalty; the correction is recorded in the artifact, because repetition is what caught it.** A home-project **tiebreak** applies only on an exact fused-score tie. **Strict home-project prioritisation is rejected** (D8): if you widen precisely because the answer is not in your project, and home rows always win, then with `k = 8` and eight mediocre home matches you never see the foreign answer — the feature silently defeats itself.
- **`memory.search` gains one strict boolean argument, `across_projects`.** Not `all_projects` (D11): on a set token that name promises every project and delivers the member set, and a published input name that overclaims is the class `mcp-api/spec.md:2576` forbids. Not `scope` either — `mcp-api/spec.md:2716`'s scenario states "no property name SHALL be `scope` or `include_global`".
- **The response says what actually happened.** `searchedProjects: string[]` names the project slugs actually searched, and `widened: true` is present only when more than one was. This is load-bearing rather than cosmetic: `auth/spec.md:222` requires that an unauthorized widening be **dropped and the resolved-scope result served unchanged rather than the call rejected**, so without a marker the agent cannot tell "this is all there is across five projects" from "my token only reaches one".
- **The tool description carries its own requirement, separate from registration**, on the precedent of `mcp-api/spec.md:456` (`memory.archive`). It must steer the model to widen only on an explicit user request or a genuinely broad exploration. The asymmetry is deliberate and stated: on a single-user instance the authorization gate always passes, so the description is the only thing bounding frequency — and the description is not a substitute for the gate, nor the gate for the description. They bound different threats (noise, cost and precision vs unauthorized access).
- **The entity branch of `memory.search` widens too**, under the same argument and the same authorization (D12). It is the branch with no ranking risk at all — unranked, chronological, exact-address — and "which of my projects mentions this file, this CVE, this host" is the strongest case for the feature. `memory-entities/spec.md:271`'s "**No widening exists**" is modified rather than worked around. The 400-row completeness bound stays a bound on the **response**, not per project, so widening cannot multiply the worst-case annotation payload `mcp-api/spec.md:2430` pins in CI.

**BREAKING**: none at the wire. `across_projects` is optional and absent means today's behaviour exactly; a one-element widened set produces a query byte-identical to today's (measured: `partition_key IN ('P1')` returns the same rows as `partition_key = 'P1'`). Internally, the `Scope` union collapse is a breaking change to every construction site in the tree and to the retrieval harness's own copy.

## Capabilities

### New Capabilities

None. Every change lands as a modification to a published contract.

### Modified Capabilities

- `memory`: `Scope` collapses to one arm; `memory.search`'s scope-isolation requirement admits an authorized multi-project read; the dense-branch requirement gains the multi-partition kNN contract; the widened ranking policy (one globally-ordered list per branch, no home boost, tiebreak only).
- `mcp-api`: the `across_projects` argument and its strict schema; the description requirement; the `searchedProjects`/`widened` response fields and output schema; the path-scoped isolation requirement, whose "No argument SHALL widen the result set past it" (`:23`) is the sentence this change contradicts head-on.
- `auth`: the widening's authorization semantics are the token's read reach, evaluated per candidate project, constructed at exactly one site; the two GHSA scenarios that currently pin "no argument reintroduces widening" become "no _unauthorized_ widening is reachable".
- `retrieval-evaluation`: gold sets sized against `k`, cross-project distractors, the `foreignScopeRate` cap, and the standing obligation that the over-widening mutation must go RED.
- `memory-entities`: the entity lookup widens under the same argument and authorization; ordering and the response-level completeness bound across projects.
- `data-access`: the dense branch's recorded latency floor becomes a function of the union of searched partitions, with the measured `IN(n) ≈ n ×` law and the refutation of the predicate-free form.
