# Resume closed sessions by returning the row to `active`

## Why

A host conversation Rembric has already closed cannot be reattached, and the host keeps talking anyway.

Pi is the proof, because its identity provably survives: `SessionManager` reads the id out of the persisted session file's header (`this.sessionId = header?.id ?? createSessionId()` — `dist/core/session-manager.js:632` of `@earendil-works/pi-coding-agent@0.84.1`), so a resumed conversation re-POSTs `/api/<slug>/sessions` with the exact id the previous run ended. Pi _does_ end it: `CLOSING_SHUTDOWN_REASONS` includes `quit` (`apps/plugin/.pi-plugin/index.ts:351`). `ensure()` then finds the row, bumps `last_activity_at`, and returns it `ended` (`apps/server/src/services/agent-sessions.ts:205-217`) — the only two things it is allowed to do.

Four consequences follow, each verified in code rather than argued:

1. **Memories lose their attribution.** `findActiveForTransport` filters `status = 'active'` (`apps/server/src/db/repositories/agent-sessions-repository.ts:157`), so it matches nothing and `resolveSessionId` returns `null` (`apps/server/src/mcp/_shared.ts:328-333`). Every subsequent `memory.save` on that transport persists `session_id = NULL`.
2. **One conversation becomes two rows.** `memory.session_start`'s adoption path is the same `findActiveForTransport` (`apps/server/src/mcp/session-tools.ts:159`), so it falls through and mints a second `sessions` row for the same logical conversation.
3. **The resumed handoff is silently dropped.** `writeTerminalFields` is first-final-wins on a terminal row: `if (existing.summaryFinal) { delete set.summary; … }` (`apps/server/src/services/agent-sessions.ts:266-273`). The agent's obligatory end-of-turn `memory.session_summary({final:true})` against the original row is discarded with a `200`, because the previous run already curated it.
4. **The original row sits in the purge set.** `findPurgeableEmptyIds` selects `status IN ('ended','abandoned')` (`apps/server/src/db/repositories/agent-sessions-repository.ts:290`), so a conversation that is demonstrably still running is eligible for physical deletion once its grace elapses.

This is not a Pi-only edge. `abandoned` is the _documented steady state_ for Codex CLI and opencode (neither ever posts `/end` — `plugin-session-protocol/spec.md:271`), and the stale-active sweep flips any client's still-live row at the 24h default window, re-evaluated every 30 minutes. "Terminal row, live conversation" is the common case, not the exception. The existing late-write allowance (`sessions/spec.md:54`) patched the _symptom_ — it let a summary land on a closed row — while leaving the row closed, which is why consequences 1, 2 and 4 survived it.

## What Changes

- **Add one state transition: `ended | abandoned → active`, reached only by an explicit, id-targeted resume.** Chosen over the issue's proposal of a per-execution epoch column plus a fencing token: the hazard fencing would guard — a zombie `/end` from the dying process landing after the resume — is bounded at **3 seconds** by the clients' own timeouts (`--max-time 3` in `apps/plugin/scripts/_api.sh:79`; `POST_TIMEOUT_MS = 3000` in `apps/plugin/bin/rembric-plugin-core.mjs:8`), and Pi and Hermes await the POST before the process dies, so the close is already ordered before the resume. The structural cost was also measured once already: the equivalent shape (new column + new HTTP signal + local file + every client) was built, tested end-to-end and reverted as not worth it (`openspec/changes/archive/2026-07-12-fix-cross-session-misattribution/design.md` Decision 2). See design D6.
- **Ship it as a fourth MCP tool, `memory.session_resume`, not an overload of `ensure()` or `memory.session_start`.** Both are per-turn idempotent paths that cannot distinguish a genuine resume from a retry — the issue is right about that. The tool additionally pins the `SessionRouter` transport binding via `setActiveSession`, the same call `memory.session_start` makes at `apps/server/src/mcp/session-tools.ts:189` (the only site in the codebase that writes that binding). That pin is what makes attribution unambiguous without depending on the `findActiveForTransport` last resort at all. See design D1, D4.
- **`ended_at` is cleared to NULL on resume; write-once becomes write-once-per-terminal-transition.** **BREAKING** for `sessions/spec.md:11`. Preserving it was considered and rejected as _not actually preservation_: the next `end()` writes `endedAt: ts` on its active branch (`agent-sessions.ts:374`) and `markAbandoned` writes `endedAt: this.now()` (`:554`), so a preserved value is overwritten at the next close regardless — preserving only buys an interval during which every read surface reports an `Ended` timestamp on an `active` row. See design D2.
- **Resume behaves identically on `ended` and `abandoned`.** Restricting it to `ended` would make it useless for the three clients whose rows reach `abandoned` by design, and would swap one indefensible asymmetry for another — the same reasoning that settled `2026-07-26-allow-late-summary-on-terminal-sessions` D1. See design D3.
- **`last_activity_at` is stamped; `started_at` is never touched.** Without the stamp `abandonInactiveSince` retires the row on its next pass (`COALESCE(last_activity_at, started_at) < cutoff`, `agent-sessions-repository.ts:73`, `:216-228`). `started_at` stays immutable — it is grep-enforced (`apps/server/src/test/invariants.test.ts:105-114`) and re-stamping it to fix ordering is explicitly out of scope. See design D5, D12.
- **All five clients emit the resume, under one uniform unconditional rule: after the FIRST `/sessions` ensure for a session id in that process, POST `/api/<slug>/sessions/<id>/resume` exactly once.** Chosen over a per-client rule driven by the host's own resume signal, because the signals do not cover the case that matters: Claude Code and Codex expose `source: "resume"` and Hermes exposes `reason="resume"`, but all three fire only for a session change **inside a living process**, where the client's in-memory state already keeps attribution correct. Pi has no cold-start signal at all (`reason: "startup"` for `pi -r`, `-c` and `--session`), and `getEntries()` cannot separate a header-only persisted file from a new session. A signal-driven emitter would have been asymmetric across the five and would still have missed every cold start. The unconditional form is safe because resume on an `active` row is a documented no-op, so the client never needs to know which case it is in. See design D10.
- **The resume is a new HTTP route, `POST /api/<slug>/sessions/:id/resume`, not a field on the existing ensure body.** `sessionPostSchema` is a non-strict `z.object(...)` (`apps/server/src/server/api-router.ts:60-65`), so an `{ id, attach: true }` body against an older server, or with the field misspelled, is accepted with `200 created:false` and does nothing — a failure the client cannot detect, on the exact path where the client is trying to repair attribution. An unimplemented route is refused by the router and reaches the one stderr diagnostic every client already emits. The route deliberately does NOT pin the `SessionRouter` (no `mcpSessionId` on an HTTP request); that stays exclusive to the MCP tool. See design D13.
- **Ordering is ensure-then-resume, and it is what makes the purge case free.** If `purgeEmpty` physically removed the row while the conversation was away, the ensure recreates it `active` and the resume no-ops against the row just created. The conversation continues under the same id with no special case. The reverse order would report `session_not_found` for a conversation about to be perfectly healthy.
- **Fixes a recovery two clients already claim and provably cannot perform.** `apps/plugin/scripts/post-compact.sh:22-24` says its ensure "covers the case where the row was abandoned by the stale sweep between the pre-compact moment and the post-compact resume — re-create silently". `ensure()` returns a terminal row untouched, so before this change that comment described behaviour that did not exist on either client that wires the hook.
- **Corrects a false claim this repo asserts in ~10 places: Codex CLI DOES have `SessionEnd`.** `learn.chatgpt.com/docs/hooks` (which `developers.openai.com/codex/hooks`, the URL `codex-distribution/spec.md:65` cites as its verification, redirects to): it "runs for the main thread when you archive or delete a conversation that's still open, when Codex closes normally, or after a conversation has been idle and isn't open in any connected client for 30 minutes. It won't run for subagents." This matters here because `abandoned` being Codex's steady state is half the population resume exists for. The event carries the tightest budget on either host — "`SessionEnd` uses `1` second by default and supports up to `3` seconds", against 600 for every other Codex hook — while `apps/plugin/scripts/_api.sh:79` allows a POST 3 seconds, so wiring it needs both `"timeout": 3` on the entry and a tighter POST budget. Four assertions in `apps/plugin/test/hook-manifests.test.ts` codify the falsehood and are retired by name. See design D14.
- **Corrects a second false claim: Claude Code has a fifth `SessionStart` source, `fork`, and `apps/plugin/hooks/hooks.json:5` declares only `startup|resume|clear`.** Per `code.claude.com/docs/en/hooks` the matchers are `startup`, `resume`, `clear`, `compact` and `fork`, the last firing for `--fork-session`, `/fork` and `/branch`, with "Before v2.1.214, forked sessions reported source `\"resume\"`". Today a forked conversation fires **no hook of this plugin at all** — no row, no nudge, `session_id = NULL` for its entire life. A fork carries a new id (`--fork-session`: "create a new session ID instead of reusing the original"), so it is a new session and belongs in the registration matcher group. See design D15.
- **Corrects a third: three published statements about Hermes are wrong.** `hermes-agent-plugin/spec.md:377` claims `on_session_switch` always rotates the id — measured against `hermes_agent` 0.19.0, three of its seven call sites pass the id the provider already holds (in-place compression, `/undo`, the gateway rewind). `apps/plugin/.hermes-plugin/__init__.py:606-608` claims `/reset` and `/new` pass `parent_session_id=""` "by upstream contract" — `cli.py:7292` passes `old_session_id or ""`, i.e. populated. And the host passes a `reason` kwarg the ABC does not declare, which `__init__.py:611` discards. See design D16.
- **Deliberately NOT fixed, and recorded as an open question rather than assumed benign:** Claude Code's `SessionEnd` handlers "share a 1.5-second budget" unless a per-hook `timeout` raises it, and `hooks.json` declares none while `_api.sh` allows the POST 3 seconds. Found while verifying the Codex budget. It is a pre-existing condition on a path this change does not otherwise touch, so it is named with its measurement rather than fixed here. See design, open question 3.
- **Deferred explicitly, not silently:** the issue's acceptance criterion 8 (an inspectable lifecycle/execution history). It has no concrete consumer and would cost a new append-only table plus a repository, and the repository-classification invariant (`invariants.test.ts:747-758`) makes that a wider change than the transition itself. The resume response returns the discarded `previousEndedAt` so the value is observable at the moment it is dropped, but it is not persisted. See design D7.
- **Free wins, no code required:** a revived row leaves the purge set on its own (`status` is no longer terminal, `findPurgeableEmptyIds`), and the issue's criterion 5 is satisfied by the existing precedence split — first-final-wins is exclusive to terminal rows (`agent-sessions.ts:256-277`), so an `active` row is back under last-final-wins (`:681-694`) and the resumed handoff replaces the old one.

## Impact

**Specs.** Eight capabilities. `sessions` (the FSM, `ended_at`'s write-once clause, and the new service verb — one requirement is REMOVED + re-ADDED because a published scenario titled "No path revives a terminal session" cannot be dropped inside a `MODIFIED` block); `mcp-api` (the "three session-lifecycle tools" requirement becomes four, same REMOVED + ADDED reason; the soft-delete rejection requirement gains the new tool); `http-api` (the ensure requirement gains an explicit statement that it does NOT resume and why the resume is a separate route, plus the new route's own requirement); `plugin-session-protocol` (the convergence requirement's Codex clauses, the lifecycle mapping — new rows for all five clients, the uniform rule, and both hook-manifest scenarios — and the shared-core requirement, which gains the resume as a core-owned call); `claude-code-plugin` (the `fork` matcher, the resume on both `SessionStart` groups, the agent argument on `session-end.sh`, and an overridable POST budget in `_api.sh`); `codex-distribution` (REMOVED + ADDED: the requirement asserts Codex has no `SessionEnd`, and carries a scenario titled "Codex sessions remain active until abandoned by sweep" whose GIVEN is now exactly when `SessionEnd` fires); `hermes-agent-plugin` (RENAMED + MODIFIED: the header claims the id rotates); `opencode-plugin` (the `ensureSession` contract). `dashboard` is deliberately untouched — no operator Resume action (design D11).

**Code.** `apps/server/src/services/agent-sessions.ts` (new `resume()`); `apps/server/src/mcp/session-tools.ts` (new handler, `setActiveSession` pin); `apps/server/src/mcp/server.ts` (tool registration + description); `apps/server/src/server/api-router.ts` (new route, strict empty schema, `rejectIfDeleted`); `apps/server/src/services/agent-sessions.test.ts` (the `terminal rows are terminal` block at `:923-957` drives eight mutating verbs and must be rewritten deliberately — its own header records that a counting invariant passed under mutation on this exact terrain). No new repository method: `updateById(id, set, { requireActive: false })` already exists.

**Plugin.** One shared tree, five clients, and the resume has exactly ONE JS/TS implementation: `apps/plugin/bin/rembric-plugin-core.mjs` issues it from `ensureSession`'s newly-known branch, so opencode and Pi inherit it with no client-side edit and the once-per-id gate is the `knownSessions` set that already guards the ensure. `apps/plugin/scripts/session-start.sh` and `post-compact.sh` add the POST for the two bash clients; `apps/plugin/.hermes-plugin/__init__.py` adds a process-scoped ensured-id set (Python keeps its own implementation, by the existing cross-language rule). Separately: `hooks.json` gains `fork` in its `SessionStart` matcher and passes `claude-code` to `session-end.sh`; `hooks.codex.json` gains a `SessionEnd` entry declaring `"timeout": 3` and `REMBRIC_POST_MAX_TIME=2`; `session-end.sh` gains the agent-name argument that selects its transcript parser, following `pre-compact.sh`'s existing pattern; `_api.sh` makes its `--max-time` overridable. Claude Code's `SessionEnd` timeout is deliberately left as it is (open question 3).

**No migration, no schema change.** `ended_at` is already nullable (`schema/agent-sessions.ts:63`) and `status` already admits `'active'`. Nothing is added to `sessions`, so the SQLite table-rebuild dance and its FK-parent hazard (`memory.session_id`, `prompts.session_id`, `confirmations.session_id`) are not engaged.

**Existing installations.** No first-boot work: the boot sweep (`bootstrap.ts:114-118`) is unchanged and no existing row is rewritten. No derived data is invalidated — `memory_fts`, `memory_vec` and the three entity tables are keyed on `memory`, and no `memory` row is touched. Rollback is a plain code revert; a row resumed under the new code and left `active` is indistinguishable from any other stale-active row and is retired by `abandonStale` on the next pass, so reverting strands nothing.

**Existing installations, version skew.** The server and the plugin tree are independent release tracks, so both mismatches must hold. **New plugin against an old server** is the one that matters and is bounded by design: the resume POST hits a route the old server does not have, the router returns `404`, and every client already emits one stderr diagnostic and continues — the ensure that preceded it landed normally, so behaviour is exactly today's. This is the property that justified a route over a body field: the same skew on an `{ id, attach: true }` body would have been accepted with `200` and silently done nothing. **Old plugin against a new server** simply never calls the route, and the tool remains agent-callable over MCP. A back-fill of the resume POST across a fleet is therefore never required; each client picks it up when it upgrades.

**Existing installations, the Codex behaviour change.** Codex rows that used to sit `active` for up to 24 hours before `abandonStale` retired them now reach `ended` with a transcript-derived summary on a normal close. Rows already `abandoned` are not rewritten and need no repair — they are resumable by the same route as any other terminal row. Operators watching `memory.stats.sessionsByStatus` will see `ended` grow and `abandoned` shrink for Codex, which is the correction, not a regression.

**Behaviour changes an operator will notice.** `memory.stats.sessionsByStatus` stops being monotonic — `ended` and `abandoned` can now decrease. The dashboard shows a resumed row with `status = active`, `Ended` rendered as `—` (`dashboard/sessions.ts:110`, `:380`), and the Abandon form back on it (`dashboard/spec.md:876`); the dashboard's own modal copy, "This transition is not reversible from the dashboard", stays literally true and is unchanged, because no dashboard resume action is added.

**Accepted limitation, stated rather than hidden.** `recentForContext` orders by `started_at DESC` with no status filter (`agent-sessions-repository.ts:190`), so a resumed conversation keeps sorting by when it first began, not by when it resumed. It appears exactly once — the issue's criterion 3 — but not necessarily first. Changing the sort key is a separate change with its own evidence (design, open question 2).
