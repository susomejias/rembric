## Context

Sessions end "under-curated" more often than not: an agent that never calls `memory.session_summary` before the session ends leaves the row with a raw, uncurated `summary` (or none at all). Two independent problems follow from this:

1. **Context pollution.** `recentForContext` (backing `memory.context.recentSessions`) currently gates on `sessionHasContentSql`, which only checks `summary IS NOT NULL` — it does not check whether that summary is curated (`summary_final=1`). Claude Code's `session-end.sh` fallback dumps the raw transcript JSONL when no curated summary exists, including Claude Code's own framework-injected wrappers (e.g. `<local-command-caveat>...</local-command-caveat>` around a bare `/clear`). That raw noise reaches `memory.context` for every future session. This was reproduced live during exploration: a session from 2026-07-08 carrying exactly that wrapper text as its `summary` resurfaced as a `recentSession` at the start of a later, unrelated conversation.
2. **Empty-session clutter.** Sessions with no curated content and nothing anchored to them (no memories/prompts/confirmations) accumulate in the dashboard and DB indefinitely; the only cleanup path (`purgeEmpty`) is a manual button on `/dashboard/maintenance`.

A prior attempt at fixing problem 1 exists as design reference only: branch `feat/tighten-context-final-summaries` (commit `e626a59`, May 2026) implemented a predicate split + HTTP hardening + server-side auto-curate-at-terminal-transition. It was never merged (confirmed not an ancestor of `main`) and now diverges by 704 files (forked before the `apps/`+`packages/` monorepo restructure) — not rescuable as code, but its reasoning about the predicate split is sound and is reused here. Its HTTP-hardening piece is explicitly NOT reused — see the declined HTTP-hardening question below.

A separate question raised and resolved during exploration: should `/summary`/`/end` also be hardened to force `final: false` regardless of client input, closing the theoretical possibility of an HTTP writer claiming `final:true`? **Declined.** That capability is tested, documented, ratified behavior (`http-api/spec.md:89-93`, exercised by `api-router.test.ts:216`), not a bug — and closing it wouldn't raise the security bar anyway: anyone holding a valid bearer token for the HTTP endpoint already holds the same token for MCP, where `memory.session_summary` lets them reach the identical "curated" outcome legitimately. No current script sends `final:true` over HTTP, so Decision 1 below is fully effective without touching this endpoint. The `http-api` capability is untouched by this change.

Separately, an audit for the in-progress `proactive-save-nudges` change (16/18 tasks done) already investigated adding nudges via Claude Code's `Stop` hook and explicitly rejected it ("forced-continuation risk") for the `memory.save` nudge use case. That decision is **not disturbed** here: this change adds a `Stop` hook that never emits model-facing output at all (no `additionalContext`), which is a categorically different use of the same hook event — the rejected use case and this one are distinguished explicitly in Decision 3 below.

The owner's binding constraint discovered during exploration: **zero added LLM token cost, and no perceptible latency added to any turn.** Every decision below was filtered through that constraint.

## Goals / Non-Goals

**Goals:**

- Guarantee `memory.context.recentSessions` never surfaces a session whose `summary`/`title` isn't genuinely curated (`_final=1`), closing the live pollution bug.
- Reduce how often sessions end with a stale/empty `summary` by syncing raw transcript content more often, across clients, for free (no LLM involvement, no added per-turn latency).
- Reduce dashboard/DB clutter from empty noise sessions via automatic, already-scheduled cleanup.
- Reach full behavioral parity across all four clients: every client syncs raw transcript content on every turn, with no model involvement anywhere. Replicate the same functionality on every plugin we support wherever it's technically possible to do so without cost — not just wherever it happened to exist already.

**Non-Goals:**

- Any model-facing nudge specifically asking the agent to call `memory.session_summary` (curation), on any client. Evaluated and declined — see Decision 4.
- Fixing Codex's pre-existing blocking-latency behavior. Unlike Hermes, Codex's hook is an external subprocess with no async escape hatch Codex itself supports — there is no fix available to apply, not just one we're choosing to skip (Decision 5).
- Reviving or rebasing the `feat/tighten-context-final-summaries` branch. It is reference material only.
- Server-side auto-curate-at-terminal-transition (composing a derived `[auto]`-prefixed summary from anchored content when a session ends without curation). The predicate split alone fully prevents pollution without needing this; it can be proposed separately later if genuinely-curated-looking `recentSessions` entries become a priority.

## Decisions

### Decision 1 — Tighten the ONE existing predicate's summary clause; do not fork it

The current spec (`openspec/specs/sessions/spec.md`, requirement "`sessionHasContent` is the single source-of-truth predicate...") already deliberately unifies purge-eligibility and context-surfacing behind one five-clause predicate: `summary IS NOT NULL OR title_final=1 OR EXISTS(memory) OR EXISTS(prompts) OR EXISTS(confirmations)`. Note clause 2 (`title_final=1`) already requires curation; only clause 1 (`summary IS NOT NULL`) does not — that asymmetry IS the bug. The fix is to tighten clause 1 to `(summary IS NOT NULL AND summary_final = 1)`, in the SAME shared predicate, rather than forking a second one.

This single tightened clause fixes both halves of the proposal in one move: (a) a session whose only "content" is a raw uncurated transcript dump no longer satisfies the predicate, so it stops surfacing in `memory.context.recentSessions` (context-pollution fix); (b) that same session now correctly fails `sessionHasContent`, making it purge-eligible under the existing `purgeEmpty`/`countPurgeableEmpty` logic with zero code change there beyond the predicate itself (empty-session-clutter fix, folding Decision 2 in for free for this specific case).

**Alternative considered (and initially proposed, then corrected during spec drafting):** fork a _separate_ `sessionIsContextWorthySql` predicate — `(summary IS NOT NULL AND summary_final=1) OR title_final=1` — dropping the `EXISTS(memory)`/`EXISTS(prompts)`/`EXISTS(confirmations)` clauses entirely for the context-surfacing use, mirroring the abandoned branch's design verbatim. **Rejected upon closer inspection**: the abandoned branch's version only worked because it was paired with a THIRD piece — server-side auto-curate at terminal transition — which guaranteed any session with anchored-but-uncurated content got an auto-derived `summary_final=1` at session end, before `recentForContext` could ever see it. This change explicitly declines to implement auto-curate (see Non-Goals). Reusing the fork _without_ that compensating mechanism would silently regress "Type B" sessions — real memories/prompts/confirmations saved, but the agent never called `memory.session_summary` — out of `recentSessions` entirely, with no compensating signal. Tightening the shared predicate's one buggy clause instead avoids that regression, needs no new predicate name, and keeps the existing spec's "single source-of-truth predicate" claim true rather than breaking it.

### Decision 2 — Auto-purge empty sessions from the existing consolidation sweep

`purgeEmpty` already exists and is fully implemented (`AgentSessionsService.purgeEmpty`); it is invoked today only from a manual dashboard button. Add a call to it from the same deterministic sweep that already runs throttled on `session.start` (no LLM, no cron, journals to `consolidation_ops`). No new scheduling primitive, no new admin-bypass surface — reuses the existing sweep's throttle and journaling. Decision 1's tightened predicate means this sweep will, for the first time, actually catch raw-transcript-only "noise" sessions (previously wrongly considered "has content" and never purge-eligible) — the two decisions compound rather than overlap.

**Alternative considered:** a dedicated cron/timer. Rejected — violates the project's "no cron" consolidation invariant for no added benefit; the existing sweep already fires often enough (every session start) to keep clutter bounded.

### Decision 3 — Claude Code `Stop` hook: side-effect only, reviving a narrowed version of a previously-rejected wiring

The current `claude-code-plugin` spec states "the prior Stop and PreCompact entries SHALL NOT be wired in this version," with the recorded reason being a **semantic bug**: a previous `Stop` hook posted to `/end` (session termination), but `Stop` fires once per assistant turn, not once per session — so the first turn prematurely ended the session and every subsequent turn's call failed silently. Separately, the same spec's own token-budget table already anticipated a _different_ kind of `Stop` hook: "`Stop` hook output: 0 tokens to model (side effect)" — the same category as the already-shipped `PreCompact` hook (`pre-compact.sh`, wired today, does an HTTP POST and returns nothing to the model).

This change wires a `Stop` hook that:

- POSTs to `/sessions/:id/summary` (never `/end`) — cannot trigger the old semantic bug, since it never transitions session status.
- Never emits `hookSpecificOutput.additionalContext` or any other model-facing output — cannot be confused with the nudge-style Stop usage that `proactive-save-nudges` already evaluated and rejected for a different reason (see Decision 4).

It reuses the existing `_transcript.sh` parser pair (`rembric_format_transcript_claude_code`, `rembric_extract_first_assistant_claude_code`) already used by `session-end.sh`, so both `summary` and `title` populate from the first `Stop` where at least one assistant message exists. The script never sends `final: true` (the field is simply omitted from its POST body, same as every other raw-sync caller today), so `title_final`/`summary_final` stay `false` — the raw sync can never satisfy Decision 1's predicate on its own, and `applyPrecedence`'s existing "last-final-wins" semantics (`agent-sessions.ts::writeSummary`, unchanged) mean a later genuine curation via `memory.session_summary` always wins over anything this hook wrote.

**Cadence — resolved empirically, not assumed:**

| Path      | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                       | Status                                                                                                                                                                                                                                                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preferred | Hook entry declares `"async": true` (documented Claude Code `command`-hook field; Claude Code otherwise blocks on hook completion by default, confirmed against `code.claude.com/docs/en/hooks.md`, with a configurable timeout). If it genuinely decouples the HTTP call from turn completion, sync on **every** `Stop`, no throttle — matches Codex's own existing (blocking) per-turn cadence, but without the latency cost. | To validate empirically during this change's e2e pass (task in tasks.md) — the docs describe `async` generically for `command` hooks but don't give a `Stop`-specific example, and don't document whether `additionalContext`/exit-code output is even meaningful from an async invocation (moot here since this hook never emits any). |
| Fallback  | If the e2e pass shows `async` does not reliably decouple latency, wire the same per-session throttle-counter pattern already used by `post-tool.sh` (file counter under `${TMPDIR}/rembric-savenudge/` or a sibling dir), initial cadence every 3 `Stop`s.                                                                                                                                                                      | Only implemented if the preferred path fails validation.                                                                                                                                                                                                                                                                                |

**Alternative considered:** shell-background the `curl` (`&` + `disown`) instead of using `"async": true`. Rejected — Claude Code's docs don't document whether child processes backgrounded inside a hook script survive after the parent hook process exits; the docs explicitly recommend the `async`/`asyncRewake` config fields as the supported mechanism instead of shell backgrounding tricks.

### Decision 4 — No session_summary nudge, on any client (non-goal, not an oversight)

The in-progress `proactive-save-nudges` change already audited every client's model-facing injection channel and explicitly rejected Claude's `Stop` hook for nudging ("forced-continuation risk" — `additionalContext` on `Stop` has no documented guarantee of being free of an extra model turn). The same channel, the same risk profile, applies identically to a hypothetical `memory.session_summary` nudge. Reopening it would need its own justification distinct from "we already reopened Stop for something else" — and Decision 1's predicate split makes it unnecessary: uncurated content simply never reaches `memory.context` regardless of whether curation ever happens. Revisit only if a future need for genuinely-curated-looking `recentSessions` content (beyond "just don't show garbage") emerges.

### Decision 5 — Codex: no change, no fix available (structural, not a choice)

`session-stop.sh` already syncs raw content on every turn via a synchronous `curl --max-time 3` (`rembric_post`). Confirmed against Codex's official docs (`developers.openai.com/codex/hooks`): Codex has no async execution mode for hooks at all, and — notably — if a hook config sets `async: true` anyway, **Codex silently skips that hook entirely** rather than detaching it ("asynchronous command hooks aren't supported yet. Codex skips those handlers"). Codex's hook is an external subprocess the Codex binary itself waits on; there is no mechanism inside `session-stop.sh` that could change that. Codex already pays this latency tax today, silently, with no drop-in fix available. Left unchanged — genuinely out of scope, not a corner cut.

### Decision 6 — Hermes: bump cadence to every turn, non-blocking per its Threading Contract, and serialize only the conversation

Initial assumption (corrected after checking Hermes's official docs, per the owner's explicit ask to validate every client against its real API documentation rather than inferring from our own plugin code): Hermes's host framework does **not** actually block the user-facing turn on `sync_turn` today. Confirmed against `github.com/NousResearch/hermes-agent`: `MemoryManager.sync_all()` already submits provider `sync_turn` calls to a lazily-created single-worker `DaemonThreadPoolExecutor` (docstring: "doing that inline held `run_conversation` open long after the user saw their response") — so `sync_turn`'s blocking `urlopen` call was never actually blocking the user's perceived response, only Hermes's own internal serialized mem-sync worker.

The remaining reason to still add our own threading inside `sync_turn` is to avoid backlogging that worker: if `_api_post` is slow, turn N+1's sync could queue up behind turn N's on Hermes's single-worker executor even though the user isn't waiting on it. Hermes's own official developer guide (`website/docs/developer-guide/memory-provider-plugin.md`, "Threading Contract" section) documents exactly this scenario and the fix: spawn a `daemon=True` `threading.Thread` for the provider's own outbound call, but — refining our original plan — store the thread handle and `join(timeout=5.0)` the previous one before starting a new one, bounding thread growth on long/chatty sessions rather than leaving prior threads to pile up unmanaged. `MemoryProvider` has no `async def` support and no `asyncio` anywhere in the call path (confirmed: raw `threading.Thread` is the documented, not just inferred, mechanism — it doesn't fight an event loop because there isn't one here).

With per-provider threading in place (bounded via join-then-spawn), `_SYNC_TURN_HEARTBEAT_EVERY` (currently 5) can safely drop to 1 (every turn) — reaching full cross-client parity: Claude, Codex, opencode, and Hermes all sync raw content every single turn, and none of them (Codex aside) add latency to it.

**Implementation shape:** snapshot the values `sync_turn` needs (`base`, `slug`, `session_id`, formatted `transcript`) into local variables; store the spawned `threading.Thread` on `self._sync_thread`; before starting a new one, `if self._sync_thread and self._sync_thread.is_alive(): self._sync_thread.join(timeout=5.0)`; then `self._sync_thread = threading.Thread(target=_api_post, args=(...), daemon=True); self._sync_thread.start()`.

**Additionally — filter `_format_transcript` to conversational roles.** Root-caused from a live ended Hermes session (2026-07-12): its `summary` column was dominated by the tail of Hermes's own system prompt (toolset docs, voice/TTS tables), because `_format_transcript` serializes EVERY message in `messages` — including `role: system` — and its tail-truncation window (`_SUMMARY_MAX_CHARS = 20_000`, keeping the most recent chars) leaves mostly system-prompt text for short sessions whose system prompt dwarfs the conversation. The Claude/Codex bash parsers (`_transcript.sh`) already "filter strictly to type ∈ {user, assistant}" and drop framework metadata lines; opencode's accumulator only ever collects conversation text. Hermes is the lone outlier. Fix: `_format_transcript` skips any message whose `role` is not `user` or `assistant` (system prompts and tool payloads never reach the summary channel). This applies to all three of its callers at once (`sync_turn`, `on_pre_compress`, `on_session_end`) and costs nothing. `_derive_title_from_messages` is already assistant-only and needs no change. Drive-by spec correction folded into the same MODIFIED requirement: the ratified spec's "19,500 characters" truncation figure never matched the code's `_SUMMARY_MAX_CHARS = 20_000` — the delta now states 20,000 (the wire bound is non-authoritative anyway; the server's 10,000-char cap is the real trimmer).

**Alternative considered:** leave Hermes's cadence at every-5-turns since "it isn't actually blocking anything user-facing today." Rejected — the owner's explicit ask was to replicate the same raw-sync behavior across every client wherever technically possible, and per Hermes's own documented Threading Contract, it is possible here at negligible cost (one bounded background thread per turn instead of one call every 5th).

### Decision 7 — opencode: reuse the existing fire-and-forget convention

opencode already has a proven non-blocking pattern for exactly this kind of background sync: `scheduleIdleFlush` calls `void flushSessionSummary(sessionId)` (unawaited) from a `setTimeout` callback, shipping today. Add a call to `flushSessionSummary` inside the existing per-turn `chat.message` handler using the same `void` (fire-and-forget) pattern. (The one existing call site that _does_ `await flushSessionSummary` — `session.compacted` — is unaffected and out of scope; it fires rarely, not per-turn.)

Validated against opencode's source (`sst/opencode`, since `chat.message` isn't covered by the official docs site at all — confirmed by checking, not assumed): the host `yield*`s (awaits) each plugin's `chat.message` hook sequentially (`session/prompt.ts`) before persisting the message, but that only waits on what the hook itself awaits — an un-awaited `void flushSessionSummary(...)` resolves the hook's own promise immediately, so the host proceeds without waiting on the fetch. This is real, source-confirmed behavior, not an inferred precedent. One nuance: `chat.message` fires at the **start** of a turn (pre-send), not on completion — so each sync captures everything accumulated through the _previous_ turn, one turn behind. That's fine for a periodic freshness heartbeat (the same lag Hermes's every-5-turn heartbeat already had, just smaller now); it is not a per-exact-moment capture requirement.

**Alternative considered:** await the flush in `chat.message` for stronger delivery guarantees. Rejected — would reintroduce the exact per-turn blocking risk this change avoids for Claude, for no compensating benefit (a dropped fire-and-forget POST just means the summary is slightly less fresh until the next turn's attempt).

**Related finding, out of scope:** the existing code comment above `experimental.chat.system.transform` claiming its mutations are "silently discarded" (citing a since-retracted GitHub issue, opencode/issues/17100) is stale — reading current opencode source (`session/llm/request.ts`) shows the mutated `system` array IS consumed into the final LLM request. Not touched by this change; worth a follow-up comment fix.

### Decision 8 — Dashboard: uncurated session summaries render as raw preformatted text with a RAW badge

Observed operator confusion (owner, 2026-07-12): the session detail view Markdown-renders `row.summary` unconditionally (`mdBody`, per the ratified "Long text content on detail views MUST be rendered as Markdown" requirement), so a raw transcript sync — which frequently contains Markdown-looking framework text (tables, tool docs, headers) — renders as a polished, formatted page visually indistinguishable from a model-authored summary. The operator reasonably read it as "the summary the LLM produced" and concluded the pipeline was broken, when in fact the row was simply never curated (`summary_final = 0`).

With this change making raw syncs far more frequent (every turn, all four clients), that ambiguity would get worse, not better — so the dashboard now renders honesty: `summary_final = 0` → escaped preformatted monospace block (the existing `<pre>` pattern used for judgment Evidence, in an `overflow-x: auto` container) plus a "RAW" chip next to the Summary heading, using existing chip styling (no new design token — no OpenSpec conflict with the locked design tokens). `summary_final = 1` → Markdown render, unchanged. The description (seed goal) is never raw-synced and stays Markdown unconditionally. The admin session read already returns the full row (schema-derived), so `summaryFinal` is available to the template without repository changes.

**Alternative considered:** a badge only, keeping the Markdown render for raw summaries. Rejected — the render itself is the misleading part; a chip next to a beautifully-rendered fake doesn't undo the impression, and `<pre>` also displays transcripts more faithfully (they aren't Markdown).

## Risks / Trade-offs

- **[Risk]** `"async": true` may not behave as hoped for the `Stop` event specifically (undocumented edge case) → **Mitigation**: explicit e2e validation task before relying on it; documented fallback to a throttled counter, same pattern as `post-tool.sh`, zero design risk since that pattern is already proven.
- **[Risk]** A raw sync fires mid-turn while the transcript is momentarily inconsistent (e.g., mid-write) and produces a malformed summary → **Mitigation**: existing parser behavior is unchanged (same `_transcript.sh` functions already used by `session-end.sh`), and any garbage produced is still gated by Decision 1 — it can never reach `memory.context` because it's never curated (`final:false`).
- **[Risk]** Non-blocking raw syncs can land out of order: an async Claude `Stop` POST (or a hanging opencode `void` flush) from turn N could arrive after turn N+1's, briefly overwriting a newer transcript with an older one; or an in-flight POST could arrive after `/end` → **Mitigation**: already server-guarded and self-healing. `writeSummary` rejects writes on non-active sessions (`session_already_ended`, `agent-sessions.ts` — verified), so nothing can land after `/end`; an older-overwrites-newer inversion between two active-session raw writes self-heals on the very next turn's sync (both are `final:false`, and per-turn cadence makes the stale window one turn at most). Hermes cannot invert at all — its join-then-spawn threading serializes syncs per provider instance.
- **[Trade-off]** Sessions with raw-synced-but-uncurated summaries still show raw transcript text in the dashboard's session detail view → **Accepted because** the dashboard renders raw DB state by design (operator visibility); Decision 8 makes the raw-vs-curated distinction explicit (RAW chip + preformatted render) instead of hiding it behind a misleading Markdown render.
- **[Trade-off]** Codex keeps its existing blocking latency (up to 3s/turn) — full "zero latency on every client" isn't achieved → **Accepted because** Codex's hook execution model has no documented async escape hatch at all (confirmed: it silently skips hooks that request one); there is nothing this change can do about it without a Codex-side or upstream fix.
- **[Risk]** Hermes's background-thread POST could, on a crash-y host or an extremely short-lived process, get killed mid-request before the socket flushes → **Mitigation**: identical, already-accepted trade-off to opencode's existing `disposeFlushFireAndForget` (best-effort, may drop on abrupt exit); the _next_ turn's sync attempt (now every turn instead of every 5) makes any single dropped sync inconsequential.
- **[Risk]** Coordinating file overlap with the in-progress `proactive-save-nudges` change (`hooks.json`, `plugin.ts` both touched by both changes) → **Mitigation**: land `proactive-save-nudges` first (it's at 16/18 tasks); rebase this change's diffs against its final state before implementation.
- **[Trade-off]** `/summary`/`/end` still honor a client-supplied `final: true` over HTTP, so the "only MCP curates" invariant is a convention every current script happens to follow, not a server-enforced guarantee → **Accepted because** anyone with a valid bearer token for the HTTP endpoint already has the same token for MCP, where `memory.session_summary` reaches the identical outcome legitimately — hardening the HTTP path wouldn't raise the actual security bar, only remove a tested capability no current writer uses.

## Migration Plan

1. Land the predicate tightening + purge-sweep wiring (Decisions 1, 2) first — server-only, no plugin version bump needed, no client dependency.
2. Land the Claude Code `Stop` hook, the opencode periodic flush, and the Hermes cadence/threading/role-filter change (Decisions 3, 6, 7) together, since all three are plugin-tree changes and share one plugin version bump. Validate the `async` behavior empirically as part of this step; fall back per Decision 3 if needed.
3. No rollback complexity beyond normal revert — no data migration, no schema change, no irreversible write path introduced (the raw-sync writes were already possible via the existing HTTP endpoints, unchanged by this proposal; this only adds more callers of the same, already-tested `writeSummary`/`end` service methods).
