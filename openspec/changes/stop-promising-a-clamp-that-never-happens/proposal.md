# Stop promising a clamp that never happens

## Why

Six MCP tool surfaces tell agents something the server does not do. The change is named for the first one found — `clamped`, a required boolean whose `true` value no client can produce — but a sweep of all 24 registered tools through the real MCP boundary found five more, and one of them is a live code defect that makes an agent conclude nothing needs review. The rule this change adds is therefore stated once, generally, with the six as its scenarios.

All measurements below were taken through the real boundary (bootstrapped `createServer` + official MCP SDK `Client` over `StreamableHTTPClientTransport`), each with a control that had to pass.

**1. `memory.get({ids})` never computes review state, while its description promises it unconditionally.** This is the only code defect in the set and the one an agent is actively misled by today. `GET_DESCRIPTION` (`apps/server/src/mcp/server.ts:133`) says: "For an active memory the response also carries `reviewState`/`reviewAfter`: `needs_review` means re-verify". The batch branch (`apps/server/src/mcp/memory-tools.ts:1114-1136`) makes no `reviewStateForMemories` call, unlike `handleSearch` (`:992`) and the single-`id` path (`:1181-1187`); `memoryRow` declares both fields optional (`:331-332`) so nothing fails. Measured on the SAME row, adjacent calls, same connection: via `id` → `reviewState:"needs_review", reviewAfter:"2026-08-04T02:20:34.707Z", reviewEscalated:true`; via `ids` → those three keys absent entirely. Two controls passed — the single-`id` form and `memory.search` both emit review state for that identical row — so this is a defect in one branch, not a scope or fixture artefact.

The cost is concrete: `memory.context.needsReview` hands the agent a list of ids and tells it to re-verify, and the batch flow this repo teaches is `memory.confirm({ids})`. An agent that batch-reads those ids with `memory.get({ids})` sees no review signal on any of them and concludes the corpus is fresh. It also contradicts `openspec/specs/mcp-api/spec.md:297` verbatim — "each entry carrying the same per-memory shape as the single-`id` form" — and that sentence is false in BOTH directions: batch rows carry `lastSeenAt` but not `replaces`, the single-`id` form the reverse. No scenario pins the parity, which is why no test caught it.

**2. `memory.session_start`'s `reused` is a required output field named nowhere agent-facing.** Its description (`server.ts:280`) ends with a closed-form list that reads as exhaustive: "Returns: { sessionId, scope, projectId, startedAt }." The `outputSchema` (`apps/server/src/mcp/session-tools.ts:58-65`) marks SIX fields required, including `title` and `reused`. Measured: two consecutive `session_start` calls returned the SAME `sessionId` with `reused:false` then `reused:true`. `reused:true` means the call adopted the row `findActiveForTransport` found (`session-tools.ts:179-190`) instead of starting one — precisely the host-hook case the description's own first sentence is about. The single field that answers "did I just create a duplicate session or attach to the host's?" is the omitted one. Two published sentences are wrong too: `mcp-api/spec.md:500` enumerates only `{ sessionId, scope, startedAt, title }`, and `:1313` asserts "`memory.session_start` is unaffected — every call opens a brand-new session row and never touches a deleted one", which the measurement falsifies.

**3. `memory.doctor` offers one cause for a divergence that has two.** Its description (`server.ts:378`) says its counters differ from `memory.stats`' because they are "NOT scoped". True for `needsReview` — both sides reach the same `needsReviewPredicate` (`memory-repository.ts:755`) through `runCountNeedsReview`. False for `pendingJudgments`: `bootstrap.ts:568` uses `adminCountByStatus('pending')`, a bare `WHERE status='pending'` (`relations-repository.ts:438-445`), while `countPendingInScope` (`:408-424`) additionally requires `endpointsActive`. Measured inside a SINGLE project, so scope cannot explain it: before archiving an endpoint, doctor 1 / stats 1 / context 1; after, doctor **1** / stats **0** / context **0**. The behaviour is deliberate and specified (`openspec/specs/memory/spec.md:1130`, "that field SHALL remain an unfiltered count of pending rows"; `openspec/changes/archive/2026-08-01-filter-retired-endpoints-from-pending-queue/design.md:77-83` D5) — the defect is the prose. The sharp part: `memory/spec.md:1128` defines the very term the description leans on — "A count that included pairs the agent is not shown and cannot usefully close would not be a queue depth — it would be an inventory the agent has no way to drain" — and `:1130` exempts exactly this field from it. An agent that checks the one named cause, finds both calls resolve to one project, and sees the numbers still differ concludes one of them is stale. Naming one of two causes is worse than naming none.

**4. `clamped: true` is unreachable over the wire on `memory.context` and `memory.search_prompts`.** All four `memory.context` size arguments are rejected with `-32602 too_big` at max+1 (`sessions` 26, `prompts` 51, `memories` 101, `judgments` 51); at the maximum, and on an empty call, they return `clamped=false`. `25.5`, `-1`, `100.0001` are rejected too. The handler's flag is a disjunction of strictly-greater-than comparisons against the very bounds zod already enforced (`memory-tools.ts:1334-1338` against `contextSchema`'s `.max(25)`/`.max(50)`/`.max(100)`/`.max(PENDING_JUDGMENTS_MAX)` at `:260-262` and `:267`), so it is false for every input the transport admits. On `memory.search_prompts` the bracketing is exact on both sides — `z.number().int().min(1).max(100)` (`prompt-tools.ts:45`) against `clamp(requestedLimit, 1, 100)` (`services/prompts.ts:279-280`): `limit:101` → `-32602 too_big`, `limit:0` → `-32602 too_small`, `limit:100` / `limit:1` / omitted → `clamped:false` with `total:1` as the control.

And `memory.context`'s description contradicts itself about it: it contains both `asking for more is rejected, not clamped` (about `judgments`) and, as its literal tail, `the response includes a clamped:true flag if you asked for too much`. `openspec/specs/mcp-api/spec.md:2126` records that client truncation is a tail cut and "the LAST content of a description is what is lost first" — so the false clause is the most truncation-exposed text in the string.

**5. `memory.doctor.db.open` is a hardcoded `true`.** `apps/server/src/server/bootstrap.ts:571` builds `db: { open: true, … }` as a literal at the single production construction site; pragma failures land in `warnings` (`:525-533`) and the report still says `open:true`. `mcp-api/spec.md:841` makes `open` required contract surface. Fault-injected at the wire: after closing the DB handle the call never reached the handler — authentication died first at `tokens-repository.ts:26` and the transport returned 500. So `false` is unreachable because the state the field exists to report is one where the tool cannot answer at all. No prose promises `false`, so the impact is low; the shape is identical to `clamped`.

**6. `memory.timeline` rejects a bound its description never mentions.** Its description (`server.ts:334`) names neither `before` nor `after` nor the `invalid_input` its handler raises for `before + after > 50` (`memory-tools.ts:1531-1536`). Measured `{30,30}` → `invalid_input`, control `{25,25}` → ok. This one matters beyond its own size because `memory.timeline` is the tool this change holds up as the model: its _error message_ names the remedy ("for larger windows use memory.search"), which is `:2163`'s safety condition satisfied. If it is the model, its description has to be one.

**Why one general rule rather than six fixes.** This is now the seventh instance in three days of a family whose first member (`abstained`) was repaired on 2026-08-03. Fixing six tools one at a time would stack six special cases over shared infrastructure — the shape today's altitude review flagged — and a seventh would arrive as a seventh. The added requirement states the invariant once (the description, the declared `outputSchema` and the emitted payload must agree) with three named failure modes and three named remedies, and the six as scenarios. A future instance costs one scenario.

**The class is closed, not left ajar.** The sweep covered all 24 registered tools and measured the negative result too: every other `z.boolean()` / `z.literal()` under `apps/server/src/mcp/` has both wire values reachable, every error code any description names was reached at the wire, and `DIVERSITY_CAP` (which ships `null`) is named on no agent-facing surface. Named-and-reached: `headTruncated`, `truncated`, `reviewEscalated`, `entityIndexDraining`, `viaEntity`, `occupied`/`nearby`, `created`/`switched`/`previousSlug`, `titleFinal:false`, `judgmentRequired`, `candidatesDetected`, `capture_passive.reason`. `summaryFinal` is always `true`, but `mcp-api/spec.md:526` requires exactly that — specified, not a defect.

## What Changes

### The code defect (1)

- **`memory.get`'s batch branch computes review state, in one batched lookup for the page.** `reviewStateForMemories` already exists and is already used by `handleSearch` (`memory-tools.ts:992`), so this is a call, not a mechanism. `reviewState`/`reviewAfter`/`reviewEscalated` are emitted per row on the same status-driven terms as the single-`id` form — present for `active`, omitted otherwise.
- **`replaces` is added to the batch rows.** It is a column on the row already fetched; its absence is half of `:297`'s two-directional falsehood.
- **The description is NOT weakened.** `GET_DESCRIPTION` states the intended contract; the code is the defect. Chosen over the alternative of qualifying the description with "single-`id` form only", which would ratify the gap and leave `memory.context.needsReview`'s taught batch follow-up blind.
- **`:297`'s parity claim is replaced by an enumeration, and the deliberate asymmetries are named.** "The same per-memory shape as the single-`id` form" is unenforceable and was false both ways. The batch form keeps `lastSeenAt` (the single-`id` form advances the very signal it would report, so its value would be its own call's timestamp) and keeps NOT carrying the ancestry projection (`head`, `predecessors`, `predecessorCount`, `truncated`, `headTruncated`) or `confirmationCount` — those are per-target walks, and N of them would turn a bulk read into N ancestry queries. Both asymmetries are now spec text with reasons, so a future reader cannot mistake either for drift.

### Removals — fields whose reported state is unreachable (4, 5). **BREAKING** on three published output schemas

- **`clamped` leaves `memory.context` and `memory.search_prompts` — schema and payload together.** It is `required` in both declared schemas (`clamped: z.boolean()` with no `.optional()`, at `memory-tools.ts:548` and `prompt-tools.ts:73`) and present in `structuredContent`; measured `memory.context` keys are `clamped, needsReview, needsReviewTotal, pendingJudgments, pendingJudgmentsTotal, recentMemories, recentPrompts, recentSessions, relevantMemories, scope`. The SDK validates `structuredContent` against the cached schema, so dropping the key alone fails validation and dropping the schema field alone publishes an undeclared key.
- **`db.open` leaves `memory.doctor`.** Same shape, and nothing is lost: `integrity` (which returns `unknown` when the pragma read fails) and `warnings` are where a real database problem surfaces, and both vary.
- **Removal over description-only repair,** on the precedent `openspec/changes/archive/2026-08-03-scope-and-name-the-project-memory-count/design.md:90` set verbatim: "ship both fields for backward compatibility … **rejected. It preserves a field the change exists to discredit**, and a consumer reading the old key keeps getting the misleading number indefinitely." And `:98`, on why a loud break is the safer failure: keeping a key while its meaning changes "would ship changed semantics under an unchanged key, which is the worse of the two failure modes — a consumer has no signal to re-check."
- **The internal `clamp()` calls stay** (`memory-tools.ts:1332,1333,1373,1529,1530`, `prompts.ts:279`) as defensive bounds. `memory.search`'s `clampLimit` (`services/memory.ts:819-824`) is already in exactly this state, so keeping is the consistent choice; removing them would make the transport the only bound and leave a future direct caller of `buildMemoryHandlers` unbounded (D3).

### Structural

- **The four `contextSchema` maxima and `timelineSchema`'s window become named constants.** Today only `PENDING_JUDGMENTS_MAX = 50` (`memory-tools.ts:84`) is named; `25`, `50` and `100` each appear twice (schema `:260-262`, handler `:1332,1333,1373`) and `50` three more times for the timeline window (`:283,284,1531`) including inside the error message text, so a future bound change can silently disagree with the message it prints. The removals touch the second copy of each anyway. The timeline bound gets its OWN constant, not a shared one (D5).
- **The dead unit test is replaced with the wire test the behaviour has never had.** `context-pending-judgments.test.ts:205-216` calls `handlers.context({judgments: 999})` directly, bypassing the schema, and its own comment says the state is unobservable on the wire. In its place: each of the four arguments at max+1 asserting `-32602`, with an at-max control that must pass — the shape at `apps/server/src/test/mcp-integration.test.ts:378-410`, which already does this for `relations_limit`. Same for `prompts.test.ts:288-295`.
- **The two controls that must keep passing are named as controls:** `annotation-bound.test.ts:408` and `mcp-integration.test.ts:374` assert the `/rejected, not clamped/` substring. They are the evidence this change did not weaken `mcp-api/spec.md:2163` while removing the field that contradicted it.

**Closed by precedent — do not re-litigate.** "Relax the maxima so `clamped` becomes reachable" was already rejected in writing at `openspec/changes/archive/2026-07-30-bound-annotation-response-size/design.md:206-211`:

> **Clamping with a receipt** (clamp, and report the applied bound in the response) — not silent, and honestly the closest call. Rejected because it splits one parameter into two truths (requested vs applied) that a caller must reconcile on every read; because the caller only learns after paying for the round trip it was trying to budget; and because it adds a response field on every read to describe a situation that the description can teach an agent to avoid entirely.

and on the silent variant, `:200-204`:

> the caller cannot distinguish a clamped list from a complete one except by comparing against `relationsTotal`, which is the boolean-truncation-flag problem in a new place. It also contradicts the published "REJECTED, not clamped" in the requirement it would amend.

That design's Open question 2 keeps a door ajar for clamp-with-a-receipt _if rejections turn out to be common_ — but the instrument it names is a field rejection rate nobody collects, and nothing in this codebase counts `-32602` responses per parameter. The door is ajar onto a measurement that does not exist (D2, open question 1).

**Deferred with a stated reason, not dropped:**

- **`memory.context`'s relevance-channel signal.** Its description explains a small `relevantMemories` only as "empty if nothing is relevant" while `rankedPass`/`gateShortened` are reachable there — measured `rankedPass {abstained:false, gateShortened:true}` with `relevantCount 1` on a 7-row pool, control `{abstained:false}` with `relevantCount 5`. Deferred because it is **not an instance of this class**: no field is unreachable, no closed-form list is falsified, and "empty if nothing is relevant" is true as written. It belongs to a different requirement (`mcp-api/spec.md:744`), and it competes for the same 468 characters as the maxima clause this change owes under `:2163` — which is mandated, while the relevance clause is discretionary. Worth reopening on its own, though: the archived deferral's premise was "no measured benefit" (`archive/2026-08-03-tell-the-truth-about-the-relevance-gate/design.md:122`) and that premise is now falsified by the measurement above. Recorded as `tasks.md` 12.3 with the numbers, so the next change starts from evidence rather than rediscovering it (design open question 2).
- **`confirmationCount` on the batch form.** Not named by any description as a batch guarantee, and adding a per-row count to a bulk read is a query-shape decision for `db-performance-auditor`, not a guess inside a prose-correctness change (design D8, `tasks.md` 12.4).

**Explicitly out of scope, each with a reason:**

- **`POST /api/<slug>/memory/recall`'s silent clamp** (`openspec/specs/http-api/spec.md:384`, scenario `:402`). It clamps `limit` to `[1,5]` and publishes no field, so the new rule does not reach it, and it is not an agent-facing tool description. Named so the general requirement is not later read as demanding an HTTP change.
- **`memory.search`'s `clampLimit` and `memory.timeline`'s two clamps.** Equally unreachable in-process bounds with no flag, therefore no claim to correct (D3).
- **Any change to `DESCRIPTION_MAX_LENGTH`.** The cap does not move; all five descriptions grow inside it.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `mcp-api`: one requirement added, seven modified.
  1. **ADDED** — _A tool's description and its response MUST agree, and neither may promise an unreachable state_. The general rule with three failure modes (unreachable-state field · description misstates the response · stated cause is not the actual cause) and three remedies (remove the field · correct the description · **correct the code**). The third remedy is what makes `memory.get` a scenario of this rule rather than an exception to it, and what keeps the `abstained` repair conforming (design D6).
  2. **MODIFIED** — _The `memory.get` tool MUST return the memory and its history_ (`:291`). `:297`'s unenforceable parity claim becomes an enumeration; the batch form gains review metadata and `replaces`; the two deliberate asymmetries (`lastSeenAt`, the ancestry projection) are named with reasons; three scenarios pin the parity in both directions, with the single-`id` call as the control.
  3. **MODIFIED** — _The MCP server MUST expose three session-lifecycle tools_ (`:485`). The response shape at `:500` gains `projectId` and `reused`; new prose specifies the adoption path and makes `reused` required; two scenarios pin the two-consecutive-calls behaviour (same `sessionId`, one row) and the description/`outputSchema` agreement.
  4. **MODIFIED** — _The MCP server MUST expose two observability tools_ (`:834`). `db.open` leaves the response shape at `:841`, with a scenario that a database fault which still permits the call is reported through `warnings` and `integrity`.
  5. **MODIFIED** — _The observability tool descriptions MUST disclose which population their counters cover_ (`:856`). Doctor's description must name EVERY cause of the divergence, not only the population; two scenarios, one of which is the single-project measurement where population cannot explain the difference.
  6. **MODIFIED** — _Session-lifecycle MCP tools MUST reject soft-deleted sessions_ (`:1309`). `:1313`'s falsified sentence is replaced by the true reason `session_start` is unaffected (it resolves no row by id, and the adoption lookup excludes soft-deleted rows).
  7. **MODIFIED** — _The MCP server MUST expose three research tools_ (`:581`). `clamped` leaves the `memory.context` response shape (`:592`), the defaults scenario (`:642`) and the over-ask scenario (`:656-661`); the four maxima and the reject rule enter the prose and the description scenario; `memory.timeline` gains a description scenario. `:659` ("the server SHALL silently clamp to the maximum and SHALL include a `clamped: true` field in the response") is **unsatisfiable on the shipped build** and is the sentence this change retires; `:660`'s "in-process defence rather than the wire behaviour" clause goes with it — the defence survives in code, but a spec sentence whose only job is to excuse a field that no longer exists has no work to do.
  8. **MODIFIED** — _The MCP server MUST expose `memory.search_prompts`_ (`:1407`). `clamped` leaves the input-schema note (`:1417`), the JSON response shape (`:1440`) and the scenario at `:1471-1475`; a description scenario is added for `limit`'s bound.
- `mcp-api`'s reject-not-clamp requirement (`:2157`, prose `:2163`, scenarios `:2189,:2192,:2219`) is **NOT modified**. This change makes the surface agree with it; a requirement the code was violating needs no delta. Stated so the archive step does not look for one.
- `mcp-api`'s _Tool descriptions MUST stay below the client truncation ceiling_ (`:2120`) is **NOT modified**. The cap does not move and all five descriptions are satisfied within it.

Checked and deliberately given no delta:

- `memory` — defines the review-state derivation (`:971-976`) but not which surfaces carry it; the surface obligation is `mcp-api:295-297`, so the `memory.get` fix needs no `memory` delta. `:1130`'s "unfiltered count of pending rows" stays exactly as published — this change corrects the description of that behaviour, not the behaviour.
- `sessions` — the adoption path in `findActiveForTransport` is existing, specified behaviour; nothing about session lifecycle changes.
- `http-api` — `/api/<slug>/memory/recall`'s clamp is deliberate and publishes nothing (above).
- `dashboard` — no operator surface renders `clamped` or `db.open`. Design tokens untouched.

Completeness check: `grep -n clamp openspec/specs/mcp-api/spec.md` returns exactly `592, 642, 656, 659, 660, 661, 1417, 1440, 1471, 1474, 1475, 2163, 2189, 2192, 2219`. The first eleven move; the last four are the policy they contradicted and stay. (The explore brief listed fourteen; `:592` is the fifteenth, re-measured on the current tree, and it is the response-shape list naming `clamped` as a returned key — it must move or the shape and the payload disagree.)

## Impact

**Durable invariants.** None crossed. Append-only memory is untouched: no `DELETE`, no `content` `UPDATE`, no status flip, no `consolidation_ops` entry. Scope-at-the-service-layer is untouched: `scopeFromContext`/`requireScope` still resolve the `Scope` and pass it down, and the `memory.get` batch fix calls an existing service method (`reviewStateForMemories`) over rows a scoped read already returned — no new repository read, no scope widening. `topic_key` convergence, fresh-context judgment and derived-never-stored review state are all unaffected; the review fix makes an existing derived-at-read-time computation reach one more surface, which is exactly what that invariant prescribes (no column, no sweep, no new verb). **No SQL is added, moved or altered**, so `db/`-confinement is untouched. **No new MCP tool.** Locked dashboard design tokens are not read.

**Code:**

- `apps/server/src/mcp/memory-tools.ts` — batch branch (`:1114-1136`) gains a `reviewStateForMemories` call and emits the three review fields plus `replaces`. **`memoryRow` (`:310-337`) must gain `replaces` and `reviewEscalated` first**: it is the shared row schema for BOTH `memory.search` rows (`:376`) and `memory.get`'s batch rows (`:441`), and it currently declares `reviewState`/`reviewAfter` (`:331-332`) but neither `reviewEscalated` nor `replaces`, so emitting them without widening the schema fails output validation. Both are added OPTIONAL, so `memory.search` is unaffected — it emits `reviewState`/`reviewAfter` only (`:1061-1062`), and whether it should also emit `reviewEscalated` is pre-existing and out of scope (`tasks.md` 12.5). `contextOutput` loses `clamped` (`:548`), the disjunction (`:1334-1338`) and the response entry (`:1515`) go; the four `contextSchema` maxima (`:260-262`, `:267`) and the `timelineSchema` window (`:283-284`) become named constants used by the schemas, the surviving `clamp()` calls (`:1332,1333,1373,1529,1530`) and the timeline error message (`:1531-1536`).
- `apps/server/src/mcp/prompt-tools.ts` — `clamped` out of `searchPromptsOutput` (`:73`) and the response (`:197`).
- `apps/server/src/services/prompts.ts` — `clamped` out of `SearchByScopeResult` (`:65`), its computation (`:280`) and the return (`:299`); the `clamp` at `:279` stays.
- `apps/server/src/server/bootstrap.ts` — `db: { open: true, … }` (`:571`) loses `open`.
- `apps/server/src/mcp/session-tools.ts` — no schema change; `reused` and `title` are already required (`:58-65`). Only its description changes.
- `apps/server/src/mcp/server.ts` — five descriptions: `:312` (`memory.context`), `:334` (`memory.timeline`), `:367` (`memory.search_prompts`), `:378` (`memory.doctor`), `:280` (`memory.session_start`). `GET_DESCRIPTION` (`:133`) is deliberately **unchanged** — the code moves to meet it.
- `doctorOutput`'s `db` shape wherever it is declared, so the removed field leaves the published schema with the payload.
- Tests: `context-pending-judgments.test.ts:192,202` and `:205-216`; `mcp-integration.test.ts:893,1635`; `services/prompts.test.ts:214,288-295`. Must keep passing as controls: `annotation-bound.test.ts:408`, `mcp-integration.test.ts:374`.

**Existing installations.** **No migration. No schema change to the database.** No new column, index, trigger or table rebuild. Nothing derived needs invalidating: `memory_fts`, `memory_vec` and the three entity tables are not written, not read differently, and not re-scoped. First boot after upgrade on a populated installation performs no startup work. The one behaviour that changes on real data is `memory.get({ids})`, which starts returning review metadata for `active` rows — computed from `confirmations` and per-type TTLs that already exist, so no backfill and no first-run cost beyond one batched lookup per call (the same lookup `memory.search` already performs on every search).

**Rollback** is a plain image downgrade with no data step. An older server republishes the old schemas, re-emits `clamped: false` and `db.open: true`, and stops returning review metadata on batch reads. Nothing persisted differs, so there is no forward-only step to undo. The only client this could break is one that hard-requires a removed field, and the measured consumer set is zero: `grep -rn clamped apps/plugin/ docs/ README.md CONTRIBUTING.md` returns **0** lines; `handleContext` is reachable only from the tool registration (`server.ts:317`); the HTTP API has four routes and none is context (`api-router.ts:94,134,178,220`); `PromptsService.searchByScope` has exactly two non-test callers.

**Wire-visible behaviour on first boot**, stated plainly because three output schemas break: `memory.context` returns 9 keys instead of 10; `memory.search_prompts` 3 instead of 4; `memory.doctor`'s `db` block 3 instead of 4; `memory.get({ids})` rows gain up to four keys; five tool descriptions change text. No error code changes, no result set changes, no ordering changes, and no argument becomes newly valid or newly invalid. An agent that ignored the removed fields — which is every agent, since no plugin or doc names them — sees only better descriptions and a review signal it was promised all along.

**Plugin tree.** No change, verified rather than assumed: `grep -rn clamped apps/plugin` and `grep -rn "db.open\|reused" apps/plugin` return zero relevant lines, so no plugin release is implied and no per-client file is touched. All five descriptions are server-side and all four clients read them from `tools/list`; the bridge does not interpret response bodies. One shared resource, four clients, nothing to copy.
